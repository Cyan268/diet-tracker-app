## 问题、复现与修复

### 1. 请求超时不等于服务端没有执行

旧代码在 create 响应丢失后将事件标为 failed，后续编辑仍修改同一个幂等键的 payload；删除则取消 create。新增的两个回归先失败：编辑后 payload 不一致，删除后队列变为空。测试模拟服务端已接受请求、只丢响应，使用真实 SQLite 表执行客户端代码，不以 Mock SQL 断言替代队列状态。

现在首次发送前在事务中持久化 `first_attempt_at/request_path/request_body` 并增加尝试次数；只有从未发送的 pending create 可以合并或取消。后续编辑/删除拥有独立事件，以 `queue_order` 排在该记录的前驱之后。发送前重新读取事件，避免“选中队列后、正式发送前”发生编辑导致读取旧 payload。服务端身份未知的删除继续保留，create 找回成功后才发送删除。

```text
本地创建 → 冻结 create → 服务端提交，但响应丢失
                         ↓ 用户继续编辑/删除
重放原 create（同键同内容）→ 获得 server_id → 发送后继意图
```

重试的 PUT/DELETE 路径、请求体及版本也冻结。create 重放若返回被其他设备修改过的较新版本，不自动把本地后继意图基线提升到该版本，而是保留最初版本 1，交给已有冲突机制处理。用户明确选择“保留本机”时才产生新请求；云端已删除则换新 client_id，本地主键保持不变，由 `remote_client_id` 维护映射。

### 2. 账号相同不代表同一轮会话

旧认证回归先出现两个失败：A 的迟到 401 没有正确失效、logout 后迟到 refresh 返回了 authenticated。现在 `AuthSession.capture()` 保存 owner + epoch。登录、恢复、退出会改变 epoch；刷新、重发和返回结果都验证原会话，不允许拿 B 的 Token 发 A 的事件。同一个账号退出再登录也会使旧工作失效。

同步的出队、资料、分页、错误处理、游标与本地提交贯穿同一 scope；写事务前后校验，事务中发生会话变化则回滚。认证持久化串行，防止迟到的旧写覆盖新登录/退出。AuthContext 另以 UI 代次防止旧请求改变新账号的界面状态。已发给服务端的 A 请求可能仍完成，但只属于 A；本轮保证是旧结果不进入 B，不是撤销已经发送的网络请求。

### 3. 自增取号顺序不是提交顺序

真实 PostgreSQL 实验故意绕过新写入器：A 分配小 ID 后暂停，B 分配大 ID 并提交，读者将游标推进到 B；A 后提交后，`id > after` 查不到 A，旧问题复现。

新增 `user_sync_state` 和 `sync_changes.user_seq`。CRUD 和 Demo 种子/重置入口先获取同一用户状态行锁，再修改日志、递增行内序号、写快照事件；同事务提交/回滚。并发首次初始化用冲突忽略插入，随后 `SELECT ... FOR UPDATE`，读取时刷新 ORM 已缓存的计数。测试验证同用户 B 等待 A、另一用户能前进、回滚不发布序号、幂等重放只有一条事件、CRUD 依次产生 1/2/3。

v1 仍使用原全局 ID，OpenAPI 和客户端生成类型未变。切换后的同用户写入先拿锁、后分配全局 ID，也修复新事件的 v1 反序提交风险。user_seq 暂为内部准备字段；公开按用户序号与稳定快照属于 U4-02。历史回填不能找回旧客户端已经漏拉的数据。

### 4. Web 普通事务不等于 Native 独占事务

加入同一数据库实例共享的 FIFO 写入队列；Web 在队列中使用 regular transaction，Native 在队列中使用 exclusive transaction。所有运行期写入仓库经过这个入口，初始化迁移/种子在数据库开放给页面之前执行。数据库打开本身合并为一个 Promise，避免竞争打开不同实例使队列失效。失败事务不会阻塞后续队列。

应用内浏览器的独立内存数据库实际运行了 Expo SQLite WASM/Worker：旧写法将并发写入 B 一并回滚；新写法只留下 `preserved-B`，失败事务的游标行数为 0。SQLite 版本 3.50.3、crossOriginIsolated=true，未打开用户的 diet-tracker.db。

此队列只协调同一个 JS 运行时/数据库实例，不是跨标签页分布式锁；后台读取可能看到同连接尚未提交的临时状态，不应将这种读取结果持久化为业务决定。Native 目前只有 API 路由和队列单测，不以 Node SQLite 或浏览器结果代替真实原生运行时验证。

## 迁移、兼容与回滚

1. SQLite v4 新增字段、队列顺序和远端身份映射；不清空旧记录。旧 processing/failed/blocked 或 attempt_count>0 保守视为已尝试，不再允许 create 合并。若旧版本已经把首次 payload 改坏，新迁移不能恢复从未保存的原请求，需要冲突人工恢复，不能宣称自动修复全部历史数据。
2. PostgreSQL v9 以旧全局 ID 为每用户回填序号和高水位，保留全局 ID，不重解释现有游标。正式部署需维护窗口，暂停所有旧写入器、备份、迁移、启动全部遵循新锁顺序的版本，再验收。不支持新旧写入器混跑。
3. 旧镜像写 SyncChange 没有 user_seq，迁移后不能盲目回滚旧镜像；虽然迁移提供 downgrade，它不是业务数据恢复方案。上线回滚应采用验证过的兼容修订镜像，数据恢复单独操作。
4. 本轮没有新服务器连接、Render 修改、生产数据库访问、真实用户数据上传、付费模型调用，也没有启动手机连接。

## 遇到的工程问题

- Docker 初始未运行，批准启动 Docker Desktop 后使用独立临时容器；没有用 SQLite 的通过替代 PostgreSQL 锁语义。
- Windows 默认 Proactor 与 Psycopg 异步模式不兼容。Alembic 和 pytest 配置 SelectorEventLoop；pytest 用 loop factory，避免弃用的全局 policy 覆盖。依据：[Psycopg 官方文档](https://www.psycopg.org/psycopg3/docs/advanced/async.html)。
- 诊断页最初缺少 Metro `lazy=true`，导致 Worker 分包报错。对照仓库安装的 Expo 源码后修正测试入口；业务页面未因此改动。生产构建则因沙箱子进程 EPERM 重试，这与业务代码失败分开记录。
- 额外 schema drift 检查暴露旧助手表约束命名差异；本轮不重写历史迁移、不夹带助手改造，登记后由 U1-01 发布前处理。

## 面试回答与追问

**一分钟回答：** 我在离线同步中复现了“服务端已创建、客户端没收到响应”的故障。旧实现允许继续修改同键 payload，重试发生冲突；删除又可能留下云端孤儿记录。我把首次请求在发送前持久化冻结，后续意图单独排队；请求和写回绑定账号及会话代次，避免迟到请求串账号。服务端用每用户状态行锁保证日志和同步事件按提交顺序产生，在真实 PG 复现旧自增游标漏拉并验证修复。另用浏览器真实 SQLite Worker 证明写队列隔离回滚。代码和本地测试已完成，手机实测和上线尚未做。

1. **为什么 failed 不能直接当作没发送？** failed 是客户端看到的结果，可能请求未到达，也可能数据库已经提交而响应丢失。后者必须同键同内容找回结果；不能换键重建，也不能直接取消删除。
2. **为什么只检查 user_id 不够？** 同账号退出再登录仍会复用 user_id，但旧工作已过期；epoch 标记当前一轮会话，同时将 owner 固定用于 SQL 权限过滤。两者职责不同。
3. **为什么不是把序列换成时间戳？** 时间戳、分配 ID 都不代表提交顺序，也存在相同值/晚提交。锁必须在业务写入和分配事件之前获取，并由所有入口遵守。代价是同用户写入串行，不能对同用户承诺无限并发吞吐。
4. **用了锁就等于解决全部一致性吗？** 不是。这里锁解决新日志事件顺序；Profile 仍按时间戳 LWW、历史漏拉需稳定快照恢复、跨标签页和 Native 未实测。客户端写队列也不是数据库分布式锁。
5. **如何证明你不是只写了一套 Mock？** 响应丢失/会话测试使用真实 SQLite 执行迁移与 SQL；PG 竞争使用真实数据库和独立事务；Web 使用实际 WASM/Worker。每层仍有边界：请求丢失用测试服务模拟，未注入真实公网丢包或运行两台手机。

建议学习顺序：先画丢响应的时序，再读一个失败断言；之后读出队与冻结事务；最后讲 PG 自增为什么不能代替提交顺序。可用于简历的是已验证的实现与故障实验，不是“零丢失、全平台高可用、生产级 exactly-once”。
