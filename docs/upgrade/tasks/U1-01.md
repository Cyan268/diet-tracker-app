## 设计取舍

1. **启动与数据运维分离**：自动重启是高频生命周期事件，迁移、种子和重置是需维护窗口的低频数据操作。
2. **预检、存活和就绪分离**：配置正确不代表数据库可达；进程存活也不代表 Schema 已升级或 Redis 保护可用。
3. **最小网络入口**：Caddy 与 API 只共享 edge；PG/Redis 位于 internal data 网络，Caddy 不能进入。
4. **明确代理信任**：应用只信任固定 Caddy 地址；Caddy 用真实 TCP 对端覆盖攻击者提交的转发头。
5. **同源 Web 优先**：继续由 FastAPI 托管 Expo Web，保留 COOP/COEP 和 WASM MIME；图片对象存储尚未实现，不虚构跨域上传能力。

## 本轮发现并修复的问题

1. **镜像网络超时**：最初 npm registry 报 `EIDLETIMEOUT`，Caddy 拉取停滞。网络恢复后重新构建，未关闭 TLS 或更换未知镜像源。
2. **WSL 与 Docker Desktop 未集成**：Windows 的 `bash` 指向 WSL，脚本内找不到 Docker。改用已安装的 Git Bash 完成本地验收；是否启用 WSL integration 由用户决定。
3. **运行中预检固定 IP 冲突**：一次性 Caddy 容器继承 `172.30.91.2`，与运行中代理冲突。预检现在检测代理状态：已运行则 `exec` 验证，未运行才 `run` 一次性容器。
4. **Git Bash 路径改写**：`/etc/caddy/Caddyfile` 被改写为 `C:/Program Files/Git/...`。脚本只对该容器路径设置 `MSYS2_ARG_CONV_EXCL`，不关闭其他宿主路径转换。
5. **限流测试顺序耦合**：正常登录已经消耗访客桶，导致同一来源第 5 个伪造请求提前 429。最终从新的 edge 测试容器发起请求，既不清库也不修改限流算法。
6. **隔离 PG 护栏和工作目录**：错误库名被测试主动拒绝；空库缺 `alembic_version`；从仓库根运行又无法导入 migrations。最终顺序是规定库名 → 在 `backend` 迁移 → 在 `backend` 测试。

## 面试追问

1. **为什么不让 API 启动时自动迁移？** 多实例或自动重启可能竞争迁移；更严重的是旧逻辑还会重置演示数据。启动必须幂等，数据变更必须显式、有窗口、可停止。
2. **预检通过为什么还需要 readiness？** 预检只检查配置和拓扑。空数据库也可能建立 TCP 连接，所以 readiness 还必须核对数据库与镜像要求的 Alembic head。
3. **JWT 已经鉴权，为什么还要网络隔离？** JWT 保护业务资源，不保护数据库端口，也不能阻止伪造转发头绕限流。入口、网络、Host、代理信任和用户鉴权解决不同层的问题。
4. **如何证明重启无副作用？** 对相同合成库连续重启 API 两次，比较用户、日志、事件数量和 Schema；同时启动命令中没有 Alembic、种子或重置入口。
5. **这轮最有价值的故障是什么？** 运行中预检的固定 IP 冲突。静态 YAML 全绿看不出它，只有在真实拓扑已运行时再次执行运维命令才会出现。
