## 核心设计与取舍

1. **tag 用于人读，digest 用于机器执行**：Git SHA 解释代码来源，digest 固定实际字节；生产同时要求两者和 OCI 标签一致，拒绝 `latest`。
2. **CI 与 CD 分权**：PR 只验证和产出证据；人工 workflow 只发布镜像/manifest，不自动接触服务器。生产 environment 还需仓库管理员配置 required reviewers。
3. **互斥覆盖整个危险窗口**：锁从读取候选前的状态校验持续到冒烟和 manifest 提升，避免两个进程交错迁移、切换或覆盖 previous。
4. **备份必须可验证且绑定发布**：custom dump 还要通过 `pg_restore --list`、文件 SHA-256、release/source 绑定；但本机可读不等于异地可恢复。
5. **失败停止优先于假可用**：先停旧写入器再迁移；任何 upgrade/check/目标版本失败都不启动候选、不提升 current。代价是首版有维护窗口。
6. **数据库前滚，应用可回滚**：回滚前检查旧 manifest 是否兼容当前 Schema；绝不自动 downgrade。破坏性 contract 迁移要等回滚窗口结束并单独执行。

## 遇到的问题与可复现命令

### 1. Docker 基础层下载停滞

失败命令：

```powershell
docker build --file Dockerfile.production --target vps --build-arg BUILD_REVISION=u1-02-previous --build-arg SOURCE_REVISION=local-previous --tag nutripilot:vps-u1-02-previous .
```

`python:3.13-slim` 的 11.91 MB 层连续约 100 秒停在 3.15 MB。没有关闭 TLS、改未知镜像源或把旧源码挂载说成新构建。由于 U1-02 要验证发布编排而 U1-01 镜像已经完成内容验收，本地用该镜像生成两个仅 OCI 标签不同的变体；CI 仍从 Dockerfile 完整构建。

### 2. Caddy 候选预检缺少可执行文件

失败症状：`exec: "validate": executable file not found in $PATH`。直接 `docker run` 不使用镜像默认 CMD；Caddy 镜像也没有把二进制设成 ENTRYPOINT。修复为显式参数 `caddy validate --config ...`，并新增命令形状单测。

### 3. 文件 capability 与过度限制冲突

第二次错误：`exec /usr/bin/caddy: operation not permitted`。Caddy 二进制带低端口 capability，断网校验容器同时使用 `cap-drop ALL + no-new-privileges` 会在 exec 阶段被内核拒绝。预检保留 `--network none`、只读根和临时 `/data`/`/config`，移除互相冲突的 capability 参数。运行时代理安全边界仍由 Compose 单独定义。

### 4. Pytest 临时目录 ACL 误报

沙箱内 `tmp_path` 在 Windows 报 `PermissionError: pytest-of-31572`，测试尚未进入业务断言。在受控沙箱外运行同一文件 8/8 通过；随后一次性真实 PG 完整套件 155/155。判断依据是失败栈位于 fixture setup，而不是通过删除测试或放宽断言“修复”。

### 5. 本机漏洞扫描缺少 Docker 登录

准确命令：

```powershell
docker scout cves --only-severity critical,high --exit-code --format sarif --output deploy/.local/u1-02/scout.sarif.json local://nutripilot:vps-u1-02-candidate
```

Scout 返回“Log in with your Docker ID”，没有生成漏洞结论。用户若要本机复测，可先在 Docker Desktop 登录，再执行上面命令；项目正式 CI 选择 Trivy，避免把个人 Docker 账号变成 PR 门禁依赖。

## 面试追问

1. **为什么 Git SHA tag 仍不够？** 仓库 tag 可以被覆盖或重新推送，digest 才固定 registry 中的内容。SHA 负责可追溯，digest 负责不可变，镜像标签再防止构建参数与源码不一致。
2. **为什么迁移前要停止旧 API？** 本次 v9 改变同步写入顺序，旧写入器不遵守新用户锁。首版用维护窗口换确定性；若将来要零停机，必须先设计真正向前/向后兼容的 expand 阶段。
3. **为什么不自动 downgrade？** DDL 和数据重写可能不可逆，旧应用也可能不知道新数据含义。回滚应用前验证兼容 Schema；不兼容时前滚修复或按独立恢复方案处理。
4. **互斥只用 GitHub concurrency 不行吗？** GitHub 只约束该工作流；管理员可能在服务器手动运行或有多个 runner。宿主状态目录锁是最后一道控制面互斥，两层解决不同入口。
5. **有 pg_dump 为什么还不能说可恢复？** dump 可能截断、密钥缺失、存储同盘，或从未真正 restore。当前只证明格式可读和哈希稳定；U1-03 要加密异地保存并恢复到隔离库后做业务校验。
6. **故障后为什么服务会暂时停止？** 这是明确的失败模式：不让与 Schema 不匹配的候选对外假健康。首版接受维护窗口；告警和人工回滚/前滚必须跟上。
