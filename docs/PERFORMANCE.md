# PostgreSQL API 性能基线

## 结论

2026-07-17 在本机 Docker Compose 环境完成第一次可复现的 API 混合读写基线。30 秒内共发出 2,950 个 HTTP 请求，错误率为 0%，所有检查通过；日志查询、增量同步查询和日志写入的 P95 分别为 27.29 ms、31.73 ms 和 38.32 ms。

这组数据用于发现后续代码改动造成的性能退化，不代表生产环境最大容量。简历和面试中不能把 97.61 req/s 表述为“系统支持 100 QPS”。

## 测试环境

| 项目                | 配置                                             |
| ------------------- | ------------------------------------------------ |
| 日期                | 2026-07-17                                       |
| CPU                 | Intel Core i7-14650HX，16 核 24 线程             |
| 主机内存            | 15.8 GB                                          |

| 数据库              | PostgreSQL 17 Alpine                             |
| 缓存                | Redis 7.4 Alpine（本场景未进入业务请求主链路）   |

| 网络                | API、k6、PostgreSQL 位于同一台电脑的 Docker 网络 |

同机 Docker 网络没有公网延迟、TLS、负载均衡和多实例调度开销，因此延迟通常会优于真实生产环境。

## 负载模型

压测开始时只注册一个隔离测试账号，随后并行运行两个场景：

| 场景   | 执行器                  |                          负载 | 请求                                                                  |
| ------ | ----------------------- | ----------------------------: | --------------------------------------------------------------------- |
| 读请求 | `constant-vus`          |      10 个固定 VU，持续 30 秒 | 每轮并行查询日志列表和 `after=0` 的前 100 条同步变更，然后等待 200 ms |
| 写请求 | `constant-arrival-rate` | 每秒启动 5 次迭代，持续 30 秒 | 每次使用新 `client_id` 创建一条自定义食物记录                         |

读场景使用固定虚拟用户，表达“10 个用户持续操作”；写场景使用固定到达率，表达“无论单次响应快慢，都尝试每秒发起 5 次写入”。二者不能直接换算为真实在线用户数。

## 验收阈值

| 指标              |       阈值 |                结果 |
| ----------------- | ---------: | ------------------: |
| 自定义 API 错误率 |     `< 1%` |                  0% |
| k6 检查通过率     |    `> 99%` | 100%（2,949/2,949） |
| 日志查询 P95      | `< 200 ms` |            27.29 ms |
| 同步查询 P95      | `< 200 ms` |            31.73 ms |
| 日志写入 P95      | `< 500 ms` |            38.32 ms |

## 详细结果

| 指标           |   平均值 |   中位数 |      P90 |      P95 |    最大值 |
| -------------- | -------: | -------: | -------: | -------: | --------: |
| 全部 HTTP 请求 | 13.16 ms |  8.58 ms | 19.41 ms | 31.97 ms | 310.47 ms |
| 日志查询       | 12.24 ms |  8.07 ms | 16.98 ms | 27.29 ms | 290.44 ms |
| 同步查询       | 13.01 ms |  8.65 ms | 17.92 ms | 31.73 ms | 284.64 ms |
| 日志写入       | 22.68 ms | 17.62 ms | 28.74 ms | 38.32 ms | 310.47 ms |

- HTTP 请求：2,950 个，平均 97.61 req/s。
- 业务迭代：1,550 次，平均 51.29 iterations/s。
- 接收数据：约 99.6 MB；发送数据：约 1.44 MB。
- 注册请求只在 `setup()` 中执行一次，所以 HTTP 请求数比业务检查数多 1。

最大延迟约 310 ms，但 P95 仍小于 40 ms，说明少量请求存在长尾。面试中应同时说明分位数和最大值：P95 描述大多数用户体验，最大值帮助发现偶发抖动，两者不能互相替代。

## 运行方式

先启动 API、PostgreSQL 和 Redis：

```powershell
docker compose up -d --build
npm run load:test
```

直接调整场景参数的示例：

```powershell
docker compose --profile loadtest run --rm `
  -e DURATION=60s `
  -e READ_VUS=20 `
  -e WRITE_RPS=10 `
  loadtest run --summary-export=/results/postgres-local-baseline.json `
  /scripts/api-baseline.js
```

原始结果保存在 [`load-tests/results/postgres-local-baseline.json`](../load-tests/results/postgres-local-baseline.json)，场景代码位于 [`load-tests/api-baseline.js`](../load-tests/api-baseline.js)。

## 当前限制与下一轮计划

- 30 秒、2,950 个请求的样本适合建立基线，不足以证明长时间稳定性。
- 所有请求共用一个账号，既不代表多租户分布，也会让日志列表和 `after=0` 同步页逐渐增大。
- 实际客户端会推进同步游标；本场景固定 `after=0`，反复读取前 100 条快照，偏向较重的同步读取。
- 未覆盖登录、Argon2 密码哈希、Refresh Token 轮换、图片上传和未来的 AI 调用。
- 未在压测期间采集 CPU、内存、数据库连接池、慢查询与锁等待，暂时不能解释长尾来源。
- 未做逐级增加负载直至阈值失败的容量测试，因此不知道饱和点。
- 下一轮应增加 10 分钟稳定性测试、分级容量测试、服务端结构化指标和 PostgreSQL 查询分析。
