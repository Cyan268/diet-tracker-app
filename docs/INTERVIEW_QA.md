# 项目面试问题库

本文件用于项目完成后的口头复习。回答应遵循“背景 → 问题 → 方案 → 取舍 → 结果”的顺序，避免只罗列技术名词。

## 一分钟项目介绍

> NutriPilot 是一个 AI 多模态饮食记录与个性化营养分析平台。项目最初是基于 React Native 和 SQLite 的本地饮食记录 App，我将它升级为具备 FastAPI 后端、PostgreSQL 云端数据、离线同步和 AI 结构化识别的全栈系统。用户可以通过自然语言或图片生成饮食草稿，系统使用结构化输出、食品实体匹配和人工确认降低模型幻觉，再由确定性代码计算营养数据。AI 助手通过 Tool Calling 查询用户真实数据，而不是让模型自行编造结论。项目还会建立评测集，持续跟踪准确率、修改率、延迟和调用成本。

注意：上述介绍中的未完成功能，在对应代码和测试完成之前不能用于正式简历。

## 架构与全栈

### 1. 为什么保留 SQLite，又增加 PostgreSQL？

SQLite 面向单设备离线读写，PostgreSQL 是多用户云端真实数据源。两者职责不同：SQLite 改造成缓存和离线队列，PostgreSQL 负责账号下的持久数据、约束和跨设备查询。

### 2. 为什么选择 FastAPI？

AI 应用大量使用 Python SDK，FastAPI 对类型注解、异步 I/O、Pydantic 校验和 OpenAPI 支持较好，适合快速建立类型明确的 API。它不是唯一选择；若团队以 Java 为主，Spring Boot 也完全可行。

### 3. 为什么不直接使用微服务？

当前规模下，微服务会增加服务发现、分布式事务、日志追踪和部署复杂度，却没有明确收益。先采用模块化单体保持清晰边界；AI 图片任务可以先作为独立 Worker 异步扩缩容。

### 4. 什么是幂等，项目中为什么需要？

幂等表示同一个请求执行一次或多次，最终业务效果相同。移动端离线同步可能因超时重复上传，所以每次本地写入需要稳定的客户端事件 ID，后端用唯一约束防止创建重复饮食记录。

### 4.1 为什么 FastAPI 使用异步，但不是所有函数都盲目写成 async？

异步主要提升 I/O 等待期间的并发利用率，适合数据库、Redis、对象存储和模型 API。CPU 密集任务不会因为 `async` 自动变快，反而可能阻塞事件循环，应该交给 Worker 或进程池。

### 4.2 Engine 和 Session 有什么区别？

Engine 管理数据库方言和连接池，可被应用复用；Session 是一次有状态的工作单元和事务边界。AsyncSession 不能被多个并发任务共享，所以每个请求需要独立 Session。

### 4.3 Liveness 和 Readiness 有什么区别？

Liveness 判断进程是否还活着，失败通常触发重启；Readiness 判断实例是否能接收流量，失败通常只从负载均衡摘除。数据库故障时，本项目保持 Live 200、Ready 503。

### 4.4 为什么既有 pyproject 版本范围，又有 lock 文件？

版本范围表达项目兼容的依赖区间，方便维护和安全升级；lock 文件记录已经验证的精确依赖树，保证开发、CI 和容器结果可复现。升级依赖时应重新运行测试后更新 lock。

### 4.5 为什么 Access Token 和 Refresh Token 要分开？

Access Token 只有 15 分钟有效期，签名和有效期无需查询令牌表；本项目仍会加载用户以确认账号有效。Refresh Token 有效期更长，只用于换取新令牌，并在数据库中保存状态以支持登出、轮换和重放检测。只用长期 JWT 虽然简单，但泄漏后难以及时撤销；每次请求都查询会话表又会增加延迟和数据库负载。

### 4.6 Refresh Token 被重复使用时发生什么？

正常刷新会把旧令牌标记为已撤销，创建同一 `family_id` 下的新令牌，并记录替换关系。如果旧令牌再次出现，说明客户端并未遵守轮换协议，或者旧令牌副本已泄漏。服务端会撤销这个家族里仍有效的令牌，要求用户重新登录。PostgreSQL 中通过行锁串行化同一令牌的并发刷新，避免两个请求同时成功。

### 4.7 为什么密码用 Argon2id，而 Refresh Token 摘要用 SHA-256？

用户密码通常熵低，攻击者拿到数据库后可以高速猜测，所以需要带盐、内存困难且计算昂贵的 Argon2id。Refresh Token 由安全随机源生成，具有约 384 bit 原始随机性，攻击者无法现实地穷举，因此数据库只需保存 SHA-256 摘要用于等值查找。不能因为 SHA-256 适合随机令牌，就用它直接保存密码。

### 4.8 为什么 Argon2 放到线程池执行？

数据库调用属于异步 I/O，等待期间事件循环可以处理其他请求；Argon2 是刻意设计得较慢的计算任务，直接在 `async` 函数中运行会阻塞事件循环。项目把密码哈希和验证交给线程池，让事件循环保持可响应。线程池并不会让单次哈希更快，它解决的是并发请求互相阻塞的问题；高并发下仍需限制认证速率和线程池容量。

### 4.9 这套认证目前验证到什么程度？

SQLite 集成测试覆盖了注册、大小写邮箱去重、错误密码、Bearer 鉴权、刷新轮换、旧令牌重放后撤销令牌家族、幂等登出和数据库只存摘要。Docker 中的真实 PostgreSQL 已完成 Alembic v1-v4 迁移、日志 CRUD、游标/tombstone 冒烟，以及双请求幂等新增、乐观锁更新、Refresh Token 重放竞争测试。三项并发正确性测试均通过，但这不代表高负载性能、连接池容量和 P95 延迟已经验证。

### 4.10 移动端为什么不把 Access Token 和 Refresh Token 都持久化？

Access Token 短期且请求频繁，只保存在内存；Refresh Token 有效期长，保存在系统安全存储以支持冷启动恢复。这样减少 Access Token 的长期落盘暴露面，也避免每次请求都访问安全存储。安全存储不能防住已解锁设备上的恶意进程，所以还要配合短 Access Token、Refresh Token 轮换、服务端撤销和重放检测。

### 4.11 多个请求同时返回 401 时如何避免刷新令牌被重复使用？

认证会话保存一个共享的刷新 Promise。第一个 401 创建刷新请求，其余请求等待同一个结果；刷新成功后每个原请求只重试一次。若各自刷新，一次性 Refresh Token 可能只有第一个成功，后续请求会被服务端识别为重放并撤销整个令牌家族。

### 4.12 离线启动时为什么还能进入 App，这是否绕过了认证？

它只允许读取已在本设备上、按该账号隔离的 SQLite 数据，不代表获得新的云端授权。应用保存最小用户会话，在无法连接服务端时进入 `offline-authenticated` 状态；所有云端请求仍需有效 Access Token 或恢复网络后刷新。用户主动退出会删除安全存储中的 Refresh Token 并清空活动账号。

## AI 工程

### 5. 这个项目和普通 LLM 套壳有什么区别？

核心区别是模型被放在受约束的业务链路中：结构化输出必须通过 Schema 校验；食品必须匹配数据源；低置信度结果要求确认；确定性计算不交给模型；每次调用记录版本、延迟、成本和反馈；模型升级前运行评测集。

### 6. 如何减少幻觉？

- 缩小模型职责，只提取候选信息。
- 使用结构化输出和枚举约束。
- 通过食品数据库和工具提供事实。
- 对低置信度或缺失字段追问用户。
- 不允许未经确认的 AI 结果直接落库。
- 使用固定评测集做回归测试。

### 7. RAG 是否是项目核心？

不是。用户饮食统计属于结构化数据，应该通过 SQL 和 Tool Calling 查询，而不是先转成文本做向量检索。只有在需要检索大量营养指南、菜谱或非结构化知识时，RAG 才可能有价值。

### 8. 如何评价 AI 功能好不好？

不仅看模型输出“像不像”，还要记录 Schema 合法率、食物识别准确率、实体匹配准确率、用户直接接受率、字段修改率、P95 延迟、失败率和单次调用成本。

## 数据库与同步

### 9. 如何处理同一条记录在两台设备上同时修改？

第一版可以采用版本号或 `updated_at` 的乐观并发控制。请求携带客户端看到的版本；服务端版本不一致时返回冲突，由客户端提示用户选择，或按明确的字段级规则合并。不能悄悄覆盖而不记录。

### 10. 为什么需要数据库迁移？

`CREATE TABLE IF NOT EXISTS` 只能创建缺失表，无法可靠描述字段新增、约束变更和数据回填。迁移文件为每次 Schema 变化提供有序、可审计、可重复执行的升级路径。

### 10.1 为什么迁移必须放在事务里？

一个迁移可能包含多条 Schema 修改或数据回填。如果执行到一半失败但前半部分已经生效，数据库会处于无法准确描述的中间状态。事务保证这些修改要么全部成功并提升版本，要么全部回滚。

### 10.2 如果数据库版本比 App 支持的版本高怎么办？

拒绝继续访问并提示升级 App。旧版本代码并不了解新 Schema，继续读写可能破坏数据，不能简单把版本号降回去。

### 10.3 项目如何保证离线重试不产生重复记录？

客户端在本地创建记录时生成稳定的 `client_id`，所有网络重试复用该值。服务端以 `(user_id, client_id)` 建立唯一约束，并保存规范化请求指纹。同键同内容返回已有记录；同键不同内容返回 409，提示客户端错误复用了幂等键。应用层预查询改善正常路径体验，数据库唯一约束负责处理两个请求同时通过预查询的竞争条件。

### 10.4 为什么使用乐观锁，而不是更新前加数据库行锁？

饮食记录通常由单个用户低频修改，冲突概率低。乐观锁不在用户思考和网络传输期间持有连接或行锁：客户端读取 `version=1`，更新时提交 `expected_version=1`，SQL 只更新版本仍为 1 的记录并把版本加一。影响行数为 0 表示记录已被其他设备修改，返回 409。悲观锁更适合冲突频繁且事务很短的场景。

### 10.5 如何防止用户读取或修改别人的饮食记录？

不能先按资源 ID 查询，再在 Python 中判断所有者；一旦某条分支漏掉判断就会产生 IDOR。项目所有读、改、删 SQL 都同时带 `id` 和当前令牌解析出的 `user_id`，列表和统计也先按 `user_id` 过滤。访问其他用户资源统一返回 404，不暴露该 UUID 是否真实存在。数据库外键负责完整性，查询所有权条件负责授权，两者职责不同。

### 10.6 为什么饮食记录要保存营养快照？

食品目录的营养数据可能被修正。如果历史记录每次统计都重新关联当前食品数据，过去已经确认的摄入量会悄悄变化。项目在创建饮食记录时由服务端确定性换算并保存 kcal、蛋白质等快照；之后食品目录更新不影响历史事实。代价是数据冗余，但获得了可追溯性和稳定统计。

### 10.7 Transactional Outbox 解决了什么，没解决什么？

它把业务写入和“稍后同步”的事件放在同一个本地事务中，避免 App 崩溃后只留下业务数据却丢失同步意图。Worker 可以至少一次投递，但网络超时会让同一请求重复到达服务端，因此仍需 `client_id` 幂等和数据库唯一约束。它也不自动解决多设备冲突；冲突仍需版本号、拉取最新值和用户合并流程。

### 10.8 为什么同步事件要有 pending、processing、failed 和 blocked？

pending 表示等待发送，processing 用于并发抢占，failed 表示可自动重试的网络或临时错误，blocked 表示 409/422 这类继续重试也不会自行恢复的业务问题。processing 事件若超过阈值会被判定为进程中断并恢复为 failed。明确状态比一个布尔值更便于恢复、监控和向用户解释。

### 10.9 本地 SQLite 如何防止切换账号后看到他人数据？

每条用户数据和 Outbox 事件都有 `owner_user_id`，Repository 的读取、更新、删除、聚合和导出都必须绑定当前账号。旧版无主数据只由第一个登录账号在事务中认领。仅在 UI 隐藏数据不够，因为导出、统计或按 ID 查询仍可能泄漏，所以隔离条件必须下沉到数据访问层并用双账号测试验证。

### 10.10 为什么没有为了清零漏洞直接运行 `npm audit fix --force`？

兼容范围内修复后，高危和严重项已经为 0；剩余中危的自动修复要求 Expo 54 跨主版本到 57。`--force` 可能同时破坏 React Native、原生模块、Metro 和测试工具链，因此应在独立升级任务中依据迁移指南并做真机回归。安全工作的目标是识别、降低和跟踪风险，而不是牺牲可运行性换一个好看的数字。

### 10.11 为什么增量同步使用整数游标，而不是更新时间？

更新时间可能相同、精度有限，分页时容易遗漏边界记录，而且无法表示已经物理删除的记录。项目在业务事务中追加带单调递增 ID 的变更事件，客户端按 `id > cursor` 拉取；删除用 tombstone。整数游标不是权限边界，接口仍然强制按当前 `user_id` 查询。

### 10.12 为什么 upsert 事件保存完整快照？

如果变更事件只保存记录 ID，客户端拉取较旧事件时原记录可能已经再次更新或删除，服务端无法还原当时状态。不可变快照让分页可以确定重放，代价是存储冗余。生产环境可做压缩和保留策略，但必须同时设计过期游标与全量重建协议。

### 10.13 客户端何时推进同步游标？

只有整页变更、冲突记录和新游标在同一个 SQLite 事务中成功提交后才推进。若先推进游标再写数据，崩溃会永久漏掉一页。每个账号拥有独立游标，避免切换账号时复用其他用户的同步进度。

### 10.14 云端修改与本地待发送修改冲突时怎么处理？

如果远端版本高于本地记录的 `server_version`，或远端已删除但本地仍在修改，拉取器不会覆盖本地数据，而是阻塞 Outbox 并保存远端快照。用户选择云端时取消本地事件；选择本机时更新并发基准后重试。远端删除时，保留本机会重新创建一条云端记录。

### 10.15 这套增量同步目前还缺什么生产化能力？

缺少变更日志保留与过期游标重建、字段级冲突合并、私有食品目录同步、同步成功率和延迟监控，以及两台 Android 设备、弱网、压力性能和进程崩溃测试。真实 PostgreSQL 的迁移、顺序 API 冒烟和三类双请求竞争已通过，但仍不能声称已经验证生产级跨设备可靠性。

### 10.16 为什么真实 PostgreSQL 并发测试不能被 SQLite 测试替代？

SQLite 的写锁粒度、事务调度和 `SELECT FOR UPDATE` 行为与 PostgreSQL 不同。项目默认测试继续使用 SQLite保证速度，但额外提供 opt-in Docker 测试：两个请求同时使用同一幂等键、同一 expected_version 或同一 Refresh Token。只有真实 PostgreSQL 才能验证唯一约束竞争、条件 UPDATE 和行锁序列化的实际行为。

### 10.17 三个并发测试通过后，为什么还不能说“支持高并发”？

这些测试证明两个竞争请求下的业务结果正确，不测吞吐量、连接池耗尽、锁等待时间、P95/P99 延迟和限流效果。“并发正确性”和“并发性能”是两件事。项目随后用 k6 建立了固定负载的性能回归基线，但还需要阶梯加压和资源监控才能得到容量结论。

### 10.18 为什么读请求使用固定 VU，写请求使用固定到达率？

固定 VU 模拟一定数量的用户循环发起操作，响应变慢时完成吞吐会自然下降，适合读操作的交互模型。固定到达率按时间启动迭代，不因响应变慢而主动降速，适合表达每秒持续进入的写流量。两者并行能形成可重复的混合负载，但 VU 和真实在线用户数不能直接等同。

### 10.19 97.61 req/s 是否表示系统支持约 100 QPS？

不能。它是 10 个读 VU、每秒 5 次写入、30 秒、单机 Docker 网络和当前数据规模下的实际吞吐。测试没有逐级加压到阈值失败，也没有覆盖公网、TLS、多实例或长时间运行，所以只能作为版本回归基线。容量结论至少需要阶梯负载、明确 SLO、稳定性时长以及 CPU、内存、连接池、慢查询和锁等待数据。

### 10.20 最大延迟超过 300 ms，为什么 P95 仍只有约 38 ms？

P95 表示 95% 的样本不超过该值，最大值只取最慢的一个请求；少量长尾不会把 P95 推到最大值。用户体验和回归门禁通常看 P95/P99 与错误率，最大值仍用于提醒偶发抖动。本轮尚未采集服务端资源与查询追踪，所以不能武断归因，下一轮要结合慢查询和连接池指标定位。

### 10.21 为什么 React Native App 在 Web 上还需要额外适配？

UI 组件跨平台不等于原生能力完全一致。本项目的 SQLite Web 版依赖 WASM、Worker、`SharedArrayBuffer` 和 COOP/COEP；SecureStore 没有 Web 实现；独占事务 API 也不支持 Web。我为 WASM 配置 Metro 和带安全头的本地预览服务器，Web 会话使用标签页级 `sessionStorage`，事务适配器在 Web 使用普通异步事务、在 Android/iOS 保留独占事务。后端 CORS 使用明确来源白名单。这样差异集中在基础设施层，业务 Repository 不需要理解平台细节。

### 10.22 为什么饮品选项使用“单品规则优先、通用规则回退”？

通用糖度、奶基和小料能减少重复数据，但直接合并会让美式和果汁出现牛奶选项。项目把糖度、奶基视为互斥配置：单品声明规则时只返回单品规则，否则才回退通用配置。相比在 UI 中判断名称，这种规则下沉到目录和 Repository 后可复用、可单测，也不会因为页面重构而失效。

### 10.23 为什么不能宣称饮品库“完整且营养精确”？

品牌菜单会按季节、地区、门店、杯型和冷热变化，公开网页也不等于稳定的数据 API。当前项目覆盖 20+ 品牌和 100+ 代表产品，但除品牌明确公开的营养值外，其余是标准杯工程估算；UI 显示版本和估算声明。生产化需要服务端目录、来源与采集时间、规格维度、可信度、审核和过期策略。诚实描述数据边界比虚构“全量精确”更能体现工程判断。

### 10.24 个性化营养目标是如何计算的，局限在哪里？

项目用年龄、身高、体重和生理性别进入 Mifflin–St Jeor 公式估算 BMR，再乘活动系数得到 TDEE，最后按减脂、维持或增肌目标调整能量；蛋白质按体重估算，脂肪按能量比例计算，碳水使用剩余能量反推。糖、钠、咖啡因显示为公共健康提醒上限。公式和活动级别都有误差，只面向普通成年人日常记录，不适用于孕期、未成年人、慢性病治疗或专业运动营养处方。

### 10.25 为什么模型输出通过 JSON Schema 后仍不能直接保存？

Schema 只验证类型、必填字段和数值范围，无法证明“这份食物确实有这些营养值”。项目让 Provider 只提取食物实体、数量、单位和餐次；客户端必须匹配受控食品目录，再由确定性函数换算营养。未知食物或单位无法换算时保持 unresolved，不生成最终数值。最后还需要用户明确确认，AI 不拥有正式写入权限。

### 10.26 Provider 抽象解决了什么问题？

页面和业务服务只依赖 `FoodTextProvider.extract` 的结构化契约，不依赖某家模型 SDK。测试和本地演示使用规则 Provider，后续可以增加真实模型实现；切换厂商时，Schema、确认 UI 和营养计算保持不变。抽象本身不会自动解决 Prompt 质量、超时和成本，所以这些仍要通过评测、重试策略和调用日志处理。

### 10.27 AI 一次识别多条食物时如何避免部分保存？

用户确认的是一个整体草稿。如果逐条开启事务，第二条失败时第一条已写入，会形成难以解释的部分成功。项目用 `addLogs` 在一个 SQLite 写事务里插入全部记录，并为每条记录追加 Outbox 事件；任一 SQL 失败就整体回滚。服务端同步仍依靠每条记录独立的 `client_id` 保证至少一次重试下的幂等。

### 10.28 为什么账号作用域检查要抛错，而不是默认查询公共数据？

账号未激活时继续查询会把生命周期 Bug 变成潜在的数据隔离 Bug。Repository 采用 fail closed，没有当前 `owner_user_id` 就抛错；页面只在认证状态为 `authenticated` 或 `offline` 后加载数据。浏览器验收曾发现登录重定向前 Tab 已短暂挂载的竞态，最终修复在页面生命周期层，而不是放松 Repository 的安全边界。

### 10.29 为什么结构化抽取默认选择 Luna，而不是始终选择最强模型？

模型选择应匹配任务和 SLO。当前任务是高频、低延迟的字段抽取，不需要复杂长链推理，因此默认使用适合抽取与严格延迟场景的 `gpt-5.6-luna`，并把模型名放进服务端环境配置。后续用固定评测集比较 Schema 合法率、实体准确率、延迟和成本；如果较小模型达不到阈值，再升级模型，而不是凭型号大小决策。

### 10.30 哪些模型错误应该重试，为什么不能全部重试？

超时、网络错误、408/409/429 和 5xx 可能是短暂故障，可以有限重试并短指数退避。鉴权等普通 4xx、空响应和 Schema 校验失败通常不会因立即重发而消失，盲目重试只会增加延迟、费用和下游压力。当前最多尝试两次，失败后规则降级；熔断仍是待办，不能把重试等同于熔断。

### 10.31 AI 成本统计如何避免“看起来很精确、其实是错的”？

每次调用保存输入/输出 Token，但单价由部署环境显式配置。未配置价格时成本保持空值并计入 `unpriced_calls`，不会硬编码可能过期的价格。当前估算还没覆盖价格版本、缓存 Token 和批处理折扣，所以它是开发期估算，不是账单对账系统；生产化需要记录计价版本并与供应商账单校验。

### 10.32 用户自己填写 API Key，为什么不能直接存在 SecureStore？

SecureStore 只提高设备静态存储的安全性，Key 在 App 运行、请求发送、调试和逆向分析时仍可能暴露；Web 端风险更高。项目让客户端只提交一次，后端加密保存并代理模型请求。这样客户端包里没有长期凭证，结构校验、重试、日志和限流也继续集中在服务端。

### 10.33 API Key 在数据库中如何保护？

后端使用 AES-GCM：随机 nonce 保证相同 Key 的密文不同，认证标签能检测篡改，AAD 绑定用户 ID 防止密文跨账号替换。加密主密钥来自环境配置，不与密文存放在同一数据库；接口永远不返回完整 Key，只返回末四位。生产还需要密钥管理服务、访问审计和轮换版本，当前实现是可解释的第一版凭证保险箱。

### 10.34 加密存储是否意味着服务器管理员也看不到 Key？

不是。后端必须在调用 OpenAI 时临时解密，所以持有主密钥和服务器执行权限的人仍在信任边界内。这是“加密存储”而不是端到端加密。它主要降低数据库备份泄露、误查询和密文篡改风险，不能替代 HTTPS、最小权限、日志脱敏与组织安全治理。

### 10.35 你如何设计 AI 饮食抽取评测集？

首版使用 26 条脱敏中文输入和 32 个 Ground Truth 实体，覆盖单/多实体、中文数量、单位换算、餐次提示、缺少数量、目录外食品、品牌饮品、否定、未来计划和无食物输入。样本刻意包含规则 Provider 的未知区域，避免只测成功样例。数据集有独立版本，报告绑定数据集、Provider、实际模型和 Prompt 版本，后续扩充而不静默改标签。

### 10.36 Precision、Recall、F1 和 Case Exact Match 各回答什么问题？

Precision 衡量模型返回的实体有多少是真的，Recall 衡量应识别的实体找回了多少，F1 平衡误报和漏报。Case Exact Match 更严格：一条输入的实体集合、数量、单位和餐次都必须正确。首版规则基线实体 F1 为 81.25%，但整例完全正确率只有 65.38%，说明一个局部错误就会导致整条草稿需要用户修改；两个指标不能互相替代。

### 10.37 为什么 Schema 合法率不能把网络超时也算进去？

网络超时表示没有拿到可评估输出，Schema 错误表示拿到了输出但不符合结构约束，根因和修复方式不同。项目用请求成功率衡量可用性；Schema 合法率只在成功结果与 Schema/空响应错误之间计算，网络错误记为不可评估。否则“网络变差”会被误诊成“Prompt 或 JSON Schema 变差”。

### 10.38 如何防止为提高评测分数而过拟合测试集？

固定回归集主要防止已知能力退化，不等于泛化能力证明。改 Prompt 时不能把每条测试答案逐字塞进去；应按错误类型设计通用指令，并保留未参与调试的 holdout 集。数据量扩大后还要从真实、获授权且脱敏的用户修改样本中分层采样，做双人标注和一致性检查，并分别报告开发集、回归集和线上反馈指标。

### 10.39 当前 81.25% F1 能否写成“AI 识别准确率 81.25%”？

不能省略上下文。它是 2026-07-19、26 条自建离线样本上规则降级 Provider 的实体 F1，不是 OpenAI 模型或生产用户准确率，也不是笼统的 Accuracy。简历可以写“建立 26 条/32 实体版本化评测集与回归门禁，规则降级基线实体 P/R/F1 均为 81.25%”，并补充真实模型指标待用 Key 采集。规则 Provider 的本地延迟和零 Token 也不能包装成模型性能与成本。

### 10.40 为什么使用 Tool Calling，而不是把用户记录全部塞进 Prompt？

全量塞入 Prompt 会重复传输、增加 Token 成本，也容易带入无关或过期数据。Tool Calling 让模型先判断需要哪类信息，再由后端执行固定查询；模型看到的是最小必要结果。权限、聚合和数值由确定性代码负责，模型只做意图选择与语言表达。用户记录是结构化强权限数据，因此这里也比向量 RAG 更适合用受控 SQL 工具。

### 10.41 如何防止模型查询到其他用户的数据？

工具 Schema 根本不提供 `user_id`。后端先从 Bearer JWT 得到当前用户，再把该 ID 通过闭包注入工具执行器；日志和资料 SQL 显式绑定它，食品查询只允许公共项或该用户私有项。即使模型伪造参数，也没有选择账号的入口。双用户集成测试用 520 和 999 kcal 的差异数据验证回答不串号，并验证私有食品不可见。

### 10.42 `strict: true` 是否已经保证工具安全？

没有。严格 Schema 只约束参数类型、必填字段和额外属性，不能判断调用者是否有权限、查询是否昂贵、结果是否包含隐私，也不能防止业务语义错误。项目仍在服务端使用 Pydantic 校验、工具白名单、用户隔离 SQL、只读能力和轮次上限。Schema 是输入契约，不是授权系统。

### 10.43 Responses Function Calling 的完整循环是什么？

第一轮模型返回带 `name`、JSON `arguments` 和 `call_id` 的 `function_call`。应用保留原始输出，校验并执行工具，然后把结果作为 `function_call_output`、使用相同 `call_id` 追加到下一次请求。模型获得结果后才生成最终文本。漏掉原始输出或 call ID 不一致都会破坏关联，所以 HTTP Mock 明确断言了第二轮请求体。

### 10.44 如何防止模型无限调用工具？

首轮设为 `required`，确保回答有真实数据；工具返回后的轮次改成 `auto`，允许模型结束。首版设置 `parallel_tool_calls=false`，每轮至多一个调用，总工具轮次上限为三。超过上限按 Provider 错误处理，再进入本地规则降级。生产化还可以增加单请求时间预算、每工具限流和熔断。

### 10.45 为什么周趋势要同时返回 0 值和记录天数？

为了固定图表和统计窗口，查询总是生成连续七个日期，缺失日补零；但零只表示“系统没有记录”，不能推断“没有进食”。因此结果同时返回 `days_with_records/7`，回答提示可能低估摄入，并明确平均值按完整七天计算。若要估计真实摄入，需要另外建立记录完整度模型，不能静默插值。

### 10.46 本地规则助手算不算假 AI？

它不是要冒充真实模型，而是明确标记的可靠性降级路径。它复用与 OpenAI 相同的只读工具执行器，保证无 Key、无网络或凭证失效时仍能给出基础数据摘要；响应中的 Provider、模型、零 Token 和 `fallback_used` 都如实展示。简历应写“规则降级”，不能把其延迟或结果包装成大模型指标。

### 10.47 为什么先做单轮助手，再升级多轮对话？

单轮阶段先验证授权、工具循环、证据和降级，减少一次引入的变量。确认事实查询边界后，再加入消息表、所有权、裁剪、删除和幂等。这样出现问题时可以区分是 Tool Calling 还是状态管理。当前已完成多轮持久化，但仍不把它描述为完整自主 Agent。

### 10.48 为什么自己保存会话，而不是只使用 `previous_response_id`？

产品需要会话列表、用户所有权、删除、规则降级和未来跨 Provider，这些都不应完全绑定供应商状态。项目将可见消息和证据保存在 PostgreSQL，请求仍设 `store: false` 并手动传入有限历史。代价是应用必须自己处理顺序、裁剪、隐私生命周期和并发，但控制边界更清晰。

### 10.49 如何设计对话表和消息表？

会话表保存 `user_id`、标题和时间；消息表保存角色、正文、顺序号、参考日期，以及助手消息的 Provider、模型、Prompt、Token、延迟、降级、证据和 trace ID。`conversation_id + sequence` 唯一保证顺序，`conversation_id + client_message_id` 唯一支持重试。读取会话时同时绑定当前 JWT 用户，越权统一返回 404。

### 10.50 为什么历史上下文只取最近四轮？

全量历史会让 Token、延迟和费用随对话长度无限增长，还会增加过期事实和 Prompt Injection 的暴露面。首版取最近 8 条消息、最多 6,000 字符，并保证从用户消息开始。这个数字是可解释的工程上限，不是模型最优值；真实评测后可升级为 Token 预算、历史摘要加最近消息。

### 10.51 如何避免复用历史中的过期营养数据？

历史只用于理解代词和省略表达。Prompt v1.1.0 明确禁止沿用历史摄入、趋势、目标和食品数值，首轮又使用 `tool_choice=required`，因此每次回答都重新读取当前数据库。持久化的旧证据用于展示当时回答依据，不作为本轮事实缓存。

### 10.52 消息发送为什么需要幂等键？

移动网络可能在服务端完成后、响应到达前断开。客户端若换一个请求 ID 重试，会重复调用并保存两轮。页面保留同一会话、问题和 `client_message_id`，服务端查到已完成消息就返回原结果；同键不同内容返回 409。进程重启会丢失当前内存待发送键，这是后续可通过本地持久化改善的边界。

### 10.53 数据库唯一约束能否保证模型只调用一次？

不能。它能保证并发请求最终只保存一组消息，但两个实例可能同时通过预检查并都调用模型，之后才在唯一约束处竞争。因此当前是消息写入幂等，不是外部模型调用恰好一次。生产化可用 Redis single-flight、持久化 processing 状态、租约和过期恢复减少重复调用。

### 10.54 `store: false` 是否意味着对话数据没有发送给 OpenAI？

不是。它表示应用不要求 OpenAI 保存该响应状态，但请求中的裁剪历史和工具结果仍会发送给模型服务。项目自管数据库也会保存完整可见对话。因此需要 HTTPS、按用户鉴权、数据库保护、删除和保留策略，并在产品隐私说明中区分“发送处理”“供应商存储”和“应用自身存储”。

### 10.55 为什么周报不用模型直接读取原始日志并计算？

模型适合解释和表达，不适合承担需要稳定复现的聚合与权限逻辑。项目先在 SQL/Python 中按 JWT 用户计算双周事实，再让模型只生成叙事。这样同一事实输入的数字固定，双用户隔离可以用集成测试证明，模型输出错误也不会改写前端展示的核心数值。

### 10.56 `strict: true` 能否保证周报内容正确？

不能。严格 Structured Outputs 主要保证返回符合 JSON Schema，例如标题是字符串、要点不超过三条；它不能证明“1800 kcal”来自数据库，也不能判断医疗建议是否合理。因此营养数字不让模型生成，后端还要做用户隔离、确定性计算、Pydantic 二次校验、Prompt 约束和免责声明。

### 10.57 为什么周平均固定除以 7？

为了让不同周保持相同时间口径。若一周记录三天、另一周记录七天，却分别除以 3 和 7，结果会混入记录习惯变化。固定除以 7 会在缺失时低估，所以接口必须同时返回 `days_with_records`，低完整度时警告，并在两周任一周少于四天时关闭环比。它是透明的统计口径，不是对真实摄入的插值。

### 10.58 上周为 0 时为什么环比返回 `null`？

百分比变化以旧值为分母，旧值为零时没有有限定义。在饮食记录场景，0 更可能代表没有记录，而非没有进食。返回 `null` 并显示“记录不足”比制造 100%、无穷大或任意上限更诚实，前端类型也强制处理这个状态。

### 10.59 周报事实指纹解决什么问题？

后端把规范化、排序后的事实 JSON 做 SHA-256。相同指纹表示报告基于相同的事实输入，便于定位“文字变化来自模型随机性还是数据变化”。它不可逆地摘要输入，不保存原始报告，也不能证明谁在何时看过内容，因此不能替代报告快照、签名、调用日志或审计系统。

### 10.60 为什么周报选择固定管线而不是 Tool Calling？

周报每次都需要同一组双周事实，查询步骤没有开放式决策价值。固定管线少一次或多次模型往返，Token 和延迟更低，结构更容易回归测试。问答助手面对不同意图才使用 Tool Calling。选择 Agent 工作流应看任务是否需要动态规划，不是为了堆技术名词。

### 10.61 结构化日志比普通字符串日志多解决了什么？

结构化日志把事件、请求 ID、端点、状态和耗时变成稳定字段，日志平台可以按字段检索、聚合和告警，不需要依赖脆弱的正则解析。它本身不保证安全，所以项目只允许白名单字段，不把整个请求对象或任意 `extra` 序列化。

### 10.62 为什么允许客户端传 `X-Request-ID`，又必须校验？

允许传入可以把客户端、网关和服务端串成一条排障链路；但 Header 属于不可信输入，换行可能伪造日志，超长值会放大存储。项目只接受 8~128 位字母、数字、点、下划线和连字符，其余情况生成服务端随机 ID，并在响应头回传最终值。

### 10.63 为什么不记录请求正文，排障信息不会不够吗？

正文包含饮食内容、健康资料、密码或 API Key，通用日志通常复制范围更广、保留更久。项目优先记录端点、状态、耗时和 request ID；需要业务细节时，通过鉴权后的数据库和独立 AI trace 查询。生产中可以针对极少数脱敏事件增加专用审计字段，但不能默认复制完整正文。

### 10.64 自定义 JSON Formatter 已经不记录 Query，为什么还会泄漏？

同一进程可能有多套 Logger。Docker 验收发现 Uvicorn 默认 access log仍会打印原始 URL 和 Query，自定义 Formatter 管不到它。最终关闭 `uvicorn.access`，用应用自己的端点级结构化日志替代。安全检查必须覆盖最终容器输出，不能只看一段代码。

### 10.65 `send_default_pii=false` 是否足以保证 Sentry 没有敏感数据？

不足。它会阻止集成默认添加部分 PII，但异常消息、自定义上下文或请求 URL 仍可能包含业务数据。项目还关闭本地变量和请求正文，并在 `before_send` 删除用户、URL、Header、Cookie、Query、Body 和环境。新增 Sentry 上下文仍要评审和测试。

### 10.66 request ID、AI trace ID 和分布式 trace ID 有什么区别？

request ID 标识一次 HTTP 请求，用于客户端和服务端日志关联；AI trace ID 是项目数据库中的一次模型调用记录；分布式 trace ID 则跨服务和 Span 描述完整调用树。当前单体先实现 request ID，Sentry 可采样性能事务，但尚未建立跨服务 OpenTelemetry Trace，不能混用这些概念。

### 10.67 Sentry 的性能采样率为什么默认是 0？

错误事件和性能事务的成本、隐私与流量不同。项目在没有真实流量基线和用户告知前不自动采集性能，部署者显式配置 `sentry_traces_sample_rate` 后才采样。生产不能为了“数据越多越好”直接设 100%，应按问题、预算和保留策略调整。

### 10.68 为什么健康检查告警应从应用外部发起？

如果进程已经崩溃、网络被切断或整台主机不可达，应用内部代码无法发出“我挂了”的告警。`/live` 和 `/ready` 提供被探测信号，部署平台或外部监控负责周期访问和告警。Sentry更适合应用异常，不能替代外部可用性监控。

### 10.69 为什么演示账号需要数据库字段，不能只约定固定邮箱？

邮箱只是可修改的业务标识，命名约定无法证明账号可以被删除。`is_demo` 是数据库中的显式安全属性；种子服务只有在它为真且调用方显式要求重置时才删除数据，普通账号即使碰巧使用演示邮箱也会被拒绝。公开环境还应把执行权限限制在运维身份，字段本身不是授权机制。

### 10.70 `flush` 与 `commit` 有什么区别，为什么种子脚本需要提前 `flush`？

`flush` 把当前事务内的 SQL 发送给数据库，使约束和生成值生效，但事务仍可回滚；`commit` 才让事务永久生效。项目模型只有显式外键 ID、没有 ORM relationship，SQLAlchemy 首次无法推断用户和食品的插入顺序。先 flush 父用户可满足外键，后续 58 条日志或同步事件失败时仍会整体回滚，不会留下半套演示数据。

### 10.71 为什么重置演示账号要创建新的用户 ID？

Access JWT 是无状态的，数据库中没有逐个 Access Token 可删除记录。如果沿用用户 ID，重置前签发且尚未过期的 JWT 仍能访问新数据。轮换用户 ID 后，旧 JWT 的 subject 查不到用户；同时显式删除 Refresh Token，使旧刷新令牌也返回 401。代价是所有用户外键数据必须完整重建。

### 10.72 为什么日志 ID 要稳定，而用户 ID 要随机？

种子日志和食品使用由版本、邮箱、锚点日期与序号生成的 UUID5，目标是同一输入可复现、容易排查重复。用户 ID 使用 UUID4，目标是每次重置撤销旧会话。ID 策略取决于资源的业务语义，不应为了“统一”而统一。

### 10.73 为什么共享演示账号不能配置 API Key？

共享密码意味着任何访客都可能读取状态或触发调用。即使接口不回传完整 Key，访客仍可能覆盖别人的 Key 或消耗服务端额度。因此演示账号的凭证读接口固定返回未配置，写删返回 403，Provider 选择也忽略服务端付费 Key，固定走本地规则。客户端禁用输入只是体验层，安全边界必须在后端。

### 10.74 单元测试已经通过，为什么还会出现 PostgreSQL 外键错误？

默认快速测试使用 SQLite，外键强制和 SQLAlchemy flush 行为没有完全复现 PostgreSQL。真实容器第一次执行种子时，食品先于用户插入，被 PostgreSQL 外键拒绝。这说明测试金字塔需要不同层次：SQLite 提供快速业务回归，PostgreSQL 验证真实方言、约束和并发，不能用其中一层替代全部。

### 10.75 当前演示账号能否直接称为生产级公开 Demo？

还不能。当前已增加可重置数据、令牌失效、AI 费用隔离、Redis 限流、资源配额、多实例锁、关闭注册、认证访客桶和生产预检；但共享访客仍会修改同一数据，配额不是严格并发上限，周期任务也尚未在公网多副本长期运行。还需要真实 HTTPS 部署、平台代理网段验证、Redis/重置告警、WAF 或每访客隔离沙箱。

### 10.76 为什么日志同步成功，首页仍可能没有个性化目标？

日志通过 `sync_changes` 游标拉取，但用户资料不在这张变更表里。浏览器验收首次出现 58 条演示日志，却仍使用 2000 kcal 默认值，说明“业务数据同步”不是一个抽象开关，每种聚合都要定义契约。项目新增独立资料同步：本地为空时拉云端，云端为空或本地时间较新时推本地，并在完成后触发首页刷新。当前整对象时间戳 Last-Write-Wins 可能受时钟漂移影响，生产多设备应升级为服务端版本或冲突 UI。

### 10.77 为什么 Redis 限流要用 Lua，而不是先 `INCR` 再 `EXPIRE`？

两条独立命令之间进程可能崩溃，留下没有 TTL 的永久计数键；并发实例也可能重复初始化窗口。Lua 在 Redis 单线程执行上下文中原子完成递增、首次设置 TTL 和读取剩余 TTL，API 再用它生成 `Retry-After`。它解决操作原子性，不代表 Redis 自身高可用已经解决。

### 10.78 为什么演示限流按账号而不是按 IP？

共享账号总量桶直接限制数据库和 CPU 消耗，键只含用户 UUID，保证所有访客合计不能无限写入。认证入口已另外使用可信代理访客桶，阻止轮换邮箱；但登录后的 Demo 写入仍共享账号桶。若按访客分配写入额度，需要把服务端解析的访客标识绑定到会话，不能从客户端 Header 直接接受身份。

### 10.79 生产为什么必须 fail-closed，开发却允许 fail-open？

本地开发可能只启动 API 和 SQLite，Redis 故障不应阻断所有调试；公开 Demo 的密码已知，保护层失效后继续放行会让资源无限消耗。因此开发记录错误后放行，生产配置校验强制 fail-closed，受保护操作返回 503。普通账号和只读接口不使用该桶，避免 Redis 故障扩大成全站不可用。

### 10.80 Redis 分布式锁为什么既要 TTL 又要所有权 Token？

TTL 让持锁实例崩溃后锁能自动释放；Token 防止旧实例删除别人的新锁。实例 A 的锁可能过期，B 随后获得同名锁，如果 A 完成后直接 `DEL` 就会删掉 B 的锁。释放 Lua 只有在当前值仍等于 A 的随机 Token 时才删除。任务超过 TTL 仍可能并发执行，长任务还需要续租或更长的可测 TTL。

### 10.81 为什么资源配额不是严格并发硬上限？

当前流程先 `COUNT` 再执行原领域写事务，两个请求可能同时看到最后一个空位并都写入。它适合结合限流和周期重置做滥用缓解，但不能当计费或强一致配额。严格实现可按用户获取 PostgreSQL advisory transaction lock，或用 Redis Lua 原子预留名额并在数据库失败时补偿。

### 10.82 为什么幂等重放必须先于配额检查？

移动端可能在服务端成功后没有收到响应，用相同 `client_id` 重试。如果账号刚好达到日志上限，先检查配额会把本应返回原记录的安全重试拒绝掉，破坏离线同步契约。因此先识别同键同内容的已有资源，只对真正的新创建消耗容量；同键异内容仍返回 409。

### 10.83 自动重置为什么启动后先等待一个周期？

如果每个实例启动就立刻重置，滚动发布、扩容或崩溃重启都会轮换用户 ID，正在演示的人会频繁掉线。先等待完整周期让“部署事件”和“产品恢复节奏”解耦。需要发布前立即恢复时，运维使用带同一分布式锁的一次性 CLI。

### 10.84 已有限流后，为什么公开注册仍是风险？

最初的桶只保护 `is_demo=true` 的共享账号，攻击者可以注册普通账号绕过。项目后来增加后端注册开关、账号标识桶和可信访客桶；作品集预检要求关闭注册。这个演进说明局部资源保护不等于全站入口风控，仍需真实平台 WAF、验证码或邀请制。

### 10.85 为什么关闭注册还要让前端请求运行配置？

后端 403 才是安全边界，前端配置用于避免展示一个注定失败的入口。同一 Web 构建可以部署到“本地开放注册”和“作品集关闭注册”两种环境，无需重新打包。配置请求失败时客户端默认隐藏注册，但攻击者即使伪造 UI 仍会被后端拒绝。

### 10.86 为什么认证限流按邮箱，而不是直接按 IP？

邮箱桶限制多个来源集中爆破一个账号；访客桶限制单一来源轮换邮箱，两者解决不同维度。项目先实现邮箱桶，再在可信代理解析完成后叠加访客桶。仍需要网关全局桶或验证码处理轮换大量 IP 的分布式低频攻击。

### 10.87 为什么 Redis 键使用 HMAC，而不是 SHA-256？

邮箱空间可枚举，普通哈希泄漏后可以用常见邮箱字典反查。HMAC-SHA256 需要服务器密钥，Redis 泄漏本身不足以验证猜测。项目还把版本和 login/register 动作放进消息做域隔离。它是可关联的假名化标识，不是匿名化；应用仍应限制 Redis 访问和保留时间。

### 10.88 为什么登录和注册使用不同限流桶？

两者成本、阈值和恢复语义不同。登录成功应清除失败计数，而注册成功或邮箱冲突仍会消耗哈希/数据库资源；共用桶会让注册流量误伤登录，也无法分别调参。动作进入 HMAC 消息和 Redis 键空间，防止相互污染。

### 10.89 成功登录为什么清空计数，是否会被攻击者利用？

成功登录说明调用方已经持有正确凭证，继续保留历史输错会误伤正常用户。攻击者只有知道正确密码才能触发清桶，此时限流已经不是阻止账号接管的主要边界。高风险系统仍可保留独立失败审计和异常设备检测，项目当前只清短期 Redis 阻断桶，不删除安全日志。

### 10.90 未知邮箱和已知邮箱的限流行为为什么必须一致？

如果未知邮箱不计数、返回不同错误或不同 Header，攻击者可以据此枚举账号。项目在业务查询前对所有合法邮箱进入同一算法，凭证失败统一返回“invalid email or password”；不存在用户时仍验证固定 Argon2 假哈希，使主要计算路径接近。它减少显式泄漏和明显时序差异，但不能证明网络层完全没有可统计侧信道。

### 10.91 Redis 故障时为什么只阻断登录注册，不阻断 Refresh Token？

限流保护的是公开凭证入口。已有用户持有高熵 Refresh Token，刷新还受数据库轮换和重放检测保护；让它继续工作可缩小 Redis 故障半径。生产启用认证保护时，登录注册 fail-closed 返回 503；业务 Access Token 鉴权和刷新不依赖认证桶。

### 10.92 这套实现能否称为完整防暴力破解？

不能。它完成账号与可信访客双层固定窗口、关闭注册和隐私化键，可缓解集中爆破、邮箱轮换与作品集账号绕过。它不能阻止轮换大量 IP/邮箱的分布式低频攻击，也没有验证码、设备信誉或 WAF。简历必须准确描述已实现层次和未覆盖边界。

### 10.93 为什么成功后的 Redis 清桶故障不能继续 fail-closed？

入口限流发生在密码验证前，Redis 故障时返回 503 可以阻止绕过保护。但登录服务随后会把 Refresh Token 提交到 PostgreSQL；如果成功后的 `DEL` 失败又抛 503，客户端收不到 Token，数据库却留下有效会话。项目因此把清桶视为尽力清理：记录结构化告警但返回已完成的登录。入口和收尾阶段的故障策略不能机械复用。

### 10.94 为什么 `X-Forwarded-For` 要从右向左解析？

最右侧最接近应用，由受控代理追加，可信度最高。应用从 TCP 对端开始向左剥离已配置的代理地址，遇到第一个不可信地址即作为客户端。直接取最左侧会接受攻击者预先放入的伪造值。算法成立的前提仍是最后一跳代理网段配置正确。

### 10.95 为什么关闭 Uvicorn 的自动 Proxy Headers？

应用必须先知道原始 TCP 对端，才能判断它是否有权提供转发 Header。如果 Uvicorn 提前根据 `X-Forwarded-For` 改写 `scope.client`，应用就失去最后一跳证据。项目使用 `--no-proxy-headers`，在自己的受测逻辑中验证对端和解析链。

### 10.96 可信代理 CIDR 配错会怎样？

漏配时应用忽略转发 Header，所有用户可能聚合到代理地址，造成误限流但不接受伪造值；配得过宽则攻击者可能被当作代理并伪造客户端地址，属于安全失败。配置模型明确拒绝 `0.0.0.0/0` 和 `::/0`，生产预检要求代理模式至少配置一个 CIDR，但真实网段仍必须查托管平台文档。

### 10.97 为什么 IP 不能当作用户身份？

公司、校园和 CGNAT 后的多人可能共享 IP，移动网络与 IPv6 隐私地址又会频繁变化。IP 适合作为短期滥用信号，不适合授权、永久封禁或用户唯一标识。因此项目把访客桶和账号桶叠加，并使用短 TTL。

### 10.98 为什么成功登录不清访客桶？

成功凭证只证明账号密码正确，不代表来源可以无限调用。如果清访客桶，掌握任意一个有效账号的人可以在每次成功登录后重置网络预算，再轮换其他邮箱。项目只清账号登录桶以减少正常用户误伤，访客桶持续到窗口到期。

### 10.99 为什么限流 HMAC 要使用独立 Secret？

JWT 签名和限流假名化是不同职责。共用密钥会让 JWT 轮换导致 Redis 桶不可寻址，也扩大单个密钥泄漏的影响。项目把邮箱和 IP 摘要迁移到独立 `RATE_LIMIT_HMAC_SECRET`，并在生产拒绝开发默认值；三个生产 Secret 都由部署平台分别注入。

### 10.100 Host 白名单、CORS 和鉴权有什么区别？

Host 白名单防止异常 Host 路由和部分 Host Header 攻击；CORS 限制浏览器脚本跨源读取响应；JWT 鉴权决定调用者是否能访问用户资源。三者作用层不同，CORS 不能阻止 curl，Host 白名单也不能证明用户身份。

### 10.101 非 root 容器解决了什么，没解决什么？

它降低应用进程被利用后直接拥有容器 root 权限的风险，也让不必要的写权限更容易暴露。但容器 root 不等于宿主 root，非 root 也不能替代镜像修复、只读文件系统、能力删除、网络策略和资源限制。项目用真实 `id` 和 CI 断言验证，而不是只看 Dockerfile。

### 10.102 生产预检为什么不能替代 Readiness？

预检检查环境、安全开关、URL Scheme、Host、CORS 和代理配置是否自洽，不连接外部服务。`/ready` 在运行时实际查询 PostgreSQL；Redis 还需要独立监控。静态正确、依赖可达和公网可用是三个不同层次。

### 10.103 为什么 API 容器不直接配置 HTTPS 证书？

托管平台通常在负载均衡器集中处理证书续期、TLS 版本、HSTS、HTTP 跳转和边缘防护，应用容器只在私网接收流量。这样职责更清晰，但必须正确配置可信代理和外部 HTTPS URL。当前已选择 Render 免费演示拓扑并完成发布包，尚未创建真实公网资源，因此仍不能声称已完成 HTTPS 部署。

### 10.104 为什么部署时把 Expo Web 和 FastAPI 放进同一个镜像，不算架构倒退？

部署单元和代码边界不是一回事。前端仍是 React Native/Expo，后端仍是 FastAPI API 和独立数据库；同源镜像只是在免费作品集阶段减少 URL、CORS、安全头和计算实例的部署耦合。若流量证明需要 CDN 或独立发布，可以在不改领域 API 的情况下拆分。

### 10.105 为什么 SPA fallback 只处理无扩展名路径？

`/auth`、`/profile` 这类浏览器路由需要返回 `index.html`，但缺失的 `.js`、`.wasm` 或 API 必须是真实 404。如果错误地把所有 404 都返回 HTML，浏览器会把 HTML 当脚本/WASM 解析，既难定位又可能让健康探测产生假阳性。

### 10.106 同源以后 CORS 是否完全没用了？

浏览器 Web 版同源调用不需要 CORS，但 Native 客户端不受浏览器 CORS 限制，鉴权仍靠 JWT。将来拆分静态域名、增加管理后台或开放第三方 Web Client 时，需要重新配置明确 Origin。CORS 从来不是服务端授权机制。

### 10.107 为什么免费 Render 不使用 pre-deploy migration？

Render 官方把 pre-deploy command 限定在付费 Web Service。免费演示把预检、Alembic 和种子重置放进启动门禁，任一步失败都不会启动 Uvicorn。它适合作品集验证，但不如独立 release phase；有稳定预算后应把 migration 拆出并保留向后兼容策略。

### 10.108 应用回滚能否自动回滚数据库迁移？

不能。新实例可能已经对共享 PostgreSQL 执行 DDL，平台回滚只恢复旧镜像和配置。项目必须使用 expand/contract：先增加旧代码兼容的新结构，部署读写兼容代码，最后再删除旧结构。危险的破坏性迁移需要备份、单独窗口和明确恢复方案。

### 10.109 为什么自动把 `postgresql://` 改成 `postgresql+psycopg://`？

Render 提供标准 PostgreSQL URL，而 SQLAlchemy 异步引擎需要明确选择异步 psycopg 方言。把适配集中在 Settings 层，可让平台连接串直接注入，避免在 Blueprint 中拼接 Secret；单测固定了只替换精确前缀的契约。

### 10.110 免费 Redis 重启丢数据会不会破坏系统？

免费 Key Value 只承载短期限流桶和演示重置锁，主数据、用户、Refresh Token 和饮食记录在 PostgreSQL。Redis 丢失会短暂清空滥用预算，并可能让一个过期重置锁消失，但不会丢主数据；这也是为什么它不能被描述为强一致配额或永久审计。

### 10.111 为什么没有在 Render 上直接相信 `X-Forwarded-For`？

项目需要最后一跳代理 CIDR或平台明确的不可伪造 Header 契约。当前官方资料没有给出可直接配置的入站 CIDR，因此首版忽略 Header，让访客桶聚合到平台代理地址。它可能误限流或被共享桶 DoS，但攻击者不能用伪造地址绕过，优于猜测网段。

### 10.112 多阶段 Docker 构建如何缩小运行攻击面？

Node、npm、Metro 和 1332 个构建依赖只存在于第一阶段；最终镜像只复制静态 `dist`、Python 锁定运行依赖、应用和迁移。运行层没有 Node 工具链，并以 UID 999 启动。构建依赖告警仍需管理，但不能把它们和运行镜像漏洞混为一谈。

### 10.113 浏览器登录后为什么先看到默认目标，随后才出现演示数据？

登录接口先建立会话，客户端随后把云端资料和日志同步进账号隔离的本地 SQLite。首次渲染发生在同步完成前，所以短暂显示本地默认值。约两秒后真实种子数据出现。改进方案是让认证状态机增加 `initial_sync` 状态或骨架屏，而不是把默认值伪装成已同步数据。

### 10.114 为什么 Render 内置环境变量不能直接用 `fromService.envVarKey`？

Blueprint 解析发生在资源配置阶段，`fromService` 只能引用 Blueprint 可解析的服务属性或用户环境变量；`RENDER_EXTERNAL_HOSTNAME` 和 `RENDER_GIT_COMMIT` 是平台在运行阶段注入容器的内置变量，不在该引用集合中。第一次真实同步因此在环境变量步骤失败。项目删除了两个无效自引用，由 Settings 在没有显式 `NUTRIPILOT_*` 配置时读取 Render 内置值，并以单测固定优先级。这样没有控制台漂移，也把平台耦合限制在配置层。

## 工程质量

### 11. TypeScript 类型检查、Lint 和测试有什么区别？

- 类型检查发现类型不一致。
- Lint 发现代码规范、潜在错误和坏味道。
- 测试验证特定输入下的行为是否符合业务预期。

三者互相补充，任何一个都不能替代另外两个。

### 12. 你在项目中最困难的问题是什么？

该问题必须在开发过程中用真实案例补充。推荐从离线同步冲突、AI 结构化输出稳定性、食品实体匹配或端到端延迟优化中选择，不能虚构尚未发生的问题。
