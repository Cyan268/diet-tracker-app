# ADR-010：AI 草稿使用唯一云端确认路径

- 状态：Accepted for implementation（设计已确定；持久草稿/确认尚未实现）。
- 日期：2026-08-31；任务：U0-02；实施：U2-01～04；可选扩展：U2-05。
- 依据：[升级计划](../UPGRADE_DEVELOPMENT_PLAN.md)、[风险 R04/R05/R08/R12](../upgrade/RISKS.md)。
- 前置：[事务边界](ADR-011-log-unit-of-work.md)、[身份映射](ADR-012-food-and-log-identity.md)、[Worker](ADR-013-durable-analysis-jobs.md)、U4-01 正确性验收。

## 背景

当前 `app/ai-add.tsx` 通过页面内状态保存分析结果，确认后调用 `addLogs`，生成本地日志及普通 create Outbox。若新云端确认成功后仍调用此函数，同一食品会沿两条路径保存。刷新还会丢失页面内幂等状态，无法区分“服务器没成功”和“成功但响应丢失”。

目标是让文本和图片共享“分析 → 持久草稿 → 人工审阅 → 一次正式保存”，并保留普通手工记录的离线能力。

## 决策

### 唯一正式保存入口

```text
普通手工记录 → SQLite 日志 + create Outbox → 现有日志 API

AI 文本/图片 → 持久 Job → Draft → 在线 confirm
  → 一次服务端事务（日志 + 同步事件 + 确认映射 + 纠错）
  → SQLite 远端应用事务（不生成 create Outbox、不推进增量游标）
```

1. 新 AI UI 只用 `POST /api/v1/ai/drafts/{id}/confirm` 正式保存，不能再调用 `addLogs`。Job 成功仅代表生成草稿，草稿存在不代表饮食已入账。
2. 输入包括 `client_confirmation_id`、`expected_draft_version`、最终实体及明确业务日期/餐次。请求规范化后计算版本化 hash；食品修订、实体 ID、数量/单位、用户编辑字段均纳入，同一 owner 下校验。实体按稳定 ID 规范排序，不以界面排列决定语义。
3. 唯一约束 `(user_id, client_confirmation_id)` 和 `draft_id`；后者保证不同键也只能成功一次。先查已提交确认：同键同 hash 返回原确认快照/映射；同键不同 hash 为 409。重放检查先于草稿过期/版本检查，因此成功后过期或版本改变不妨碍找回结果。
4. 新确认锁定草稿，校验 owner、状态、期限、版本、食品权限与单位，再确定性计算营养快照，一次提交整批记录和纠错。不同键确认已确认草稿返回明确 409，允许本人按返回的确认引用找回；跨用户查询统一 404，不泄漏资源存在性。
5. 已确认后日志可能编辑或删除；重复确认返回当时的确认快照而不是重算后的现状。确认/去重标记不能随原文到期清理；本人账号删除时一起删除。若未来压缩响应历史，仍须保留不可再次确认的标记并定义恢复接口。
6. 模型只提供候选、数量和待审阅提示。营养来自有权访问的目录修订，或用户明确输入且通过单位/范围校验的自定义值；未知营养不是 0，不允许把模型猜测当权威数值保存。目录修订缺失/撤销时返回明确冲突要求重审，不能静默换用新版本。

### 客户端恢复与离线边界

1. 发送前用 SQLite 事务持久化 owner、会话代次、草稿/版本、确认键和规范请求；标记为 `pending_send`。首次尝试后 key/payload 不可变。它是确认恢复记录，不是普通日志 Outbox。
2. UI 状态区分：草稿缓存、确认中、结果未知、已确认到云端/本地待刷新、完成、冲突/过期。超时或刷新后继续用同一键/内容查询或重试；按钮防抖只是体验，不是幂等保障。
3. 断网可查看缓存草稿、保留未提交编辑；U2-04 不支持离线正式确认。不将 AI 确认请求同时转为本地正式日志，也不在结果未知时提供“一键转手工”另存。新分析需求另建 Job，不能重用旧确认键修改内容。
4. 确认结果经统一远端应用事务对齐 `server_id/client_id`，不创建普通 create 事件。应用前检查原 owner/会话 epoch，不将 A 结果写到 B。账号切换时保留 A 的恢复信息，下次 A 登录后继续。
5. 原确认快照可能比已经拉到的编辑/删除更旧：按单条远端身份保存的版本/删除标记阻止回退，删除同版本时 tombstone 优先。若本地重建后缺少足够顺序依据，只保存确认映射并触发增量/快照刷新，不能盲目复活旧记录。
6. 同步全局进度只能在完整拉取页的应用事务中推进，确认响应的任何单条序号都不能直接成为拉取游标。确认落库失败时保留“云端已确认/本地待刷新”，不能再建新确认。

### 纠错口径

保存分析原始实体基线与最终实体的差异：未改动确认也有 Confirmation；新增/删除实体单独计数，字段修改按同一实体 ID 对比。分母记录确认次数、原始/最终实体数、修改实体数与字段数。指标不复制完整输入文本、图片 URL 或 Key；正式日志 note 不自动写入完整原文。

## 不选方案

- 云端 confirm 后再 `addLogs`：形成两条创建链路，前端去重外观不能修复服务端重复统计。
- 只禁用按钮、只在内存保存 UUID：不能覆盖刷新、崩溃、双设备和响应丢失。
- 首版同时支持离线 AI 确认：涉及暂存日志、单个 confirm Outbox、过期/未知恢复，超出核心在线闭环。
- 每次重试重新读目录/重算日志：同一操作会随目录和当前日志变动而改变语义。

## 代价

AI 正式确认需要网络；需要额外确认恢复记录、服务端幂等存储和明确状态 UI。用户在未知结果时需要等待恢复而不能随意另存，这是防重复的可见代价。纠错记录增加隐私与保留期限管理，不把修改率当模型准确率。

## 兼容策略

旧同步文本分析端点和旧日志 API 在兼容窗口保持可用，已生成的普通 Outbox 仍按原路径处理；新页面每个草稿只能选择一种保存模式。202 新接口必须等 U3-01 消费者可运行后开放。U2-05 单独设计/验收稳定实体 client_id 和 `confirm_draft` Outbox，启用前不能宣传离线 AI 保存。新数据表用增量迁移，不回写旧日志“伪造来源”。
