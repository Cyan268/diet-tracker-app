# ADR-009：单 VPS、独立 Worker 与显式发布边界

- 状态：部分实现（U1-01 本地生产包已完整验收；Worker、正式镜像发布/回滚、公网 HTTPS 与备份恢复仍未实现）。
- 日期：2026-08-31；任务：U0-02；实施：U1-01～03、U3-01。
- 依据：[升级计划](../UPGRADE_DEVELOPMENT_PLAN.md)、[基线](../upgrade/BASELINE.md) R06/R10/R11 对应的[风险登记](../upgrade/RISKS.md)。
- 关系：保留 ADR-008 的同源镜像思路；只在新 VPS 路径替代其“启动即迁移/重置”决定，不改旧 Render 配置。

## 背景

实施与限制见 [U1-01 任务记录](../upgrade/tasks/U1-01.md)。新镜像与 Caddy 已完成隔离本地验收；本轮不修改旧 Render 运行环境，也不把本地结果写成公网已部署。

用户已经租好服务器，但规格、系统、域名、SSH 授权、旧数据迁移和对象存储尚未确认。当前 `Dockerfile.production` 每次启动都迁移并重置 Demo；`compose.yaml` 是发布 API/数据库/Redis 端口的开发拓扑，不能直接作为生产包。现有 AI 仍是同步调用，没有持久化任务消费者。

目标是在可解释、可维护的成本下完成作品集闭环，不为“用了更多组件”拆微服务，也不把一台机器包装成高可用系统。

## 决策

### 进程、网络与入口

```text
公网浏览器 / App
  → Caddy（唯一业务公网端口 80/443，TLS）
    → API + Expo Web（同源镜像，内部 8000）
      → PostgreSQL（业务事实与持久任务）
      → Redis（限流与演示协调，不充当任务事实源）

Worker（同镜像/同版本、不同命令）→ PostgreSQL → 模型 / 私有对象存储
备份任务 → 加密备份 → VPS 之外的独立存储
```

1. 首版单 API 进程、单 Worker 进程，模型调用并发默认 1。资源基线暂用计划的 2 核 4GB 假设，连接池/限额依据实际服务器再测量，不作为容量承诺。构建在本地/CI，服务器只拉取指定 digest。
2. `deploy/compose.prod.yml` 独立于开发 Compose 和 Render。API 与 Worker 复用业务模块、数据库和镜像，不通过新增内部 HTTP 微服务通信。U1 只预留 Worker profile/命令契约；U3-01 实现入口后才启用，不能启动空壳消费者或开放无人消费的 202 API。
3. 代理网络仅连接 Caddy/API；数据网络连接 API/Worker/PostgreSQL/Redis。数据网络不发布宿主端口；API/Worker 另具受控出网能力，以免 `internal` 网络阻断模型调用。SSH 属于管理入口，只向已确认的管理来源开放，不算业务公网端口。
4. Caddy 是当前设计的第一跳代理，忽略客户端伪造的转发链并生成实际链。API 保留 `--no-proxy-headers`，现有应用解析器只信任 Caddy 明确地址（IPv4 `/32` 或 IPv6 `/128`）。U1 选取不冲突的容器网段/固定代理地址，预检拒绝“信任全部私网”。若增加 CDN/LB，必须另验信任链，不能直接沿用配置。
5. 保留 Host 白名单、最小 CORS、请求体限制、COOP/COEP、WASM MIME、SPA fallback 和缺失资源 404。对象存储直传使用单独受限 CORS；私有签名访问必须实测与跨源隔离的兼容性。

Docker 发布端口默认可能对外可达；不依赖“有防火墙所以映射 DB 也没事”。Caddy 默认忽略外部传入的 `X-Forwarded-*` 值以防伪造，新增上游可信代理会改变这一边界。[Docker 端口文档](https://docs.docker.com/engine/network/port-publishing/)、[Caddy 反向代理文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

### 发布、数据与故障域

1. 新路径启动只做预检和启动本进程；迁移、初始化种子、Demo 重置是互斥发布流程中的显式命令。重启 API/Worker 不删数据、不轮换账号、不运行迁移。发布次序：预检 → 拉取 → 必要备份 → 一次迁移 → 更新 → 就绪 → 冒烟。
2. Secret 通过服务器受限权限文件/挂载注入；不进入镜像、示例配置、日志或 Git。限制容器日志大小，持久化数据库、Redis 所需状态与 Caddy 证书，分别设置健康检查；API 存活不代表 Worker 可消费。
3. 首版允许维护窗口。应用回滚到已记录 SHA/digest，Schema 使用 expand/contract；不自动 `downgrade`。不兼容同步锁协议的旧镜像不在可回滚集合内，见 [ADR-014](ADR-014-ordered-sync-and-snapshots.md)。
4. 业务数据以 PostgreSQL 为准，Redis 故障按现有保护策略处理，不能静默绕过生产限流。图片采用私有 S3 兼容接口；优先复用用户已有服务，具体供应商/地域/预算未确认前不购买或创建 Bucket。
5. 日备份加密后放到 VPS 之外，初始保留 7 日/4 周；对象文件与数据库分别备份并核对引用。凭证解密密钥和备份密钥独立保管。RPO ≤24 小时、RTO ≤60 分钟只是初始目标，须恢复演练测量后才能描述实际保障。
6. 同机多容器仍共用主机、磁盘、网络和运维权限。主机故障时 Web/API/Worker/数据库可能同时停止；独立 Worker 只隔离进程生命周期，异地备份只提供恢复能力，均不等于高可用。

## 不选方案

- Kubernetes、多主节点或微服务：目前没有容量证据支持额外控制面与分布式运维成本。
- API 进程内后台任务：不能在 API 重启后可靠恢复分析；不满足持久任务契约。
- Redis 作为唯一任务队列事实源：当前 PostgreSQL 足以承载小规模领取、幂等和结果事务，避免引入双系统一致性问题。
- 同机对象存储作为唯一备份：不具备独立故障域。也不未经复核就安装某个自托管实现。

## 代价

同机资源竞争、短维护窗口、手动恢复和主机单点风险仍存在。DB 队列增加数据库压力，之后依据队列等待、连接数与内存实测决定是否扩容；不预先宣称吞吐、SLA 或零停机。

## 兼容策略

旧 Render 和开发 Compose 保持原状；部署脚本必须显式选新配置，不能复用隐含生产环境变量。现有同源 URL/API 契约不变。旧数据迁移需单独授权、隔离恢复和切换计划，不自动停用/删除旧环境。服务器资料只阻塞 U1 外部验收，不阻塞当前本地设计交付。
