# ADR-011：日志内部函数不提交，外层工作单元拥有事务

- 状态：Accepted for implementation（设计已确定；尚未重构业务代码）。
- 日期：2026-08-31；任务：U0-02；实施：U2-01、U2-03、U4-01。
- 依据：[风险 R03/R04](../upgrade/RISKS.md)、`backend/app/services/diet.py`、`backend/app/core/database.py`。
- 配套：[确认入口](ADR-010-authoritative-draft-confirmation.md)、[有序同步](ADR-014-ordered-sync-and-snapshots.md)。

## 背景

现有 create/update/delete 服务内自行 `commit`，异常分支也会 `rollback`。直接循环调用 `create_log` 只能得到多个独立事务；失败后外层回滚不能撤销已经提交的第一条。当前请求的认证查询还可能已触发 AsyncSession 事务，不能不分状态就套 `session.begin()`，也不能用嵌套事务冒充整批原子提交。

## 决策

### 事务所有权

1. 提取 `create_log_in_transaction`、`update_log_in_transaction`、`delete_log_in_transaction`（目标命名，尚不存在）。接收同一个会话、已验证 owner 和规范请求，只执行查询/条件写入/flush/生成事件；禁止 commit、rollback、网络调用和后台调度。异常原样交给外层。
2. 外层工作单元（Unit of Work）负责 begin、一次 commit 和失败 rollback。普通日志 API 的兼容服务包装一条内部操作；草稿确认包装 N 条日志、N 条 SyncChange、Confirmation、Corrections 和草稿状态。业务约束依旧由服务端检查，调用内部函数不能跳过权限和 expected_version。
3. 使用写工作单元专属 AsyncSession，避免复用认证依赖已经 autobegin 的读会话。认证层只传递不可变主体标识；写事务内重新检查主体有效性/资源归属。不要把另一个会话绑定的 ORM 对象直接混入，必要字段重新查询。
4. API 返回 DTO 在写事务成功提交后交付；失败不能把 flush 后生成的 ID 当成成功。外层负责释放会话；内部函数可 flush 获得主键及约束错误，但 flush 不是持久成功。

### 锁顺序和不变量

所有会生成日志同步事件的写入口遵守同一顺序，包括普通 CRUD、AI 批量确认和演示数据写入：

```text
开启短写事务
  → 本用户 sync_state 行 FOR UPDATE（任何日志变更之前）
  → 确认幂等检查 → 草稿行（如有）
  → 需要的日志行（多条时按稳定 ID 排序）
  → 校验 / 日志变更 / 分配用户序号 / 事件 / 纠错 / 确认
  → 一次提交并释放锁
```

- 同一用户不同日志也先取同一同步锁；不同用户互不因该锁串行。状态行用唯一 user_id 创建，首次写入的并发初始化必须是原子 upsert 后锁定，不能“先查不存在再无保护 insert”。
- 草稿编辑只锁草稿，不在持有草稿锁后反向请求同步锁；Worker 只写 Job/Draft，不进入日志同步锁。多用户维护脚本按稳定 user_id 顺序，或逐用户事务；不能绕过公共写入器直接生成无序事件。
- 校验和幂等命中尽量在写入前完成；幂等重放不新建日志/事件、不推进用户序号。序号在普通行内事务递增，不使用 sequence 作为提交顺序保证。
- 原业务乐观锁仍然保留，`UPDATE/DELETE ... WHERE version = expected_version` 影响 0 行时抛出明确冲突，外层全部回滚。串行同步锁不能代替客户端版本冲突检测。
- 目录修订按不可变版本读取，权限在事务内校验。模型调用、S3 下载等网络动作在事务外完成；数据库锁不能覆盖数十秒模型等待。

### 异常与重试

1. 确认键/草稿唯一约束是最后防线，不仅依赖预查询。数据库约束失败后外层先回滚；只有识别到预期的命名唯一约束，才在新事务读取已完成结果并核对 hash。其他 IntegrityError 是真实错误，不能一律伪装为幂等成功。
2. 可恢复数据库错误按明确类别有限重试整个工作单元；不能从“第三条日志”续跑已回滚的批次。请求 key/payload 不变，网络模型步骤不在事务重试函数里。
3. “commit 响应失败”可能是数据库已提交但客户端未知；用同一确认键重新读取/重放，而不是生成新键。普通日志仍遵循原 `client_id` 幂等契约。
4. 事务测试应在真实 PostgreSQL 验证锁和竞争；SQLite/Mock 只覆盖局部分支，不能据此声称生产并发正确。

## 不选方案

- 每条日志 commit 后失败再补偿删除：用户/同步读取可能看到半批数据，补偿自身也可能失败。
- 向已有函数加 `commit=False` 到处传：容易遗漏某个异常分支 rollback，调用者难以明确事务归属；采用命名明确的内部函数和外层包装。
- 用 savepoint 包裹会自行 commit 的函数：没有解决事务所有权，可能提前结束外层事务。
- 在 API 路由周围无条件 `begin`：认证读会话已有事务时存在冲突，不以吞异常解决。

## 代价

新增内部/外层两层接口和集中写入口约束；每用户写入串行，会增加高频单用户请求等待。整批确认需设实体数上限控制锁时长；初始上限在 U2 契约中固定并测试。该成本换取清晰原子性和可证明的提交顺序，吞吐影响需 U5 测量。

## 兼容策略

现有 API 路径、响应、幂等 hash 语义、统计、404/409 等行为不变；旧测试继续保留。U4-01 先把用户同步锁接入所有现有写入口，U2-01 再提取内部函数时必须保留锁顺序，不能在重构中退回旧顺序。新约束先增量迁移，不能改写已发布的 Alembic 文件。数据库回滚方案受 ADR-014 的兼容写入器要求限制。
