# ADR-002：使用 PRAGMA user_version 管理 SQLite 迁移

- 状态：Accepted
- 日期：2026-07-15

## 背景

项目原来在每次启动时运行一组 `CREATE TABLE IF NOT EXISTS`。这种方式可以创建缺失表，却不能可靠管理新增字段、索引变更、数据回填和多版本升级顺序。

## 决策

- 使用 SQLite 内置的 `PRAGMA user_version` 保存当前 Schema 版本。
- 每个迁移具有递增版本号、名称和 `up` 函数。
- 应用只执行版本号高于当前数据库的迁移。
- 每个迁移在独立事务中执行，成功后才更新版本并提交。
- 失败时回滚，并保留原始错误作为 `cause`。
- 数据库版本高于应用支持版本时拒绝继续，避免旧 App 误写新结构。
- 已发布迁移不可修改，Schema 变化必须新增迁移。

## 为什么没有引入第三方迁移库

客户端当前只有一个 SQLite 数据库和少量表，基于 `user_version` 的迁移运行器足够清晰，也便于学习事务和版本控制。服务端 PostgreSQL 将使用 Alembic，因为服务端 Schema、部署环境和迁移需求更加复杂。

## 风险与应对

- 风险：迁移 SQL 在真实设备失败。应对：迁移事务、单元测试、升级路径真机测试和备份/导出能力。
- 风险：开发者修改历史迁移。应对：代码评审约束，后续可为迁移文件建立校验。
- 风险：多个异步写入与迁移并发。应对：迁移必须在数据库初始化阶段、页面开放前完成。
