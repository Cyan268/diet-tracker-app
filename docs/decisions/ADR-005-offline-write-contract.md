# ADR-005：离线写入的幂等键、所有权与乐观锁

- 状态：已接受
- 日期：2026-07-15

## 背景

移动端在弱网下会把写入保存在本地 Outbox，恢复网络后重试。客户端可能在服务端已经提交成功、但响应丢失时再次发送同一条记录；同一记录也可能在两台设备上被同时编辑。如果只使用普通 `POST` 和最后写入覆盖，前者会生成重复饮食记录，后者会静默丢失修改。

## 决策

- 每条饮食记录携带客户端生成且在重试间保持不变的 `client_id`。
- 数据库使用 `(user_id, client_id)` 唯一约束作为最终并发防线，而不只依赖“先查询再插入”。
- 服务端保存创建请求的规范化 SHA-256 指纹：同一键、同一内容返回已有记录；同一键、不同内容返回 HTTP 409。
- 饮食记录包含从 1 开始的 `version`。更新和删除必须携带 `expected_version`，SQL 使用 `WHERE user_id = ? AND id = ? AND version = ?`；影响行数为 0 时返回 HTTP 409。
- 所有用户私有资源都在 SQL 查询条件中包含 `user_id`。其他用户的资源统一表现为 404，避免暴露资源是否存在。
- 食品库允许全局食品（`owner_user_id IS NULL`）和用户自定义食品；用户只能查询全局食品和自己的食品。
- 饮食记录保存营养快照。目录食品由服务端按克数或标准份量确定性换算；自定义食物必须提交经过范围校验的营养值。

## 取舍与后果

- 乐观锁适合冲突少、读取多的移动应用，不会长时间持有数据库锁；代价是客户端必须处理 409，并决定刷新、覆盖还是让用户合并。
- 创建请求指纹可检测错误复用，但目前不保存完整历史响应；记录后来被编辑后，创建重试返回的是当前资源状态。若业务要求严格重放原始响应，应增加独立幂等请求表和过期清理任务。
- 营养快照会重复保存一部分数据，但保证食品目录更新不会改写历史统计，并保留当时用户实际确认的结果。
- SQLite 集成测试已覆盖顺序重试、冲突和用户隔离；Docker PostgreSQL 双请求测试已覆盖唯一约束竞争与乐观锁更新。真实多设备弱网仍待验证。
