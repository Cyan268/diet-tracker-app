# ADR-012：食品、草稿实体与日志的身份分层

- 状态：Accepted for implementation（设计已确定；映射和目录修订尚未实现）。
- 日期：2026-08-31；任务：U0-02；实施：U2-01～04、U4-01～02。
- 依据：[风险 R01/R02/R08](../upgrade/RISKS.md)、`src/db/rows.ts`、`src/features/sync/pullSyncService.ts`、`backend/app/models/food_log.py`。
- 配套：[唯一确认路径](ADR-010-authoritative-draft-confirmation.md)、[有序同步](ADR-014-ordered-sync-and-snapshots.md)。

## 背景

本地食品使用本地字符串 ID，后端食品使用 UUID，二者没有已验证映射。现有普通上行按自定义营养快照工作，这不等于云端可信目录匹配。演示账号重置、跨设备同步还说明：本地日志主键不一定等于远端 client_id，不能依靠“现在碰巧相同”关联所有数据。

## 决策

### 身份职责

| 身份                                         | 生成方 / 作用域                                | 表示什么                                  | 禁止替代的身份                        |
| -------------------------------------------- | ---------------------------------------------- | ----------------------------------------- | ------------------------------------- |
| `local_food_id`                              | SQLite / 当前安装                              | 本地食品缓存或用户录入条目                | 不是云端食品 UUID                     |
| `food_item_id + catalog_revision`            | 服务端 / 公共或本人目录                        | 稳定食品身份与不可变营养修订              | 不是草稿实体或正式日志                |
| `draft_id + entity_id`                       | 服务端 / 当前 owner 的草稿                     | 本次分析中的一项食品；改名/改量仍是同一项 | 不用名称、数组下标做 ID               |
| `local_log_id`                               | SQLite / 当前安装                              | 本地行主键；碰撞时可另生成                | 不是必须等于 client_id                |
| `client_id`                                  | 普通创建由客户端；确认由服务端规则生成 / owner | 一次日志创建的稳定幂等身份                | 不是每次 HTTP 请求的追踪 ID           |
| `server_id`                                  | PostgreSQL / 正式日志                          | 服务端正式记录身份                        | 不是本地食品 ID                       |
| `client_request_id / client_confirmation_id` | 客户端 / owner                                 | 一次分析或一次确认请求的幂等键            | 不是实体 ID，也不代表外部计费恰好一次 |

### 食品目录和历史值

1. U2-02 为云端食品增加不可变修订数据：稳定 `food_item_id` 指向当前可用修订，历史修订记录名称、品牌、来源、每份/每 100 单位的营养与单位。新修订另写，不原地改历史。食品私有性按服务端 owner 校验，客户端给的 scope 不构成授权。
2. 本地新增目录映射表，保存本地食品 ID、云端食品 UUID、修订号、作用域（公共或 owner）及来源。只在目录拉取或服务端明确匹配后建立映射，不因字符串一样或名称相似自动认定同一食品。映射按远端身份/修订/作用域唯一；本地食品可有多个历史修订映射。
3. 旧本地食品和旧日志保持原样，没有可靠映射时继续作为自定义快照。历史来源标记为 legacy/custom，不能事后冒称官方目录。确认前找不到可用修订则要求重新审阅，不能静默套最新营养值。
4. 正式日志保存显示名、来源类型/修订、数量单位和最终营养快照，历史统计不再实时连接最新目录重算。删除食品引用也不能丢失日志显示与营养。
5. ml 和 g 只有在食品/修订明确提供换算依据时转换；糖/钠/咖啡因等字段明确单位。缺少密度或营养资料时要求用户提供可验证的自定义信息或暂不确认，不能当 0 或直接信模型。

### 草稿与正式日志映射

1. 每个分析实体有稳定 UUID。编辑保留 ID，删除记入纠错差异，新加实体分配新 ID；服务端校验提交实体属于此草稿且没有重复 ID。名称相同的两份饮品仍可为两个实体。
2. 在线确认按固定版本 UUIDv5 命名规则从 `draft_id + entity_id` 生成日志 client_id，并在 Confirmation 保存 `entity_id → client_id → server_id` 映射。具体 namespace 常量随实现固定并测试，不包含姓名、食品名、日期或其他敏感原文。
3. 确认键唯一和草稿只能确认一次是事务幂等边界；可重复计算 client_id 只是辅助稳定身份，不能替代唯一约束或权限检查。确认重放直接返回保存的映射，不重新生成新日志 ID。
4. Confirmation 保留原始/最终实体身份，Corrections 引用该确认下的实体；删除实体也保留纠错基线。正式日志后续修改不回写旧分析作为“模型原始输出”。

### 本地日志与账号

1. SQLite 日志增加独立的 `remote_client_id`（可空），保留 `server_id/server_version/owner_user_id`。非空远端映射按 `(owner, server_id)`、`(owner, remote_client_id)` 唯一；本地主键碰撞时只更换 local_log_id，不能改变已发送请求里的 client_id。
2. 普通新建通常令初始 client_id 等于本地 UUID，但在首次尝试发送后必须独立冻结。已提交但响应丢失时，原 payload/key 不再合并/取消；后续编辑/删除保留意图，等原创建身份找回后排序发送。
3. 远端确已删除、用户明确选择保留本地并重建时，这是新的创建代次，使用新的 client_id；不复用已删除创建的键。旧键及结果未知的创建不能被当作已删除，需先恢复原结果。
4. 所有查找、Outbox、草稿缓存、确认恢复、快照 staging、冲突都以 owner 隔离；未登录数据保持独立作用域。不得按邮箱把重置后新 user_id 当作旧 owner，也不得通过放松归属检查解决跨账号 ID 碰撞。
5. 同步请求捕获不可变 owner/session epoch；Token 刷新仅能属于同一会话代次。切换后暂停旧队列，旧响应不能写入新作用域。身份表不能替代这个异步执行边界。

## 不选方案

- 把本地食品 ID 填进服务端 UUID 字段：缺少身份与修订映射，也无法验证权限/来源。
- 名称或数组索引作为实体键：改名、排序和同名食品会使纠错/幂等关联错位。
- 同一个 UUID 兼任所有层的主键：跨账号碰撞与重新创建时无法分别保留本地引用和远端幂等身份。
- 目录更新批量重算旧日志：改变历史营养事实，用户回看与 AI 周报会漂移。

## 代价

增加映射、来源字段、迁移和一致性断言；本地缓存需要管理历史修订。确定性 ID 会暴露关联性，不能视为匿名化或授权凭证。目录可信度取决于可追溯数据与单位校验，不因存入数据库就成为医学事实。

## 兼容策略

服务端先加可空字段/新表，旧自定义快照 API 继续有效。SQLite 用新版本迁移，优先从已知 server_id 对应的权威响应回填 remote_client_id；存在歧义则保留旧行、待同步修复，不全表假定 `id = client_id`。迁移不得改写已尝试的 Outbox payload/hash。U2-05 若开放离线实体新增和预生成 client_id，必须继续采用可验证的稳定规则并单独验收，不能无条件接受客户端声称的云端身份。
