# ADR-001：产品主线与目标架构

- 状态：Accepted
- 日期：2026-07-15

## 背景

项目当前是一款本地饮食记录 App。为了将其升级为可用于 AI 全栈实习求职的项目，需要补充真正解决用户问题的 AI 能力，以及服务端、云端数据、部署和工程质量能力。

## 决策

产品主线确定为：

> 自然语言/图片输入 → AI 结构化识别 → 用户确认 → 确定性营养计算 → 趋势分析 → 个性化建议。

技术架构采用：

- 保留 React Native + Expo 客户端。
- 保留 SQLite，但将其职责调整为离线缓存和 Outbox。
- 新增 FastAPI 模块化单体后端。
- 使用 PostgreSQL 作为云端真实数据源。
- 使用 Redis 承担缓存、限流和异步任务协调。
- 使用私有对象存储保存上传图片。
- 通过服务端 AI Orchestrator 调用模型，客户端不接触模型密钥。
- AI 负责语义识别与解释，确定性代码负责数值计算与正式写入。

## 原因

- AI 功能围绕降低记录成本形成单一、可演示的产品闭环。
- FastAPI 与 Python AI 生态结合紧密，适合个人项目快速迭代。
- PostgreSQL 适合用户、记录、食品及关系约束明确的业务数据。
- 模块化单体比微服务更符合当前规模，部署和调试成本更低。
- 离线优先可以复用现有 SQLite 投入，并形成有价值的面试技术点。

## 暂不选择的方案

### 只增加聊天页面

无法解决饮食记录成本高的核心问题，也难以证明 AI 工程能力。

### 让客户端直接调用模型

模型密钥无法安全保存，也难以实现统一限流、审计、缓存和 Provider 切换。

### 一开始拆分微服务

当前没有独立扩缩容或团队边界需求，会增加不必要的分布式复杂度。

### 把 RAG 作为第一阶段重点

饮食记录和用户统计主要是结构化数据，更适合 SQL 查询和 Tool Calling。非结构化营养知识检索可以在核心闭环稳定后评估。

## 影响

积极影响：形成清晰的产品叙事；前后端、AI、数据和部署能力都有实际载体；面试中可以讨论离线同步、幂等、结构化输出和 AI 评测。

代价：需要新增后端和运维知识；客户端数据层需要逐步重构；必须投入时间建立测试和评测体系。
