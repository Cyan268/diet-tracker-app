# ADR-004：短期 JWT 与刷新令牌轮换

- 状态：已接受
- 日期：2026-07-15

## 背景

移动端既需要减少用户重复登录，又不能把长期有效、无法撤销的凭证暴露在每次 API 请求中。单独使用长期 JWT 虽然实现简单，但令牌泄漏后在过期前很难失效；把每个 Access Token 都存入数据库又失去了无状态校验的主要优势。

## 决策

- 密码使用 Argon2id 单向哈希，哈希与验证在线程池执行，避免阻塞异步事件循环。
- Access Token 使用 15 分钟有效期的 HS256 JWT，固定校验算法、签发方、受众、类型、过期时间、用户 ID 和唯一令牌 ID。
- Refresh Token 使用 48 字节随机源生成的不透明令牌，有效期 30 天；数据库只保存 SHA-256 摘要，不保存原文。
- 每次刷新都撤销旧令牌并签发同一 `family_id` 下的新令牌，同时通过 `replaced_by_id` 保留轮换关系。
- 刷新时使用 `SELECT ... FOR UPDATE` 锁定令牌行。已撤销令牌再次出现时，视为可能被盗用，撤销该令牌家族中仍有效的所有令牌。
- 登出接口按 Refresh Token 撤销令牌并保持幂等。
- 生产环境拒绝调试模式、默认 JWT 密钥以及少于 32 个字符的 HMAC 密钥。

## 取舍与后果

- Access Token 在最多 15 分钟内不能被服务端单独撤销；换来普通 API 请求无需访问令牌表。高风险操作仍可增加二次校验或拒绝列表。
- Refresh Token 需要数据库状态和清理策略，但换来了登出、轮换、重放检测和设备会话管理的扩展基础。
- 随机 Refresh Token 具有足够高熵，因此可使用快速 SHA-256 摘要定位；用户密码熵低，必须使用带盐且计算昂贵的 Argon2id，两者不能混用策略。
- SQLite 集成测试已验证顺序轮换与重放后的家族撤销语义；SQLite 不提供 PostgreSQL 等价的行锁行为，因此真正的并发刷新测试必须在 Docker/PostgreSQL 可用后补充。在此之前不能宣称并发场景已完成实机验证。
