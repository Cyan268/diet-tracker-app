# ADR-007：游标增量同步、删除墓碑与冲突解决

- 状态：已接受
- 日期：2026-07-15

## 背景

Outbox 只能把当前设备的修改推向云端，不能让另一台设备看到变化。按日期反复下载全部记录既浪费流量，也无法表示已删除记录；只依赖 `updated_at` 还会遇到相同时间戳、服务器时钟精度和分页边界问题。

## 决策

- 后端 v4 增加不可变 `sync_changes` 表。每次日志新增、更新或删除都在同一个数据库事务中写入变更事件。
- 事件使用全局单调递增整数 ID 作为游标，并始终按当前 `user_id` 过滤。客户端提交 `after`，服务端按 ID 顺序返回最多 200 条。
- upsert 事件保存当时的完整日志快照，避免记录稍后被更新或删除后无法重放旧分页；delete 事件保存服务端 ID、客户端 ID 和版本作为 tombstone。
- SQLite v3 为每个账号保存独立游标。整页变更与游标推进在同一个独占事务中提交；任何一条应用失败都会回滚整页。
- 没有本地待发送事件时，较新的云端版本覆盖缓存；远端删除直接删除缓存。
- 存在本地未提交修改且云端版本更高或已删除时，保留本地数据、阻塞 Outbox，并写入 `sync_conflicts`。
- 用户可选择“使用云端”取消本地事件，或“保留本机”基于最新云端版本重试。若云端已删除，保留本机会把本地修改转成一次新的 create。

## 取舍与限制

- 当前变更日志尚未做保留期限和压缩。生产化需要设计最小有效游标、过期游标返回和全量重建协议，不能直接清表。
- 整数游标简单可测试，但暴露系统级顺序；接口仍按用户过滤，因此不能把游标本身当授权凭证。
- 冲突处理是整条记录二选一，尚未实现字段级合并。饮食记录较小、冲突频率低，第一版优先保证不静默丢数据。
- 另一设备创建的服务端食品尚未同步进本地食品目录；拉取日志会保留营养快照并使用通用显示名。后续需要独立同步私有食品目录。
- PostgreSQL 容器中的顺序 CRUD/tombstone 冒烟和三类双请求竞争已通过；两台真实 Android 设备、弱网、高负载压力与崩溃恢复测试尚未执行。
