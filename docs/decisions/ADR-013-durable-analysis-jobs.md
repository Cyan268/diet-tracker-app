# ADR-013：持久分析任务、租约隔离与外部结果未知

- 状态：Accepted for implementation（设计已确定；Worker/Attempt 尚未实现）。
- 日期：2026-08-31；任务：U0-02；实施：U2-01、U3-01、U2-03、U3-03。
- 依据：[升级计划](../UPGRADE_DEVELOPMENT_PLAN.md)、[当前基线](../upgrade/BASELINE.md)、`backend/app/services/ai.py`。
- 配套：[部署进程](ADR-009-single-vps-and-worker.md)、[草稿确认](ADR-010-authoritative-draft-confirmation.md)。

## 背景

当前同步 AI 服务有有限请求重试和规则降级，但没有跨进程恢复的 Job/Attempt/租约状态。外部模型与本项目数据库不处于同一事务：请求超时不等于没执行；模型已返回而数据库写入失败，也不等于可以再次免费调用。

目标是保证本项目的一次分析只有一个有效草稿结果，记录每次尝试的已知/未知事实；不承诺供应商端恰好调用一次或恰好计费一次。

## 决策

### 数据与状态

1. PostgreSQL 保存 `analysis_jobs`、`analysis_attempts`、草稿和实体。Job 以 `(user_id, client_request_id)` 唯一，并核对版本化请求 hash；同键同请求返回同 Job，异内容 409。Job 固定 input/schema/provider/model/prompt_version，配置变更要新建请求，不能让同键执行不同模型。
2. 可恢复文本输入最小化加密保存并记录 key_version；图片只存本人已验证/封存的 upload_id，不接收任意远程 URL。hash 不是可恢复输入，也不等同匿名化。初始可配置保留策略在 U2/U3 实现中固定；原文到期必须停止相关重试并给出 `input_expired`，不能一直保留输入支撑无限重试。
3. Attempt 独立保存序号、lease_token、调用阶段、开始/结束时间、Provider request_id（若有）、错误分类、Token 用量来源、费用是否已知。通用日志不存输入、Key、签名 URL 或完整模型响应。
4. Key 不复制到 Job/Attempt；仅引用 owner 下的凭证身份/版本。每次调用受控解密校验，凭证被删除/禁用后不能继续以旧缓存无限调用；演示用户只允许规则/样例 Provider。

| 状态       | 含义                                    | 后续                                   |
| ---------- | --------------------------------------- | -------------------------------------- |
| queued     | 已持久接单，尚未领取                    | 可领取/取消                            |
| running    | 某次尝试持有有效租约                    | 成功、明确失败、未知或取消             |
| retry_wait | 已明确可重试，且还有期限/次数/预算      | 到期重新领取，创建新 Attempt           |
| succeeded  | 草稿与最终状态同事务持久化              | 不再调用模型                           |
| failed     | 永久错误、输入过期或已用尽重试          | 展示原因；用户可另建任务               |
| unknown    | 外部可能已执行/计费，未得到可信最终结果 | 查询恢复或明确授权重试，不默认自动重发 |
| cancelled  | 用户不再接受本任务结果                  | 不等于外部请求已停止或退款             |

### 领取、续租与结果提交

1. 短事务按 `next_attempt_at, created_at, id` 顺序，使用 `FOR UPDATE SKIP LOCKED` 领取 queued/retry_wait，创建新 Attempt、不可复用随机 lease_token 和租约期限后提交。它适合队列领取而不是普通一致列表读取。[PostgreSQL SELECT 锁文档](https://www.postgresql.org/docs/17/sql-select.html)
2. 事务外执行模型调用。初始工程默认：单 Worker、全局并发 1、租约 120 秒、心跳 20 秒、单次网络总超时 60 秒、Job 总期限 10 分钟、最多 3 次 Attempt、每用户最多 3 个未结束 Job；这些是待压测配置，不是性能/费用承诺。预检校验超时小于租约且心跳有足够余量。
3. 续租和结果写回都按数据库当前时钟校验 `job_id + running + lease_token + lease_expires_at > clock_timestamp()`。不能使用固定在事务开始时的时间来判断等待行锁之后的租约是否仍有效。更新影响 0 行则立即丢弃写回资格。结果事务锁定 Job 并再次校验，一次保存 Draft/Entities、Attempt 摘要和 Job succeeded；job_id 上草稿唯一约束兜底。[PostgreSQL 当前时间函数语义](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)
4. 取消、回收、换租都会撤销旧 token 的写权限。旧 Worker 晚到结果即使内容“看起来正确”也不能覆盖状态。租约过期可解除本地占用，但不据此认定外部请求已停止。
5. API 停接单、Worker 停领取分别设开关；优雅关停停止领取、在有限时间内处理在途租约，否则交给恢复流程。Redis 不参与草稿结果原子提交，不是租约事实源。

### 不确定性、重试和费用

| 观察到的事实                                | 处理                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| 尚未进入 dispatch 阶段，参数/凭证失败       | 明确失败；按错误类型决定是否需要用户修改                                  |
| 已确认未发送的本地短暂故障                  | 限次退避；每次 Attempt 可追溯                                             |
| Provider 明确返回可重试错误                 | 仅按适配器已验证契约分类；尊重有效 Retry-After、总期限/预算               |
| dispatch 意图已落库，之后超时/断连/进程崩溃 | 保守标为 unknown；数据库记录无法与 HTTP 发送原子提交                      |
| 模型响应已收到，暂时落库失败                | 持有效租约时只重试数据库持久化，不再次调用模型；结果失去后按 unknown 恢复 |
| 租约过期或用户取消后模型才返回              | fencing 拒绝覆盖；记录可能计费，不宣称退款或取消外部执行                  |

1. Provider 适配器声明经验证的幂等键/结果查询能力；不根据一个 Header 名或 SDK 存在就假设支持。可查询时用同一外部身份恢复；没有能力时 unknown 默认不自动重发付费请求，提示可能重复费用，用户明确选择另一次尝试才继续。
2. 429/5xx 不是无条件安全重试证明；是否已计费/产生结果由适配器契约决定，未知就按 unknown。普通 4xx/Schema 不合法不无限重试。规则/Mock 为无外部副作用路径，可按已验证分类重试。
3. 用户确认重试只增加 Attempt/新的租约，不改变原 Job 的请求语义；仍须剩余次数、总期限和预算允许，否则另建任务。原成功结果一旦持久化就不再调用。
4. 接单配额与领取并发限制在数据库短事务内原子检查，不能“count 后无锁 insert”。初版单消费者并发限额仍有显式测试；扩多个 Worker 前需共享数据库配额/槽位，不依靠每进程信号量。unknown 外部请求仍可能在执行，单并发只表示本项目已知在途量，不保证供应商端没有重叠。
5. 每次有可能发出的 Attempt 预占预算；unknown 不自动释放为“未消费”，保留待核对。缺少实际 Token/价格时费用为 unknown，不能记为 0；计算值标为 estimate，不能当供应商账单。应用预算只能限制自身发起的调用，不能形成外部账单硬上限保证。

## 不选方案

- FastAPI BackgroundTasks/内存队列：进程重启后任务与输入丢失，不满足 202 持久语义。
- 仅 Redis 锁或只校验 status：过期 Worker 可能与新 Worker 状态相同，无法阻止迟到写回。
- 所有失败自动重试三次：会把结果未知误当请求未执行，并可能重复扣费。
- 为保证一致性把网络调用放进数据库事务：无法把供应商加入本地事务，还长期占用锁和连接。
- 仅最终 Job 记录一次 tokens/cost：掩盖失败、重试和未知尝试的费用边界。

## 代价

需要 Attempt 表、恢复扫描、心跳、配额与更复杂的 UI。保守 unknown 策略降低自动完成率，用户可能要确认重试或核对服务商记录；这是缺乏跨系统事务时诚实处理不确定性的代价，不称 exactly-once 计费。

## 兼容策略

复用当前 Provider 的结构化输出、Schema、规则降级和用户级凭证模块；新 Job 路径的重试由 Worker 统一拥有，禁用 Provider 内部不可观测的重试叠加，或将其逐次映射为 Attempt。旧同步接口在兼容窗口保留原行为，但不能宣称它也具备持久恢复。先完成 Worker/Mock 端到端再开放 202；真实模型调用需单独确认模型、样本、隐私和预算。
