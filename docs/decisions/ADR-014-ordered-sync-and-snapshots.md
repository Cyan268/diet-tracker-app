# ADR-014：每用户提交有序同步、版本兼容与稳定快照

- 状态：部分实施；U4-01 提交顺序、Outbox 与会话隔离本地验证通过，Native 待验收；v2/快照/保留恢复仍是待实施设计。
- 日期：2026-08-31；任务：U0-02；实施：U4-01～03、U2-03/04。
- 依据：[风险 R01/R02/R03/R07/R09/R10](../upgrade/RISKS.md)、`sync_changes.id` 及现有 `id > after` 查询。
- 关系：收紧 [ADR-007](ADR-007-cursor-sync-and-conflict-resolution.md) 的故障保证，不直接改变 v1 游标含义；所有写入配合 [ADR-011](ADR-011-log-unit-of-work.md)。

## 背景

实施证据见 [U4-01 记录](../upgrade/tasks/U4-01.md)。其中真实 PostgreSQL 旧算法反序提交已复现，新写入器的竞争、回滚和迁移测试通过；下文有关 v2、稳定快照和保留清理的验收场景尚未执行。

全局自增 ID 代表分配顺序，不代表提交顺序。A 先分配小 ID 但后提交，B 大 ID 先提交时，客户端推进游标后可能永远跳过 A。PostgreSQL 的 sequence 不随事务回滚，Read Committed 只读到语句开始前已提交数据；这个组合足以说明当前保证不完整，真实项目故障实验仍需 U4-01 完成。[PostgreSQL 17 事务隔离文档](https://www.postgresql.org/docs/17/transaction-iso.html)

另一个问题是快照：先读取最大游标、再跨请求分页实时日志，会混入不同时点的新增/更新/删除，不能据此安全重建 SQLite。

## 决策

### 1. 先修写入顺序，再开放新协议

1. 增加 `user_sync_state(user_id PK, epoch UUID, last_seq BIGINT, minimum_valid_after BIGINT)`；`sync_changes` 增加 user_seq，唯一 `(user_id, user_seq)`，旧全局 id 保留。
2. 所有日志写事务先锁本人状态行 `FOR UPDATE`，再改变日志、递增该行 last_seq、写事件，一次提交。批量写入按稳定实体顺序分配连续序号；回滚同时撤销行计数与事件。幂等重放不分配新号，禁止任何入口先分配全局 ID 再拿用户锁。
3. 同用户事务 B 必须等 A 提交/回滚才能进入写入，因此可见 user_seq 是已提交前缀；不同用户可以并行。这是本项目根据锁顺序建立的保证，不是 sequence 自动提供的性质。普通 CRUD、批量确认、维护/种子写入都必须覆盖。
4. 全局 v1 ID 仍在拿到用户锁后产生；新写入因同用户串行也不会产生该用户反序提交。它修复切换后新事件的顺序，不会找回旧客户端已经漏掉的历史事件。

```text
同一用户：
A: 锁 state → 日志 + seq=11 + 事件 → 提交/释放
B:          等待同一 state 锁 ─────→ 日志 + seq=12 → 提交
读者：只能看到前缀 10、11 或 12，不会先看到 12 再迟到 11
```

### 2. 显式 v2 游标与兼容窗口

1. v1 路径/数字 after/全局 ID 语义不变；新增 `/api/v2/sync/...` 及 `protocol_version: 2`。v2 cursor 显式为 `{epoch, after}`，after 是非负十进制字符串，避免 JavaScript number 的整数精度上限。具体请求/响应在 U4-02 生成 OpenAPI，不提前修改旧 Schema。
2. owner 只来自认证，不相信 cursor 或 query 中的 user_id。epoch 是协议代次，不是权限 Token；客户端游标按 origin + owner + protocol 独立保存。
3. `last_seq` 为当前已提交高水位。`minimum_valid_after` 是已完整清理的连续前缀上界：after 等于它仍合法，因为下一条所需事件是 after+1；after 小于它、超过 last_seq 或 epoch 不匹配返回 410/明确重建指令，不能返回空页伪装同步成功。格式非法为 422。
4. 以备份恢复数据后、重新对外服务前必须更换 epoch，并使旧快照失效；否则旧游标可能碰巧小于恢复库的高水位却指向另一段历史。账号重建是新 owner，不能沿用旧游标。
5. 切换使用维护窗口：停止旧写入者并等待在途事务结束 → 增量迁移/按旧 ID 对各用户历史事件回填序号 → 部署所有遵守锁的写入器 → 验证后开放。回填只是确定历史重放顺序，不能声称修复了曾被漏拉的历史。v2 首次启用强制稳定快照建立新基线。
6. v1 保留期内不启用事件清理。待支持快照恢复的客户端完成迁移/明确停止旧版写同步，再启用 U4-03；旧版不能在未知 410 下静默丢数据。应用回滚只能到同样遵守锁与新 Schema 的桥接版本；回到无锁旧镜像不属于安全自动回滚。

### 3. 物化快照：固定内容、固定高水位

1. 快照只覆盖日志及显示/营养/身份快照，不覆盖 Profile、食品目录、Job 或草稿。资料仍是时间戳 LWW，不能对外宣称这些实体具有日志同级的冲突与恢复保证。
2. 创建时在一个短 REPEATABLE READ 事务内，首先对用户状态行取 `FOR SHARE`，读取 epoch/high_water，再读取本人所有当前日志并物化到 `sync_snapshots/sync_snapshot_entries`。写事务使用 FOR UPDATE，快照因此与同用户写入短暂互斥；若 RR 锁竞争产生序列化失败，整个快照创建有限重试。
3. 保存 snapshot_id、owner、epoch、high_water、条目数、内容校验摘要、expires_at；条目保存稳定 ordinal 和完整日志快照。分页只读取这个 snapshot_id 的物化内容，不再实时 join 当前 food_logs。客户端按 ordinal 续传，跨请求不保持数据库事务。
4. 首版配置快照 TTL 30 分钟，并限制每用户活动快照数和总条目/字节数；超过规模明确拒绝/提示，不悄悄截断。物化事务必须有超时和测量，用户量增长后再评估其他快照方案。
5. 创建快照与事件清理通过同一 state 行锁协调：快照持共享锁直至物化/登记提交，清理持排他锁后查询活动快照。在其有效期内，不清除任一活动快照 high_water 之后所需的事件；条件不能满足则显式使快照失效并要求重建。
6. 快照过期返回 410；他人 snapshot_id 返回 404。清理先更新状态再分批删相应物化条目，不让半删快照继续被当作有效页读取。

REPEATABLE READ 为同一事务提供固定视图；行锁等待/并发更新仍可能产生需要重试的错误。因此采用短事务物化，而不是让数据库事务跨浏览器翻页存活。[PostgreSQL 17 事务隔离文档](https://www.postgresql.org/docs/17/transaction-iso.html)

### 4. SQLite 恢复与旧响应

1. 快照下载到 owner 隔离的 staging，检查 snapshot_id/epoch、连续页、条目数、唯一身份和规范内容摘要；校验完成前不改正式库/游标。中途崩溃可以恢复 staging 或重建，不清空用户已有数据。
2. 下载期间允许继续本地记录；最终切换短事务前暂停该 owner 的 Outbox 发送/远端应用和页面写入入口，读取最新待同步意图，将服务器基线与所有未解决创建、修改、删除、冲突叠加后原子替换，并设置游标到快照 high_water。暂存层不能覆盖这期间的新本地写入。
3. 被远端修改/删除的本地 pending update/delete 进入明确冲突，不能丢弃；首次发送后的 create 仍以原 key/payload 恢复，不能因快照没有它就换键。切换后继续拉 high_water 之后的增量。
4. 每条远端应用保存远端身份和新旧顺序依据；delete 的 tombstone 优先于同版本 upsert。确认响应和旧请求不能回退已应用版本。快照切换后若没有单条排序证据，旧确认只保存映射并安排同步，不盲目复活记录。
5. 所有异步工作捕获 owner/session epoch，并在发送和应用前检查。同一会话的 Token 更新不能被切账号后的凭证替代。SQLite Web 和 Native 共享写入调度器的保证要用真实运行时验证，不能只凭 `withWriteTransaction` 名称判断独占性。

### 5. 清理时机

生产清理默认关闭，直到 U4-02 快照恢复、客户端迁移及恢复演练通过。U4-03 以可配置 30 天为起点，只清理安全连续前缀，清理事件与 minimum_valid_after 更新同事务；活动快照限制清理边界。首次真实清理需要独立授权、dry-run 和恢复说明。

## 不选方案

- 全局自增 ID、时间戳或重复拉最近 N 条：不能证明提交顺序，回看窗口还会随停机时间失效。
- 在 v1 原地替换成用户序号：旧 cursor 会被误解释，导致跳过或重放不相干范围。
- 长期 SERIALIZABLE/跨 HTTP 数据库事务：不能解决错误客户端协议，还带来连接与事务生命周期成本。
- MAX(cursor) + 实时 OFFSET 分页：数据变化时分页会重复/漏行，高水位不对应一致内容。
- 清空本地库重新下载：会删除尚未上传的真实用户记录和删除意图。

## 代价

单用户写入和快照创建有短暂锁竞争；物化快照占数据库空间；v1/v2 兼容和 SQLite staging 增加实现复杂度。首版针对小规模作品集，任何“不会漏”声明都限定为所有写入口遵守锁、协议正确使用且恢复/保留边界受控的情况，不承诺无限离线或自动合并所有冲突。

## 兼容策略

采用增量迁移、桥接写入器、维护窗口和 v2 首次快照，保留旧全局 ID；不重写 ADR-007 历史结论为“早已支持 v2”。U4-01 先修 Outbox/session/事务与提交顺序，U4-02 再实现本文件的 v2/快照，U4-03 最后启用清理。AI 批量写入发布至少要求 U4-01 已验收，未上 v2 的客户端不能使用 v2 游标。资料同步独立记录其 LWW 局限。
