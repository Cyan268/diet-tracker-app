# AI 对话状态与消息持久化

## 1. 目标

本阶段将单轮 Tool Calling 助手升级为可创建、切换、连续追问、刷新恢复和删除的多轮对话。对话状态由 NutriPilot 自己的 PostgreSQL 管理，OpenAI 请求继续使用 `store: false`，不把产品的会话所有权、删除语义和历史读取完全托管给模型供应商。

OpenAI 官方说明 Responses 请求本身可以通过重复传入交替的 `user`/`assistant` 消息手动维持上下文；若要完整复用推理状态，还应保留之前的全部输出项。本项目当前使用 `reasoning.effort: none`，只保存用户可见消息并手动重建有限上下文，这是隐私、可解释性和实现复杂度之间的首版取舍。参考 [Conversation state 指南](https://developers.openai.com/api/docs/guides/conversation-state)。

## 2. 数据模型

```text
users
  └─ assistant_conversations
       └─ assistant_messages
            └─ trace_id → ai_call_logs
```

`assistant_conversations` 保存当前用户、标题和创建/更新时间。`assistant_messages` 保存角色、正文、顺序号、参考日期，以及助手消息的 Provider、模型、Prompt 版本、Token、延迟、降级标记、工具证据、警告和追踪 ID。

关键约束：

- 会话查询始终包含 `user_id`，其他用户只能得到统一的 404。
- `(conversation_id, sequence)` 唯一，保证消息顺序不重复。
- `(conversation_id, client_message_id)` 唯一，支持安全重试。
- 删除会话时显式删除消息，PostgreSQL 外键也配置 `ON DELETE CASCADE`。
- AI 调用日志仍只保存问题哈希；对话功能因为产品需要会保存完整消息正文，用户可以删除整段对话。

## 3. API

| 方法     | 路径                                               | 说明                           |
| -------- | -------------------------------------------------- | ------------------------------ |
| `GET`    | `/api/v1/ai/assistant/conversations`               | 按最近更新时间列出当前用户会话 |
| `POST`   | `/api/v1/ai/assistant/conversations`               | 创建空会话                     |
| `GET`    | `/api/v1/ai/assistant/conversations/{id}`          | 读取会话和最近 100 条消息      |
| `DELETE` | `/api/v1/ai/assistant/conversations/{id}`          | 删除当前用户拥有的会话         |
| `POST`   | `/api/v1/ai/assistant/conversations/{id}/messages` | 追加一轮用户问题与助手回答     |

前端首次发送时才创建会话，避免仅打开页面就产生大量空记录。首条问题自动成为会话标题，最多显示最近 20 段会话。

## 4. 上下文裁剪与事实刷新

每次回答只传入最近 8 条消息，并额外设置 6,000 字符上限；历史从用户消息开始，避免把孤立的助手回答放在上下文首部。这是一个可预测的启发式上限，不是精确 Token 预算。未来接入真实模型并采集分词数据后，可以改为 Token 预算、摘要加最近消息的组合策略。

历史只帮助理解“那最近呢”“它的蛋白质呢”之类省略表达。Prompt 版本升级为 `nutrition-assistant-v1.1.0`，明确要求摄入、趋势、目标和食品营养事实必须在当前轮重新调用工具，不能直接复述历史数字。这样即使用户在两轮之间修改了饮食记录，回答也会读取新数据。

## 5. 幂等与并发边界

客户端在发送前生成 `client_message_id`。如果网络结果不确定，页面会保留会话 ID、问题和消息 ID，手动重试仍使用同一个键；服务端已完成该轮时直接返回原会话，不再次生成消息。相同键与不同正文或参考日期组合会返回 409，防止键被误用。

数据库行锁和唯一约束保证最终只保存一轮消息。但两个服务实例完全同时收到同一新键时，仍可能都先调用模型，再由唯一约束淘汰其中一次写入，因此当前不是“模型调用恰好一次”。生产化可加入 Redis 分布式 single-flight、处理中状态和过期恢复，进一步减少重复费用。

## 6. 隐私与生命周期

对话正文可能包含饮食和健康相关信息，因此读取、追加、删除都必须鉴权并按用户过滤。模型请求仍设置 `store: false`；这只表示应用不依赖供应商存储响应，不代表数据没有发送给模型。使用 OpenAI Provider 时，当前裁剪后的消息和工具结果仍会发送给 OpenAI，界面和隐私政策需要如实说明。

当前支持用户主动删除单个会话，尚未实现自动保留期限、数据导出中的对话内容、逐条消息删除和管理员审计。部署时还需要数据库静态加密、备份删除策略和访问审计。

## 7. 验证结果

- API 集成测试覆盖创建、列表、连续两轮、顺序号、证据持久化、幂等重放、同键异内容 409、跨用户 404、删除和最近四轮上下文裁剪。
- HTTP Mock 验证历史消息按 `user`/`assistant` 顺序进入 Responses 请求。
- 前端单测验证弱网重试复用消息 ID，以及内容变化后生成新 ID。
- 真实 PostgreSQL 已迁移到 `20260720_0007`。
- Expo Web 浏览器验收完成两轮追问、第二段会话、历史切换和刷新恢复，控制台无错误。

本阶段全量结果：后端 62 个测试通过、3 个环境相关测试跳过，综合覆盖率 79%；前端 16 个套件、48 个测试通过。

## 8. 简历边界

可以写“实现用户隔离的多轮 Tool Calling 会话、消息持久化、上下文裁剪和幂等重试”。不能写成无限上下文、端到端加密、模型调用恰好一次或完整自主 Agent。真实 OpenAI 多轮效果和成本仍需使用用户显式配置的 Key 单独评测。
