## 1. 项目定位与范围

### 1.1 一句话定位

NutriPilot 是离线优先的 AI 饮食理解与营养分析平台：通过文字或图片生成可审阅草稿，匹配可追溯食品数据，由确定性代码计算营养数值；用户确认后保存，使用幂等与版本化同步处理弱网和多设备场景，并通过纠错数据持续评估识别效果。

### 1.2 必须保留的产品原则

- 普通饮食记录可以离线新增、编辑、删除，不因 AI 不可用而失效。
- 文本/图片 AI 分析需要联网；不得将云端 AI 包装成离线能力。
- AI 只负责语义抽取和解释，不拥有数据库写权限，不负责生成最终营养数值。
- 置信度只作为审阅提示；模型自报置信度不是经过验证的正确概率。
- 用户确认不是免责按钮：服务端仍必须进行权限、范围、版本和营养数据来源校验。
- 统计描述的是“已记录摄入”，不能把未记录解释成未进食。
- 记录、推荐与周报用于生活记录和软件工程学习，不提供疾病诊断或治疗方案。

### 1.3 升级完成后必须能演示

1. 使用公网 HTTPS 地址打开 Web 版，登录独立测试账号。
2. 输入一句包含多个食品的描述，看到数量、候选食品、来源与待确认信息。
3. 修改识别结果并确认，只生成一批正式日志，刷新页面仍能恢复。
4. 上传图片，看到任务排队、处理中、成功或可解释失败状态。
5. 断网后进行普通记录，恢复网络后同步；两设备冲突不会静默覆盖。
6. 周报引用真实事实；记录不足时不输出误导性环比。
7. 展示一次评测对比、一次并发/故障实验、一次数据库恢复演练。

### 1.4 首轮不做

- Kubernetes、服务网格、多地域容灾、大规模微服务拆分。
- 自训练视觉大模型、精确三维份量估算、声称通过图片精确测量克数。
- 没有评测依据的向量数据库、复杂 RAG 或自动自主写入 Agent。
- 支付、社交社区、排行榜、复杂运营后台等偏离主线的功能。
- 一开始同时重写认证、前端导航和全部业务目录。

### 2.2 五个不可忽略的设计边界

#### A. 云端确认与本地 Outbox 不能重复写入

V2 默认采用“AI 草稿在线确认、普通日志仍然离线优先”：

- AI 草稿确认由服务端一次事务创建日志、变更事件和纠错记录。
- 客户端接收结果后走远端数据应用路径，不调用会创建普通 create Outbox 的 addLogs。
- 不能既调用云端 confirm，又为同一批日志生成普通 create 事件。
- 离线时允许编辑已缓存草稿，但显示“待联网确认”，不能显示“已云端保存”。
- 真正的离线草稿确认作为 U2-05 可选增强，使用专门的 confirm_draft Outbox 事件。

#### B. 当前 Service 内部提交事务，需要先重构事务边界

现有 create_log 等函数内部会 commit。不能在确认多条食品时循环调用它，再声称“整批原子提交”。应提取不提交的内部写入函数，由最外层业务操作统一 commit/rollback，同时保留旧 API 的行为。

#### C. 数据库幂等不等于模型费用恰好一次

唯一键可以避免重复建任务；Worker 租约可以避免旧执行者覆盖新结果。但若模型已执行、网络响应丢失，应用无法普遍保证没有重复计费。应区分确定失败与结果未知，保留调用尝试记录，按 Provider 实际能力处理，不能写出“绝不重复收费”的验收承诺。

#### D. 自增序号不是事务提交顺序

当前 sync_changes 使用自增 ID。需要测试“事务 A 分配较小 ID 后暂停，事务 B 以较大 ID 先提交，客户端推进游标，再提交 A”的情况。不能仅因 ID 单调增长就认定不会漏事件。U4-01 是早期必做正确性任务，必须先于游标清理和全量快照上线。

#### E. 失败的 create 不一定没有到达服务端

Outbox 中 failed 可能来自响应丢失。已发送创建请求的幂等键与原始负载应冻结；后续编辑应成为独立 update，不能改写曾发送的 create 内容后继续使用原键。离线删除也不能因为看不到 server_id 就直接丢弃一个结果未知的创建。

## 3. Codex 执行协议

### 3.1 每轮执行方式

1. 用户指定一个任务 ID，例如 U1-01；不得默认执行整份路线。
2. 先检查适用的 AGENTS.md、Git 状态、相关代码、依赖任务与测试。
3. 简述本轮目标、边界、预计修改文件和验收方式。
4. 对已实现能力先复核，不重复造轮子。
5. 小步实现：模型/迁移 → 业务 → API → 客户端 → 测试 → 文档。
6. 先执行针对性测试，再执行受影响层的完整检查。
7. 输出实现、验证、限制与证据；未跑测试必须说明原因。
8. 只有满足全部验收项才在任务表中勾选；外部验收未执行则保持未完成。
9. 不擅自提交、推送、打标签、发布 PR 或操作生产；按用户授权执行。
10. 不自动创建子任务代理；只有用户或仓库指令明确授权时才进行并行代理开发。

### 3.2 必须取得明确授权的操作

- 购买服务器、域名、对象存储、付费监控或增加套餐。
- 使用真实模型 API 批量评测、改变 Provider、扩大费用预算。
- SSH 登录真实服务器并变更配置，修改 DNS、生产防火墙或生产 Secret。
- 发布公网服务、推送镜像到外部仓库、打开注册入口、发送邀请邮件。
- 生产数据库迁移、恢复、删除、清表、缩减存储保留期限。
- 将真实用户文本、图片、日志或备份发送到第三方。

服务器或模型凭证尚未提供时，可以继续完成本地实现、Mock、文档、镜像和隔离测试；不能把外部依赖未就绪误写成代码验证通过。

### 3.3 默认实施约束

- 只增量修改当前项目，保留无关用户改动。
- 不提交 Secret、真实图片、真实健康资料、Token 或数据库备份。
- 不为过测降低断言、删除失败用例或放宽用户隔离。
- 不对有数据的环境运行删除卷、数据库重建、自动 downgrade。
- 新 API 更新 Pydantic、OpenAPI JSON、生成的 TypeScript 和契约测试。
- 已发布的 Alembic/SQLite 迁移不可原地改写；新增迁移版本。
- 性能、准确率、稳定性指标必须附环境、样本、版本、时间和原始证据。

## 6. U1：自有服务器与安全发布

### 6.1 建议运行形态

保留 FastAPI 同源托管 Expo Web；API 与 Worker 运行相同版本业务代码但使用不同启动命令。

```text
公网客户端
  → Caddy（80/443、TLS）
    → API + Expo Web（内部8000）
      → PostgreSQL（主数据、草稿、任务、同步）
      → Redis（限流、演示协调）
    → 对象存储S3入口（仅私有Bucket和签名操作）

Worker → PostgreSQL领取任务 → 对象存储/外部模型 → 写回草稿
备份任务 → 加密数据库备份 → 服务器之外的存储
```

- 起步资源假设：2核4GB、60～80GB SSD、稳定公网IP；不是已验证容量。
- 如同机增加监控与对象存储且内存不足，再依据测量升级，不预先购买高配置。
- 云模型调用，无本地大模型，无GPU。
- 默认单API进程、单Worker进程、有限模型并发；调高并发前核算连接池和内存。
- Ubuntu 24.04 LTS 为候选基线，采购和安装时重新核对维护状态、镜像和官方说明。

确认事务：

1. 校验当前用户和请求范围；只接受有权使用的食品。
2. 查找已完成幂等确认：同键同内容返回同一次确认；同键不同内容409。
3. 锁定草稿，检查版本、过期状态和是否已经确认；不同键也不能确认两次。
4. 从可信食品目录/经校验的自定义输入确定性生成营养快照。
5. 创建整批FoodLog与SyncChange；正式日志不从模型输出直接取最终营养数值。
6. 保存纠错和幂等确认映射，更新草稿状态，一次提交。
7. 重试返回确认快照/身份映射；后续日志被编辑时不把新状态伪装成原始确认结果。

现有同步文本分析接口可在兼容窗口继续使用，但新202接口必须由U3-01持久Worker承担。不得承诺后台持久任务却仅依赖FastAPI进程内BackgroundTasks，也不能为了按章节顺序推进而先发布一个无人消费的任务API。

验收：并发确认只生成一批记录；响应丢失后重试不重复；非法版本409；跨用户404；目录变更处理明确；事务中断不留下半批日志。

## 8. U3：可靠任务与图片识别

### U3-01：PostgreSQL Worker

本任务在U2-01完成后即可提前实施，是U2-03新异步分析接口的前置任务；无需等待图片上传或真实模型凭证。

新增独立Worker入口、任务Repository/Service和analysis_attempts尝试记录；不改成微服务通信。

任务状态建议：queued → running → succeeded；明确可重试失败走retry_wait；永久错误走failed；外部结果不确定走unknown；取消单独记录，不能假定已取消外部费用。

任务领取：

1. 短事务按next_attempt_at、created_at查找可领取任务，使用FOR UPDATE SKIP LOCKED。
2. 更新状态、attempt_count、不可复用lease_token和lease_expires_at，写Attempt后提交。
3. 在事务外执行模型调用。
4. 必要时续租；租约时长、心跳周期、网络超时和总任务期限明确配置。
5. 结果提交必须检查job_id、状态与lease_token，防止过期Worker覆盖新结果。
6. 一个事务保存Draft、Entities、Attempt摘要和Job最终状态。

故障策略：

- 429/5xx等按Provider契约分类，有限重试并尊重可用的Retry-After；不能重试所有4xx。
- Worker失联后租约可被回收；旧Worker的延迟结果必须被fencing检查拒绝。
- 模型已响应但落库失败与请求未发出不是同类问题；尝试日志区分已知和未知状态。
- Provider支持幂等键或结果查询时经验证后使用；不支持时未知结果需要明确重试策略/用户确认及费用提示。
- 应用内只保证任务/结果幂等，不承诺外部计费exactly-once。
- 限制每用户排队数、全局任务并发、最大尝试次数和费用预算；共享演示账号默认规则/样例任务。
- 增加停止接单/暂停Worker开关；关停时停止领取并处理在途租约。

验收：两个Worker并行、领取后崩溃、租约过期、旧结果迟到、超时、取消和数据库失败均在真实PostgreSQL中验证；模型通过Mock完成常规CI。

- 低置信度结果要求用户确认数量；无法识别返回明确失败或空草稿，不编造成功。
- Provider密钥只能在服务端受控使用，演示账号不能消耗服务器付费Key。
- 原始图片仅按用户知情同意送往选定服务；临时对象访问时长覆盖任务生命周期但不过度扩大。
- 客户端用有上限和退避的轮询，切后台暂停，重新进入恢复；先不增加WebSocket/SSE复杂度。
- 任务完成状态跨刷新/重启可恢复；网络错误不等于任务失败。
- 真实模型调用需要先确认Provider、模型、样本数、预算与数据范围。

验收：文字和图片共用草稿确认；展示完整任务生命周期；普通手工记录不受Worker停机影响；真实调用与Mock结果在报告中分开。

## 9. U4：同步协议正确性与恢复

### U4-01：早期必做正确性审计

2026-08-31 实施更新：首次请求冻结、会话隔离、每用户序号锁及迁移已实现，真实 Web SQLite/PostgreSQL 验证通过，详见 [U4-01 任务记录](upgrade/tasks/U4-01.md)。Native 真机/模拟器实际事务边界尚未验证，故任务总表暂不勾选。v1 契约保留，v2 与快照仍属于 U4-02；暂不连接手机时可先推进 U1-01 本地发布包。

任务：

- 写出“创建已提交但响应丢失，用户随后编辑/删除”的可复现测试。
- 从第一次发送开始冻结创建payload和幂等键；仅从未尝试发送的创建可以安全合并。
- 后续编辑排在创建确认之后；服务端身份未知的删除不能直接丢弃。
- 切换账号/登出时，所有在途请求捕获原会话和owner；旧响应不能写入新账号作用域或使用新Token发送旧用户事件。
- 验证Web事务、Native独占事务和页面写入并行时的实际边界，不因同名封装就假定等价。
- 增加真实PostgreSQL“较大ID先提交、较小ID后提交”的测试。
- 采用每用户同步状态行和事务内递增序号作为候选方案：写日志前获取同一用户的序列锁，序号分配、日志和事件同事务提交；所有写入入口遵循同一锁顺序。
- 序号对外按用户有序；旧全局ID可保留内部用途，不能未经迁移直接改游标含义。
- 不使用简单时间戳、重复拉最近几条等未证明完整性的方式掩盖漏事件。

验收：响应丢失后内容修改不产生幂等键冲突导致的静默丢失；跨账号在途同步不越权；反序提交不会漏变更；旧API行为有兼容测试。

### U4-02：协议与稳定快照

任务：

- 定义protocol_version、opaque cursor或显式cursor版本，以及minimum_valid_cursor的精确含义。
- 不在原v1接口突然切换为按用户序号；通过版本化接口/明确协商升级，旧客户端无感误读必须被阻止。
- 新增快照创建/分页读取接口，使用独立快照ID、所属用户、固定高水位和过期时间。
- 小规模首版建议在一个短REPEATABLE READ事务内读取同步高水位并物化快照条目；分页读取物化内容，避免跨HTTP请求长期保持数据库事务。
- 不能“先取MAX(cursor)，再跨多次请求实时分页查日志”就声称一致快照。
- 快照包括必要显示名/营养快照；说明用户资料/食品目录是否独立同步，不能声称所有实体都已增量同步。
- 客户端下载到staging表，整套校验后原子切换；保留当前用户未发送修改、删除意图和冲突。
- 将游标设置为快照高水位后继续拉取增量；快照建立后的更新/删除仍能重放。
- 活动快照有效期内应保留它需要的增量，或在不满足时明确要求重建。

验收：快照分页期间并发新增/更新/删除不漏数据；中途崩溃不破坏可用本地库；存在Outbox时重建不清除用户未同步记录；快照不能跨用户使用。

### U4-03：过期与回收

任务：

- 初始保留期限如30天仅作可配置默认值，先完成全量恢复后才启用生产清理。
- 游标超出有效边界返回明确410及重建说明，不能返回空changes假装已同步。
- 分批清理、更新保留下界与活动快照保护，避免长事务和无界DELETE。
- 提供dry-run统计和清理报告；首次真实清理需用户授权。
- 单独描述profileSyncService当前按时间戳比较的局限；未实现版本控制前不宣称资料具备日志同级冲突保证。
- 验证两浏览器上下文和至少一台真实Android设备；无法真机验证时记录限制，不用Mock代替。

验收：过期→快照→增量完整恢复；清理失败可重试；范围外记录未受影响；所有删除具有明确目标、备份和恢复说明。

## 10. U5：事实层、评测、监控与性能

### U5-01：事实层补强

复用现有weekly_report与assistant_tools，重点是统一口径而不是新增同类报表。

- 统一业务日期、时区、单位、舍入规则和统计区间。
- 保存营养目录修订/快照，历史记录不因目录改变漂移。
- 输出有效记录天数、覆盖率、日均、达标天数、餐次/饮品结构。
- 既有4天完整度门槛作为产品规则记录，不解释成医学有效性阈值。
- 缺少上周数据时不输出环比，缺少个人资料时不判断个人目标。
- 结构化Schema不能保证模型叙事数字正确；增加事实引用ID/指标引用约束和异常叙事回归，必要时降级模板。
- 验证前后端计算一致性，浮点舍入允许误差必须明示。

验收：每项核心事实能追溯到SQL/计算函数；错误叙事被拦截或标记，已知限制公开；不声称完全消除幻觉。

### U5-02：评测集与指标

首版建议100～200条文本样本；图片另建经许可的30～50条试验集，覆盖遮挡/混合菜/非食物。样本数是计划目标，不是上线准确率承诺。

- 拆分开发集与冻结测试集；同义改写/同一图片变体按组划分，避免泄漏。
- 图片“真实克数”需要称量依据；无法获得时评估识别和合理拒答，不编造份量金标准。
- 每条记录数据来源/授权、场景标签、期望实体、单位、可接受范围和标注人。
- 小样本双人复核或抽检争议标签；盲测集不用于Prompt反复调优。
- 规则Provider、真实模型和降级样本分别报告，不能混合抬高效果。
- schema_version、数据集版本、Prompt、模型、代码SHA、配置、时间、样本数写进报告。

| 指标            | 必须固定的口径                                                 |
| --------------- | -------------------------------------------------------------- |
| Schema合法率    | 合法响应数/所有尝试；拒绝/网络失败另列，不能随意剔除分母       |
| 实体P/R/F1      | 按实体匹配规则统计，不等同于整条记录正确率                     |
| 完全正确率      | 所有必要字段都正确的样本数/评测样本数                          |
| 数量/单位正确率 | 转换为标准单位后比较；容差需事先写入评测定义                   |
| Top-K召回       | 正确食品在候选集合中的比例；与最终Top-1分开                    |
| 用户修改率      | 有修改确认数/全部确认数；实体级、字段级另列                    |
| 放弃率          | 未确认且满足统计窗口的分析数/完成分析数；区分失败与主动丢弃    |
| 延迟            | 排队、Provider执行、整条链路P50/P95分别报告                    |
| 费用            | 已知Token估算+未知/失败尝试披露；价格配置不全时显示未知，不是0 |

门禁：先记录基线，再在独立测试集设不退化阈值；不预先承诺95%等无依据目标。真实模型评测为授权的手动任务，不在每次PR里无预算调用。

验收：离线规则评测进入CI；一次版本对比可复现；原始结果脱敏保留；线上纠错进入评测须单独获得数据使用同意。

### U5-03：监控、告警和预算

- API：路由模板、状态码、请求延迟、连接池等待；指标标签不能使用用户ID、request_id或原始URL造成高基数。
- Worker：排队数量、最老任务年龄、执行耗时、租约回收、未知结果、错误分类。
- 同步：结果数、重试/冲突数、游标过期数；客户端遥测可失败，不影响业务提交。
- AI：Provider、模型/Prompt版本、Schema失败、降级、Token、预算使用。
- 主机：内存、磁盘、容器重启、备份最近成功时间。
- request_id、job_id、confirmation_id用于脱敏日志关联，不采集原始描述、完整对象URL、Token或Key。
- Redis故障、PostgreSQL故障、模型不可用分别设计：现有认证限流fail-closed规则不能随意改成放行。
- 单服务器先用已有JSON日志、外部存活探测、备份告警与可选Sentry；Prometheus/Grafana按资源启用，不默认部署完整ELK。
- 指标/管理页内网访问；公网/第三方监控只发送必要脱敏数据。
- 告警使用窗口、最小样本量和冷却，避免低流量项目被单次请求噪声淹没。
- 预算设置分用户/全局；费用预估不完整时不能声称严格财务上限，配合Provider侧预算和关闭开关。

验收：受控故障触发并恢复告警；日志隐私回归通过；监控自身故障不破坏普通记录；未授权不开付费追踪或外发敏感数据。

### U5-04：性能、安全和故障报告

依次运行：小样本冒烟 → 原基线回归 → 阶梯负载 → 10～30分钟稳定性 → 有针对性的优化复测。

- 压测优先测试环境/专用测试账号；公网部署压测必须授权。
- 压测发起端与服务端分开，不能让负载机争抢同一VPS资源后忽略该影响。
- 固定数据规模、分页大小、读写比例、网络、缓存冷热、错误定义和硬件；记录CPU/内存/池配置。
- 普通API负载使用规则/Mock模型，不把无预算真实AI调用纳入高并发测试。
- 报告客户端和服务器视角延迟，不把局域网毫秒结果作为公网体验。
- 找到饱和点后基于慢SQL/EXPLAIN、连接池、锁等待、CPU证据优化；不先加缓存再找理由。
- 若增加缓存，说明key作用域、失效、用户隔离、陈旧容忍及Redis故障降级。
- 进行用户越权、上传攻击、弱网、组件停机、磁盘阈值、备份失败和应用回滚演练。

验收：形成docs/upgrade/PERFORMANCE_REPORT.md和FAILURE_DRILLS.md；报告实际瓶颈与边界，不使用“支持高并发/高可用”等无条件结论。

### 12.2 最低故障矩阵

| 场景                       | 必须观察到的结果                            |
| -------------------------- | ------------------------------------------- |
| 同一个分析键并发提交       | 只有一个Job，同键异内容409                  |
| 同一个草稿并发确认         | 只有一次Confirmation和一批日志              |
| 确认响应丢失               | 可恢复同次结果，不新增普通create Outbox     |
| 第二条日志写入失败         | 整批回滚，不留下Correction/SyncChange半成品 |
| 云端已接受创建但客户端编辑 | 原创建payload冻结，编辑作为后续更新         |
| 创建结果未知时本地删除     | 保留删除意图，不能误丢事件                  |
| 两设备更新同版本           | 只允许一个成功，其余明确409                 |
| 较大游标事务先提交         | 不漏掉随后提交的小序变更；修复方案有证据    |
| 处理拉取页一半失败         | 数据与游标整体回滚                          |
| 登出后旧同步响应到达       | 不污染新账号或泄漏旧数据                    |
| 快照期间发生更新/删除      | 快照+增量恢复一致最终状态                   |
| Worker租约过期后旧结果到达 | 旧执行者无法覆盖新结果                      |
| Provider超时但可能已执行   | 标记未知/策略明确，不声称免费安全重试       |
| 上传完成后再次覆盖对象     | 验证封存对象不变，或明确拒绝使用            |
| 数据库或对象恢复           | 记录数量、身份、营养快照和对象关联可核对    |
| AI/Worker不可用            | 普通离线手工记录仍可用                      |

| AI识别错误       | Schema、匹配候选、人工确认、评测和降级    | 不保证精确份量或医疗准确性     |
| 日志/图片隐私    | 最小采集、短保留、权限、删除与脱敏        | hash不等于匿名化               |
| 同步迁移丢数据   | 顺序证明、版本接口、稳定快照、staging切换 | 不允许直接清本地库“修复”       |
| 部署损坏Schema   | expand/contract、独立迁移、备份           | 应用回滚不等于数据库回滚       |
| 任务范围失控     | 一轮一任务、依赖门禁、P0优先              | 不为技术数量新增组件           |
| 文档过期         | 每任务校准、版本化报告                    | 不能把历史Render状态当当前事实 |
