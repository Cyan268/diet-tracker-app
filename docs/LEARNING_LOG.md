## 学习卡 001：为什么当前项目还不是全栈应用？

日期：2026-07-15

### 业务背景

当前应用已经能完成饮食记录、计算和统计，但所有用户数据都只存在手机的 SQLite 数据库中。

### 核心认识

“全栈”不等于同时使用了 TypeScript 和数据库。通常需要客户端、服务端 API、服务端数据库、认证授权、部署运维等完整链路。

当前 SQLite 是嵌入式数据库，由 App 进程直接访问。它适合离线缓存，却无法天然支持账号、跨设备同步和集中权限控制。Open Food Facts 也由客户端直接访问，因此服务端无法统一缓存、限流和监控。

### 目标方案

保留 SQLite 作为本地缓存，新增 FastAPI 和 PostgreSQL 作为云端数据源。客户端通过 REST API 同步数据。

### 面试回答模板

> 项目最初是纯客户端单机架构，SQLite 直接存储饮食记录。为了实现多设备同步并保护 AI 密钥，我增加了 FastAPI 服务端和 PostgreSQL。SQLite 没有被直接删除，而是保留为离线缓存，通过 Outbox 和幂等 API 同步到云端，这样弱网情况下仍能记录饮食。

## 学习卡 002：为什么不能把 AI API 直接写在 App 中？

日期：2026-07-15

### 问题

移动端安装包中的代码和配置可以被提取。如果把模型 API Key 放进 App，攻击者可能盗用 Key，产生费用和数据风险。

### 目标方案

客户端只调用自己的后端。后端保存模型密钥，并负责用户鉴权、速率限制、Prompt 管理、日志审计、超时重试和模型切换。

### 面试回答模板

> 我没有让客户端直接请求大模型，因为客户端无法安全保存密钥，也无法做统一限流和审计。AI 请求先到后端 Orchestrator，后端校验用户身份、构造结构化 Prompt、调用模型并校验结果，最后只返回业务需要的数据。

### 继续追问

Q：后端就绝对安全吗？

A：不是。后端仍需要使用环境变量或密钥管理服务、最小权限、Key 轮换、日志脱敏、限流和费用告警，不能把密钥提交到 Git。

## 学习卡 003：为什么不让大模型直接计算最终热量？

日期：2026-07-15

### 问题

大模型擅长理解非结构化描述，但不适合作为精确数值计算和事实存储工具。同样的输入可能产生不同估算，而且模型可能虚构营养数据。

### 目标方案

让模型识别食物名称、份量和烹饪方式，随后匹配食品数据库。最终热量和营养素由可测试的确定性函数计算，并要求用户确认低置信度字段。

### 面试回答模板

> 我把 AI 的职责限制在语义理解和候选提取上，营养计算仍使用食品数据源和确定性函数。这样既利用了模型处理图片和自然语言的能力，又能让数值可追溯、可测试。模型输出还必须经过 Schema 校验和用户确认，不能直接写入正式记录。

## 学习卡 004：开发依赖安装中的版本冲突

日期：2026-07-15

### 业务问题

Phase 0 需要为 Expo 项目增加 ESLint、Prettier 和 Jest。

### 遇到的问题与定位过程

第一次安装因受限环境无法访问 npm registry，报错为 `fetch failed`。确认命令尚未进入依赖解析阶段，因此判断为网络权限问题，而不是包版本问题。

允许联网后，直接执行不带版本的 `npm install --save-dev jest-expo` 又产生依赖冲突。npm 选择了面向 Expo 57 和 React Native 0.86 的最新版 `jest-expo`，它要求更高版本的 React，而项目当前使用 Expo 54 和 React 19.1。

### 最终方案

使用 Expo 官方的兼容版本解析结果，将 `jest-expo` 固定在 54.x，并同步固定 Jest 29 和对应类型包。没有使用 `--force` 或 `--legacy-peer-deps` 绕过冲突。

### 为什么不使用 `--force`

`--force` 只能让安装继续，不能证明组合真的兼容。依赖可能在运行测试或构建时才失败，使问题更难定位。正确做法是根据当前 Expo SDK 选择对应版本，并将结果写入 lockfile。

### 面试回答模板

> 我在给 Expo 54 接入 Jest 时遇到 peer dependency 冲突。定位后发现 npm 拉取了面向 Expo 57 的最新版 jest-expo，而不是当前 SDK 的兼容版本。我没有用 force 跳过检查，而是固定 jest-expo 54.x 和 Jest 29，并通过 package-lock 保证 CI 与本地使用相同依赖树。

## 学习卡 005：类型检查、Lint、测试和 CI 的职责

日期：2026-07-15

### 业务问题

项目原来只有运行和构建命令。虽然 `tsc` 能通过，但它不能证明业务计算正确，也不能阻止未使用变量等代码问题。

### 最终方案

- `npm run typecheck` 检查 TypeScript 类型关系。
- `npm run lint` 检查未使用变量、React Hooks 使用和代码坏味道，并把警告也视为失败。
- `npm test` 使用 Jest 和 `jest-expo` 验证确定性业务逻辑。
- `npm run check` 串联以上检查。
- GitHub Actions 在每次 Push 和 Pull Request 时执行同一条 `check` 命令。

### 测试策略

第一批测试覆盖营养换算、每日目标和提醒规则，因为这些函数输入输出明确，错误会直接影响用户看到的数值。没有为了提高覆盖率数字去大量编写只验证页面能否渲染的脆弱测试。

当前 3 个测试套件共 9 个测试全部通过，整体行覆盖率为 26.81%。其中营养换算和目标计算行覆盖率为 100%，后续会优先补充饮品计算、数据映射和关键 API，而不是追求无差别的全仓库覆盖率。

### 面试回答模板

> TypeScript 只能检查静态类型，不能证明公式结果正确；Lint 负责发现未使用变量和 Hooks 等代码问题；Jest 通过具体输入输出验证业务行为。我把三者组合为统一 check 命令，并在 CI 中执行。第一批测试优先覆盖营养计算和提醒规则等高价值纯函数，而不是单纯追求覆盖率数字。

### 可继续追问的问题

- 为什么单元测试优先选择纯函数？
- 覆盖率达到多少才算够？
- CI 与本地 Git Hook 有什么区别？
- 为什么测试不应依赖真实网络？

## 学习卡 006：从幂等建表升级为版本化迁移

日期：2026-07-15

### 原有方案及限制

`CREATE TABLE IF NOT EXISTS` 只回答“这张表是否存在”，不能回答当前表属于哪个版本，也不能自动新增字段或按顺序执行数据回填。直接删库重建又会丢失用户记录。

### 最终方案

使用 SQLite 的 `PRAGMA user_version` 记录版本。迁移在事务中执行，Schema 修改成功后才更新版本并提交；任何一步失败都会回滚。旧数据库已有表但版本为 0 时，v1 的幂等建表不会删除原数据。

### 测试与验证

测试覆盖了待执行版本选择、拒绝未来版本、成功提交和失败回滚。当前迁移版本为 v1。

### 面试回答模板

> 原项目每次启动只做 IF NOT EXISTS 建表，无法管理字段演进。我用 SQLite 的 user_version 实现顺序迁移，每个迁移都在事务内执行，只有成功后才提升版本；失败会回滚。如果数据库版本高于当前 App 支持版本则拒绝启动，避免旧客户端破坏新 Schema。

## 学习卡 007：为什么要消除数据库边界的 `any`

日期：2026-07-15

### 遇到的问题

Repository 查询结果原来普遍使用 `any`。改成明确的 Row 类型后，TypeScript 发现日期范围汇总和单日汇总错误共用了同一种类型：前者 SQL 返回 `date`，后者不返回。

### 最终方案

为数据库蛇形命名行建立独立类型，例如 `FoodLogRow`、`UserProfileRow` 和 `NutritionTotalsRow`，再由 Repository 显式映射为业务层驼峰类型。动态 SQL 参数也由 `any[]` 收紧为 `string | number | null`。

### 核心认识

类型只在准确描述真实数据契约时才有价值。把数据库结果标成 `any` 相当于关闭了编译器；把多个不同查询强行标成同一种宽泛类型，同样会掩盖错误。

### 面试回答模板

> 我把 Repository 看作不可信数据进入业务层的边界，所以为 SQL 行和领域模型分别建模。收紧类型后实际发现单日聚合 SQL 不返回 date，而日期范围查询返回 date，之前因为 any 没有暴露。拆分查询结果类型后，src 和 app 中显式 any 降为 0。

## 学习卡 008：Liveness 与 Readiness 为什么要分开？

日期：2026-07-15

### 问题

如果健康接口总是访问数据库，数据库短暂故障会导致容器被不断重启；如果健康接口从不访问数据库，负载均衡又会继续把请求发送给无法工作的实例。

### 最终方案

`/health/live` 只检查 API 进程是否还能响应；`/health/ready` 执行数据库 `SELECT 1`。没有 PostgreSQL 时，本地冒烟测试得到 Live 200、Ready 503，符合预期。

### 面试回答模板

> Liveness 用于判断进程是否需要重启，不应该因为外部数据库短暂故障就杀死进程。Readiness 用于判断实例是否可以接收流量，所以会检查 PostgreSQL。数据库不可用时 Readiness 返回 503，让负载均衡摘除实例，但 Liveness 仍保持 200。

## 学习卡 009：AsyncSession 为什么不能全局共享？

日期：2026-07-15

### 核心认识

SQLAlchemy `AsyncSession` 是带有事务和连接状态的可变对象，不是无状态客户端。多个并发请求共享同一个 Session 会混淆事务边界，可能出现一个请求提交或回滚另一个请求数据的问题。

### 最终方案

全局只保存线程安全的 Engine 和 Session Factory。每个请求创建自己的 Session，并在异步上下文结束时关闭。

### 面试回答模板

> Engine 管理连接池，可以全局复用；Session 表示一次逻辑事务，不能跨并发任务共享。我使用 async_sessionmaker 为每个请求创建 Session，并通过依赖的 async context manager 保证请求结束后释放。

## 学习卡 011：为什么不能只发一个长期 JWT？

日期：2026-07-15

### 业务问题

移动端希望长期保持登录，但长期 JWT 一旦泄漏，在到期前很难从服务端撤销。若把 JWT 有效期设得很短，用户又会频繁重新登录。

### 最终方案

使用 15 分钟 Access JWT 访问业务接口，使用 30 天不透明 Refresh Token 换取新令牌。Refresh Token 每用一次就轮换，数据库只保存摘要、家族 ID、过期时间、撤销时间和替换关系。旧令牌再次出现时撤销整个活跃家族。

### 替代方案与取舍

- 单一长期 JWT：实现最简单，但泄漏窗口大且难撤销。
- 每次请求查询服务端 Session：撤销及时，但所有业务请求增加数据库访问。
- 当前混合方案：Access Token 的签名与过期校验不查令牌表，刷新请求有状态；本项目仍加载用户确认账号有效。代价是需要维护刷新令牌表和清理策略。

### 测试与验证

SQLite 集成测试验证了顺序轮换、旧令牌重放和家族撤销。后续 Docker 测试同时使用同一 Refresh Token，真实 PostgreSQL 返回一个 200、一个 401，且胜出的新令牌随后也因重放检测被拒绝，验证了 `FOR UPDATE` 下的家族撤销行为。

### 面试回答模板

> 我没有使用一个 30 天有效的 JWT，而是把访问和续期职责拆开。Access Token 只活 15 分钟，签名与过期校验无需查询令牌表；Refresh Token 是一次性轮换的随机令牌，数据库只存摘要。旧令牌重放时撤销令牌家族。这样把泄漏窗口、普通请求性能和可撤销性放在一个可解释的折中点上。

## 学习卡 012：严格测试如何发现 HMAC 密钥过短

日期：2026-07-15

### 遇到的问题与定位过程

认证 API 第一轮测试全部在 JWT 签发处失败。失败不是签名代码错误，而是 PyJWT 发出 `InsecureKeyLengthWarning`：开发密钥只有 26 字节，低于 HS256 建议的 32 字节。项目把 warning 当成 error，因此潜在安全配置没有被静默忽略。

### 最终方案

把开发默认密钥扩展到 32 字节以上，在 Pydantic Settings 中加入最小长度校验，并继续禁止生产环境使用默认密钥。`.env.example` 同步更新。

### 核心认识

“测试通过”不只代表业务返回值正确。把重要警告升级为失败，可以在依赖升级或安全默认值变化时尽早暴露问题。但不能无差别长期屏蔽警告；应理解来源后修正配置或迁移接口。

### 面试回答模板

> 我在接入 PyJWT 时，严格测试因为 HMAC 密钥不足 32 字节而失败。定位到这不是功能 bug，而是安全警告后，我没有屏蔽 warning，而是在配置模型中加入最小长度约束，并禁止生产使用默认密钥。这说明 CI 也可以验证安全不变量，而不只是状态码。

## 学习卡 013：异步接口中为什么仍会发生阻塞？

日期：2026-07-15

### 问题

`async def` 只允许任务在等待可挂起的 I/O 时让出执行权，不会自动把 CPU 密集代码变成非阻塞。Argon2 为抵抗暴力破解而故意消耗计算和内存，直接调用会阻塞事件循环。

### 最终方案

数据库操作继续使用 SQLAlchemy 异步接口；密码哈希和验证通过 AnyIO 线程池执行。登录不存在的账号时仍验证一个 dummy Argon2 哈希，缩小根据响应时间枚举账号的差异，并返回统一的“邮箱或密码错误”。

### 取舍

线程池保持事件循环可响应，但不会降低单次哈希成本，也不是无限资源。生产环境仍需要登录限流、线程池容量控制和压测。

### 面试回答模板

> async 主要优化 I/O 等待，CPU 密集的 Argon2 不会因为加了 async 就变快。我把哈希和验证放到线程池，避免阻塞处理数据库和网络 I/O 的事件循环；同时对不存在账号验证 dummy hash，降低时序侧信道。高并发下还要配合限流和压测。

## 学习卡 014：为什么“先查再插入”不能保证幂等？

日期：2026-07-15

### 业务问题

移动端请求可能已经在服务端成功，但响应因弱网丢失。Outbox 会重试；如果服务端每次都创建新 UUID，同一顿饭会出现两条记录。

### 容易犯的错误

只在插入前查询 `client_id` 是否存在。两个并发请求可能同时查到“不存在”，随后各自插入，这属于检查与使用之间的竞态条件。

### 最终方案

客户端生成稳定 `client_id`，数据库对 `(user_id, client_id)` 建唯一约束。应用层预查询用于快速返回；数据库约束是最终防线。服务端还保存请求指纹：同键同内容返回 200 和已有资源，同键不同内容返回 409。

### 测试与验证

SQLite API 测试已验证顺序重试不会新增记录、错误复用键会返回 409。后续真实 PostgreSQL 测试同时提交两个相同请求，得到 201/200 且资源 ID 相同，验证了唯一约束竞争路径。

### 面试回答模板

> 幂等不能只靠先查再插，因为并发请求会同时通过检查。我让客户端为本地记录生成稳定 client_id，并在 PostgreSQL 建立 user_id 与 client_id 的联合唯一约束。应用层识别正常重试，数据库约束处理竞争条件；请求指纹还能区分合法重试和错误复用键。

## 学习卡 015：乐观锁如何避免多设备静默覆盖？

日期：2026-07-15

### 业务问题

手机 A 和手机 B 都读到同一条记录，A 修改份量，B 修改备注。如果采用最后写入覆盖，B 的完整更新可能把 A 的份量改动悄悄还原。

### 最终方案

记录包含递增 `version`。更新和删除提交客户端读取时的 `expected_version`，SQL 同时匹配用户、记录 ID 和版本；成功后版本加一。影响行数为 0 返回 409，由客户端获取最新值并提示合并或重试。

### 为什么没有直接使用悲观锁

用户编辑表单可能持续几十秒，不能跨网络请求持有数据库行锁和连接。饮食记录冲突概率较低，乐观锁能在不长期占用数据库资源的情况下检测冲突。

### 面试回答模板

> 我没有使用 last-write-wins，因为它会静默丢数据。客户端提交 expected_version，服务端执行带 version 条件的原子 UPDATE；只有版本未变化时才能成功。冲突返回 409。行锁适合短事务，不能在用户编辑期间跨请求持有，所以这里选择乐观并发控制。

## 学习卡 016：为什么数据库外键不能替代数据权限？

日期：2026-07-15

### 核心认识

外键只能保证 `food_logs.user_id` 指向真实用户，不能阻止用户 A 查询用户 B 的记录。授权条件必须出现在每个私有资源查询中。

### 最终方案

读、改、删、列表和统计 SQL 全部绑定从 Access Token 得到的 `user_id`。直接访问其他用户 UUID 返回 404。用户自建食品也只对所有者可见，全局食品使用空 owner 表示公共目录。

### 测试与验证

双用户 API 测试验证了私有食品搜索隔离、饮食记录直接访问隔离、列表隔离和每日统计隔离。

### 面试回答模板

> 外键解决引用完整性，不解决授权。我把 user_id 作为 Repository 查询的强制条件，而不是查询后再做可遗漏的 Python 判断；对他人资源统一返回 404。测试会创建两个真实账号，验证直接访问、列表和聚合都不会跨用户泄漏。

## 学习卡 017：为什么要从 OpenAPI 生成移动端类型？

日期：2026-07-15

### 业务问题

后端接口持续演进时，如果移动端手写请求和响应类型，字段名、可空性或枚举很容易与真实接口悄悄分叉。这类错误通常要到运行时请求失败才暴露。

### 最终方案

FastAPI 导出确定性的 `openapi.json`，移动端使用 `openapi-typescript` 生成 TypeScript 类型。CI 会重新导出规范、重新生成类型并检查 Git 差异，因此后端改了契约却忘记更新移动端时，合并前就会失败。

### 取舍

生成类型解决的是“契约形状一致”，不等于拥有完整 SDK，也不能替代运行时校验、错误处理和接口集成测试。提交生成文件会增加少量 diff，但新成员无需先启动后端即可获得类型检查。

### 面试回答模板

> 我没有让前后端各维护一份 DTO，而是把 FastAPI 的 OpenAPI 作为单一契约源，用 openapi-typescript 生成移动端类型，并在 CI 中重新生成后检查差异。这样字段和枚举变更会在编译或 CI 阶段暴露。不过生成类型只约束静态代码，网络错误和服务端异常仍由 HTTP 层和集成测试处理。

## 学习卡 018：移动端令牌为什么要分层保存？

日期：2026-07-15

### 业务问题

Access Token 使用频繁但有效期短，Refresh Token 有效期长且泄漏影响更大。如果全部放在普通异步存储中，设备备份、调试或明文落盘会扩大风险；如果每次请求都读取安全存储，又会增加复杂度和延迟。

### 最终方案

Access Token 只保存在进程内存，Refresh Token 和最小用户会话使用 Expo SecureStore。应用恢复时用 Refresh Token 换取新令牌；断网时保留“离线已认证”状态，允许访问本账号本地数据。多个请求同时收到 401 时共享同一个刷新 Promise，避免同一个一次性 Refresh Token 被并发轮换多次。

### 遇到的问题与取舍

刷新令牌轮换存在客户端崩溃窗口：服务端已经返回新令牌，但客户端尚未持久化时崩溃，旧令牌再次使用会触发重放保护并要求重新登录。这是安全性与可用性的取舍，后续可通过短暂宽限窗口和设备绑定进一步优化。

### 面试回答模板

> 我的 Access Token 只放内存，降低长期落盘风险；Refresh Token 放系统安全存储，用于冷启动恢复。401 刷新使用 single-flight，同一时刻只有一个刷新请求，其他请求等待结果，防止轮换令牌被自己并发重放。离线时应用仍可读取当前账号的 SQLite 数据，但需要云端鉴权的请求会等待网络恢复。

## 学习卡 019：Transactional Outbox 如何保证离线写入不丢失？

日期：2026-07-15

### 业务问题

移动端保存一条饮食记录时，不能先写 SQLite 再“尽力发送”网络请求。若 App 在两步之间崩溃，本地数据存在但同步动作永久丢失；反过来先请求云端，也无法保证本地落库成功。

### 最终方案

本地记录变更和 `outbox_events` 事件在同一个 SQLite 排他事务中提交。后台 Worker 抢占事件后向服务端发送，成功才删除事件；网络错误指数退避，进程中断留下的 processing 事件会被恢复，409/422 则进入 blocked 状态等待人工解决。连续编辑会合并尚未发送的事件，创建后立即删除会直接取消无意义的网络操作。

### 取舍

Outbox 保证的是“本地业务变更和待发送意图一起持久化”，不是端到端恰好一次。网络超时仍会导致重复发送，所以服务端还必须用稳定 `client_id` 和唯一约束实现幂等。当前只完成上行同步，云端拉取与冲突解决界面仍是下一阶段。

### 面试回答模板

> 我把本地写入与 Outbox 事件放进同一个 SQLite 事务，因此不会出现数据写成了但同步意图丢失的崩溃窗口。Worker 采用抢占、重试、指数退避和中断恢复；服务端再用 client_id 幂等，因为 Outbox 只能做到至少一次投递，不能单独保证恰好一次。

## 学习卡 020：登录功能为什么会暴露本地多账号数据泄漏？

日期：2026-07-15

### 遇到的问题与定位过程

原项目是单机单用户设计，`food_logs` 和 `user_profile` 没有所有者字段。加入登录后，如果用户 A 退出、用户 B 登录，旧查询会直接展示同一个 SQLite 中 A 的记录。这不是服务端 IDOR，却是同一设备上的本地账号隔离漏洞。

### 最终方案

SQLite v2 增加 `owner_user_id`，所有读取、更新、删除、统计、导出和 Outbox 查询都强制按当前账号过滤。第一个登录账号在事务中认领旧版本的无主数据，之后切换账号不会再次认领。退出登录时清空内存中的活动账号。

### 测试与验证

测试创建两个账号的数据，验证直接读取、日期列表、统计和导出都不会跨账号；迁移失败测试验证 v2 不会留下半升级状态。

### 面试回答模板

> 接入认证后我发现，服务端隔离正确不代表本地就安全。旧 SQLite 是单用户模型，切换账号会看到上一个账号的数据。我增加 owner_user_id，并把所有 Repository、统计、导出和 Outbox 都改为强制账号作用域；首个账号只认领一次历史无主数据，并用双账号测试验证隔离。

## 学习卡 022：为什么增量同步不能只依赖 `updated_at`？

日期：2026-07-15

### 业务问题

按 `updated_at > last_time` 拉取看似简单，但数据库时间精度、同一时间戳内多条记录、分页边界和服务器时钟都会造成重复或遗漏。更关键的是，被物理删除的记录已经没有 `updated_at` 可查询。

### 最终方案

每次业务变更追加一个不可变事件，使用数据库生成的单调递增 ID 作为游标。客户端按 `id > cursor ORDER BY id` 拉取，删除以 tombstone 表示。游标只是进度，不是权限；查询仍必须绑定当前用户。

### 面试回答模板

> 更新时间适合展示，不适合单独承担可靠同步游标。我使用单调递增变更 ID，并为删除保留 tombstone，解决相同时间戳、分页边界和物理删除不可见问题。接口仍按 user_id 过滤，不能把难猜的 cursor 当鉴权。

## 学习卡 023：为什么服务端也需要 Transactional Change Log？

日期：2026-07-15

### 业务问题

如果先提交 `food_logs`，再写 `sync_changes`，进程可能在两步之间崩溃，导致业务数据已经改变但其他设备永远收不到通知。先写事件也可能产生不存在的业务变化。

### 最终方案

新增、更新、删除和 `sync_changes` 在同一个 SQLAlchemy 数据库事务中提交。upsert 事件保存当时的完整快照，删除事件保留 ID、client_id 和版本。即使记录后来再次更新或删除，旧分页仍可重放。

### 面试回答模板

> 移动端 Outbox 保证本地修改不丢，服务端 Change Log 保证云端修改可被其他设备观察。两者都必须与业务写入同事务，否则崩溃窗口会产生永久漏同步。我的 upsert 事件保存不可变快照，delete 使用 tombstone。

## 学习卡 024：为什么应用一页变更和推进游标必须原子化？

日期：2026-07-15

### 业务问题

如果先推进游标、再写本地数据，崩溃后这页永远不会重拉；如果先逐条提交再晚些推进游标，崩溃后会重复应用整页，要求每条合并都绝对幂等。

### 最终方案

SQLite 使用独占事务应用整页 upsert/delete/冲突记录，全部成功后才更新该账号的游标。任意 SQL 失败会回滚整页。服务端响应同时包含 `next_cursor` 和 `has_more`，客户端检测游标不前进以避免无限循环。

### 面试回答模板

> 游标代表“此前所有变化已落地”，所以它必须和这一页的本地合并同事务提交。我不会先保存 cursor；整页失败就回滚，下次从旧 cursor 重拉。同时检测 has_more 时 cursor 是否推进，避免服务端异常导致死循环。

## 学习卡 025：多设备冲突为什么第一版选择整条记录二选一？

日期：2026-07-15

### 业务问题

本机基于 version 1 编辑时，另一设备可能已把云端更新到 version 2 或删除。直接覆盖会静默丢失一方数据，无限重试同一个旧版本也永远不会成功。

### 最终方案

拉取器发现本地存在 Outbox 且远端更高版本时，保留本地记录、将事件标记 blocked，并保存远端快照。用户可使用云端版本，或保留本机并把 expected version 更新到远端版本后重试；远端已删除时，保留本机会转成一次新建。

### 取舍

字段级合并可能把“份量”和“营养快照”等互相依赖字段组合成从未存在过的状态。饮食记录较小且冲突低频，整条二选一更容易解释和验证；后续可对备注等独立字段提供选择性合并。

### 面试回答模板

> 我没有使用 last-write-wins，因为它会静默丢数据。第一版把冲突持久化并让用户选择本机或云端；保留本机时基于最新版本重试。整条二选一虽然不如字段级合并精细，但避免营养字段被错误拼接，适合低频小记录场景。

## 学习卡 026：数据同步成功为什么界面仍可能看起来没变化？

日期：2026-07-15

### 遇到的问题与定位过程

后台 Worker 已经把云端记录写入 SQLite，但首页只在路由获得焦点时查询数据。用户停留在首页、App 从后台恢复时，路由焦点没有重新变化，因此界面继续显示旧状态。

### 最终方案

认证上下文在同步完成后更新 `lastSyncAt`，首页和统计页订阅该信号并重新读取 SQLite。同步服务不直接修改页面状态，仍保持“SQLite 是 UI 的本地事实来源”。

### 面试回答模板

> 同步完成不等于 React 页面自动知道数据库变了。我没有让同步层直接操作多个页面，而是在 Context 发布 lastSyncAt 失效信号，页面收到后重新查询 SQLite。这样数据流仍是服务写库、UI 读库，职责更清晰。

## 学习卡 027：离线认证状态为什么必须设计“恢复”和“失效”出口？

日期：2026-07-15

### 遇到的问题与定位过程

应用离线启动后进入 `offline`，但自动同步副作用最初只监听 `authenticated`。即使网络恢复，应用也不会主动刷新令牌；另一方面，如果同步层把 401 当成普通网络失败吞掉，已被撤销的会话仍会停留在离线界面。

### 最终方案

`offline` 和 `authenticated` 都注册前台与定时同步。一次完整云端拉取成功后转回 authenticated；不可恢复的 401 不在同步层吞掉，而是由认证上下文清除本地活动账号和凭证并跳转登录。网络错误和 5xx 仍保留离线数据并等待重试。

### 面试回答模板

> 离线不是认证状态机的终点。我的离线状态有两个出口：网络恢复并完成鉴权后回到 authenticated；服务端明确返回 401 时清凭证回到 unauthenticated。NetworkError/5xx 可以重试，401 不能伪装成普通弱网，否则会形成幽灵登录状态。

## 学习卡 028：为什么“安装了 Docker”不等于开发环境已经可用？

日期：2026-07-15

### 遇到的问题与定位过程

Docker Desktop 安装成功后，CLI 和 Engine 均可启动，但首次 `docker compose up` 报错找不到 `docker-credential-desktop`。原因不是镜像或 Compose，而是 Codex 进程在安装前启动，仍持有旧 PATH；Docker bin 已写入系统 PATH，却没有进入当前进程环境。

### 面试回答模板

> 我把“工具安装”和“系统可用”分开验收。Docker 安装后曾因旧进程 PATH 找不到 credential helper，我通过确认安装目录和系统 PATH 定位，并为当前会话补路径。最终用容器健康状态、数据库迁移版本、Redis PONG 和真实 API 业务链路证明环境可用，而不是只展示 docker --version。

## 学习卡 029：并发正确性为什么必须在真实 PostgreSQL 上验证？

日期：2026-07-17

### 业务问题

默认 API 测试使用内存 SQLite，速度快但无法证明 PostgreSQL 的唯一约束竞争、条件 UPDATE 和 `SELECT ... FOR UPDATE` 行锁行为。顺序请求全部通过，也可能在两个请求同时进入时产生重复记录或双刷新。

### 最终方案

增加默认跳过的 opt-in 集成测试，只有设置 `NUTRIPILOT_POSTGRES_E2E=1` 时才连接 Docker API。测试使用独立随机账号，同时发出两个请求：同 `client_id` 新增得到 201/200 且资源 ID 相同；同 expected version 更新得到 200/409 且版本只加一次；同 Refresh Token 刷新得到 200/401，胜出的新令牌也因重放检测被撤销。

### 遇到的问题与取舍

不能把 Docker 设为默认测试的隐式依赖，否则没有容器的开发者和普通 CI 会无故失败。因此默认套件显示 29 passed、3 skipped；真实环境命令显式启用后显示 3 passed。测试数据使用 UUID 邮箱隔离，不依赖执行顺序。

### 测试边界

两个竞争请求证明业务语义正确，但不是压力测试。它没有测量 50/100 并发下的吞吐量、P95、连接池耗尽和锁等待，简历中只能写“完成 PostgreSQL 并发正确性集成测试”，不能写“支持高并发”。

### 面试回答模板

> SQLite 单测适合快速回归，但不能替代 PostgreSQL 的行锁和唯一约束竞争。我增加了 opt-in Docker 集成测试，同时触发幂等新增、乐观锁更新和令牌刷新。结果分别为 201/200 同资源、200/409 单版本递增、200/401 并撤销令牌家族。它证明并发语义，不证明高并发性能；后者还需要压测和延迟指标。

## 学习卡 030：性能回归基线为什么不等于系统容量？

日期：2026-07-17

### 业务问题

并发正确性测试通过后，仍缺少可量化的接口延迟和错误率。但如果只运行一次压测并看到约 97.61 req/s，就宣称“系统支持 100 QPS”，面试官会继续追问饱和点、硬件、负载模型和生产网络，此时结论无法成立。

### 最终方案

把第一次压测定义为“固定环境下的回归基线”。使用 k6 同时运行 10 个固定读 VU 和每秒 5 次固定写入到达率，持续 30 秒；设置错误率、检查通过率和分接口 P95 阈值，并提交脚本、环境说明、原始 JSON 与局限性。结果为 2,950 个 HTTP 请求、错误率 0%，三个接口 P95 均小于 40 ms。

### 重难点与取舍

`constant-vus` 固定并发用户数，系统变慢时每秒完成的迭代会减少；`constant-arrival-rate` 固定请求到达节奏，系统变慢时需要更多 VU 承接请求，更适合表达稳定写入流量。吞吐量是当前脚本、数据量、硬件和持续时间共同产生的结果，不是脱离上下文的系统属性。

最大值约 310 ms 而 P95 小于 40 ms，并不矛盾：P95 表示 95% 请求不超过该值，最大值只代表最慢的单个样本。回归门禁适合使用 P95 和错误率，但长尾仍需要 P99、慢查询和资源指标定位。

### 测试边界

本轮没有逐级加压直到失败，也没有采集压测期间 CPU、连接池和锁等待，因此只能写“建立 PostgreSQL API 性能基线”，不能写“最大吞吐 100 QPS”或“支持高并发”。

### 面试回答模板

> 我把性能基线和容量测试分开。基线在固定环境与固定负载下用于发现版本退化；容量测试则要逐级加压，找到错误率或延迟越过 SLO 时的饱和点。本轮 97.61 req/s 是特定混合场景的观测吞吐，不是系统上限，所以我同时保留了负载模型、P95、错误率、硬件和原始结果。

## 学习卡 031：为什么同一套 Expo 代码不能默认在 Web 上直接运行？

日期：2026-07-17

### 遇到的问题与定位过程

为了在电脑上简单体验 App，第一次执行 `expo start --web` 后页面一直停在加载状态。Metro 日志显示无法解析 `wa-sqlite.wasm`；补上 WASM 后，浏览器还需要 COOP/COEP 响应头才能使用 `SharedArrayBuffer`。登录请求随后被后端 CORS 拦截；CORS 修复后，认证 API 已返回 200/201，但界面仍提示失败。继续检查构建产物后发现 `withExclusiveTransactionAsync` 在 Web 实现中会直接抛出“不支持”的错误。

### 最终方案

- Metro 把 `wasm` 加入资产扩展，静态构建包含 SQLite Worker 和约 618 KB 的 WASM 文件。
- 增加本地静态预览服务器，为 HTML、JS、Worker 和 WASM 统一返回 COOP/COEP 头。
- Docker API 只允许 `localhost/127.0.0.1` 的 8081、8082 开发源，不使用宽泛的 `*`。
- 移动端会话继续使用 SecureStore；Web 只使用当前标签页 `sessionStorage`，关闭标签页即清除，避免把长期 Refresh Token 永久放入 `localStorage`。
- 新增事务适配器：Android/iOS 保留独占事务，Web 使用普通异步事务，并用两个单元测试固定分支行为。

### 取舍与风险

Web 的普通事务不具备移动端独占事务相同的并发隔离能力，因此浏览器预览适合演示和功能测试，不应据此宣称多标签页高并发写入已经可靠。`sessionStorage` 仍可被同源 XSS 读取，只是比持久化 `localStorage` 缩短了暴露时间；生产 Web 认证更适合评估 HttpOnly、Secure、SameSite Cookie。

### 测试与验证

在浏览器中完成测试账号登录，添加“香蕉 1 根”，首页和统计页均显示 107 kcal。手动同步后 API 日志出现 `POST /api/v1/logs 201`，随后使用新游标拉取变更。前端 11 个套件、35 个测试全部通过，Web 静态构建成功。

### 面试回答模板

> React Native 组件可以跨平台，但原生能力不一定等价。Expo SQLite 的 Web 版依赖 WASM、Worker 和跨源隔离头，SecureStore 在 Web 不可用，独占事务也只支持原生平台。我通过构建日志和 API 日志逐层定位，把差异收敛到会话存储和事务适配器，并用严格 CORS、静态预览服务器和分支测试验证，而不是到处写平台判断。

## 学习卡 032：为什么通用奶基会错误地出现在美式和水果茶中？

日期：2026-07-17

### 业务问题

原查询把“品牌单品选项”和“通用选项”直接合并。这样复用性很好，但美式、纯果汁和多数水果茶也会得到全脂牛奶、燕麦奶、椰奶，数据层虽然返回了合法行，业务语义却不成立。

也可以在页面根据饮品名称包含“美式”“果茶”来隐藏奶基，但名称规则脆弱，新增产品、别名和多语言后很容易失效。把规则放在目录数据中后，UI 只负责展示，业务约束可以单测。

### 测试与验证

### 面试回答模板

> 原来的 fallback 查询把复用和业务规则混在一起，导致美式也能选牛奶。我没有在 UI 里按名称打补丁，而是把糖度和奶基建模成精确规则优先的互斥配置，通用项只在单品没有声明时回退。这样规则位于数据访问边界，可测试，也方便菜单扩展。

## 学习卡 033：个性化营养目标为什么必须展示计算过程和适用边界？

日期：2026-07-17

### 业务问题

项目原本已经收集性别、年龄、身高、体重、活动量和目标，也会计算每日目标，但用户只能看到最终数字。未填写资料时首页还会静默使用 2000 kcal 等通用值，用户无法判断数字来自个人资料还是默认值。

### 最终方案

### 适用边界

Mifflin 原始研究是健康成年人样本，公式输出是估算而非直接测量；活动等级也来自用户主观选择。因此当前 UI 限定 18—100 岁，并明确不替代医生或营养师。孕期、哺乳期、未成年人、慢性病和专业运动员需要独立模型，不应直接复用当前公式。

### 测试与验证

计算器测试除最终营养目标外，新增 BMR、TDEE 和 BMI 的固定输入断言，防止重构后公式系数或单位被意外改变。

### 面试回答模板

> 个性化不是多收几个字段，而是让字段真正进入可解释算法。我展示 BMR、活动调整后的 TDEE 和目标热量，并区分“个体估算目标”和“公共健康上限”。同时明确成年人适用范围和估算误差，避免把生活记录功能包装成医疗建议。

## 学习卡 034：为什么 AI 不能直接生成最终营养值并写入记录？

日期：2026-07-17

### 业务问题

自然语言模型擅长从“午餐吃了200克鸡胸肉和一碗米饭”中提取食物、数量和餐次，但它可能把不存在的营养数值说得很确定。如果把模型 JSON 直接写入正式记录，Schema 合法只能证明字段形状正确，不能证明事实正确。

### 最终方案

服务端 Provider 只返回食物名称、标准化名称、数量、单位、餐次、置信度和证据，不返回最终 kcal。客户端再用本地种子食品库精确匹配，并通过确定性换算计算营养值；匹配失败或单位无法换算时禁止保存。页面明确展示置信度和待复核原因，只有用户点击确认后才调用本地 Repository。

### 遇到的问题与定位过程

首版保存逻辑逐条调用 `addLog`，如果第二条写入失败，第一条已经存在，会产生用户以为“整份草稿失败”但实际只保存一部分的问题。最终新增 `addLogs`，把所有饮食记录及其 Outbox 事件放进同一个 SQLite 写事务，保证整批成功或整批回滚。

### 测试与验证

后端接口测试覆盖鉴权、结构化多实体结果、缺失数量警告和未知食物不编造；前端测试覆盖份量换算、目录匹配、未知实体拒绝生成营养值，以及多条记录只开启一次写事务。

### 面试回答模板

> 我把 AI 定位为语义解析器，而不是事实数据库。模型只提取实体和份量，所有输出先经过 Pydantic Schema；营养值再从受控食品目录通过确定性算法计算。未知实体不会补一个“看起来合理”的数值，必须转手动流程。最终草稿还需要用户确认，多条记录和 Outbox 在同一事务写入，因此 Schema、事实来源、人机确认和事务一致性分别由不同层负责。

## 学习卡 035：为什么先实现规则型 Provider，而不是一开始就依赖真实大模型？

日期：2026-07-17

### 原有方案及限制

如果页面、业务编排、数据契约和模型 API 同时开发，网络错误、密钥、Prompt 波动和 UI Bug 会混在一起，很难判断失败在哪一层，也无法稳定运行 CI。

### 最终方案

先定义异步 `FoodTextProvider` 协议和固定 Pydantic 输出，规则型 Provider 实现同一接口，支持常见中文食物、阿拉伯数字、部分中文量词与餐次识别。它不是用来冒充 AI 效果，而是一个可复现的开发替身，用于打通鉴权、API、客户端、实体解析、营养计算和确认写入。后续真实模型 Provider 只替换语义提取层。

### 替代方案及取舍

可以直接 Mock HTTP 响应，但 Mock 只能验证固定样本，无法在浏览器中交互演示。规则 Provider 能提供有限但真实可运行的闭环；代价是语义覆盖窄，因此 UI 会显示“本地演示 Provider”，README 也明确尚未接入真实模型。

### 面试回答模板

> 我先用确定性 Provider 建立端到端契约测试，让业务闭环不依赖模型密钥和网络。Provider 接口隔离了厂商 SDK，Pydantic 固定输出边界。这样接入真实模型时，主要新增 Prompt、结构化调用、超时和观测，不需要重写页面和数据层。规则 Provider 同时可以保留为降级方案，但我不会把它的效果冒充成大模型能力。

## 学习卡 036：为什么未登录页面会触发账号数据库读取？

## 学习卡 037：真实模型接入为什么不能只有一次 HTTP 请求？

日期：2026-07-17

### 业务问题

模型服务可能出现超时、限流和短暂的 5xx。如果把这些错误直接暴露给用户，记录入口会变得不稳定；但对所有错误无限重试又会放大流量、延迟和费用。

### 最终方案

服务端实现 OpenAI Responses Provider，并让它返回统一的实体和 Token 用量。编排层最多尝试两次，采用短指数退避；只重试超时、网络错误、408/409/429 和 5xx。普通 4xx、空响应与 Schema 校验失败不会重试，因为相同请求大概率仍会失败。真实 Provider 最终失败后切换规则 Provider，并在响应中明确标记 `fallback_used`，提醒用户重点核对。

模型选择也按任务而不是按“最大参数”决定：当前工作是高频结构化抽取，默认配置使用面向提取与严格延迟场景的 `gpt-5.6-luna`；模型名仍是环境配置，便于评测后替换。Prompt 明确禁止生成营养值，输出还要经过 Pydantic 严格校验。

### 替代方案及取舍

无限重试会形成重试风暴；对 Schema 错误重试会浪费 Token；完全不降级会让核心记录入口依赖外部服务。当前还没有实现熔断器，因此路线图只把超时、有限重试和规则降级标记为完成，熔断留到有连续失败指标后再做。

### 测试与验证

使用 HTTP Mock 验证 Responses 请求、严格 JSON Schema、Token 解析、429 可重试和非法输出拒绝；使用 Fake Provider 验证“重试后成功”“耗尽后降级”和“不可重试错误直接降级”。没有 API Key 时不声称完成真实公网调用。

### 面试回答模板

> 我把模型调用分成 Provider 和编排层。Provider 负责协议与结构校验，编排层负责有限重试和规则降级。只有超时、限流和服务端错误可重试，Schema 错误不会盲目重试；两次失败后返回带降级标记的规则结果，核心记录功能仍可用。当前未实现熔断，所以我不会把有限重试包装成完整容错体系。

## 学习卡 038：AI 调用日志为什么不能直接保存原始 Prompt 和“估算价格”？

日期：2026-07-17

### 业务问题

没有调用日志就无法回答成功率、降级率、延迟、Token 和成本；但饮食文本可能包含健康与生活信息，直接保存原文扩大了隐私风险。同时模型价格会变化，硬编码一个未经确认的价格会产生虚假成本数据。

### 最终方案

新增按用户隔离的 `ai_call_logs`：记录 Provider、模型、状态、是否降级、耗时、尝试次数、Token、错误码和可选成本。输入只保存 SHA-256 指纹，用于判断重复请求，不保存原始文本。`GET /api/v1/ai/metrics` 聚合成功、降级、失败、平均延迟、Token 和成本。只有部署环境显式配置输入/输出单价时才计算成本，否则返回未定价调用数，不猜价格。

### 取舍与边界

哈希不是加密，也不能恢复原文；低熵文本仍可能被字典猜测，因此它只用于去除明文暴露，不应当被描述为匿名化。当前成本没有保存“价格表版本”，适合开发监控；生产化还应记录计价版本、币种和缓存 Token 等更细的计量字段。

### 面试回答模板

> 可观测性与隐私要同时设计。我记录请求状态、延迟、尝试次数、模型和 Token，但不保存饮食原文，只保存 SHA-256 指纹。成本只有在价格作为部署配置明确提供时才估算，未配置就标记为 unpriced，避免用过期价格制造看似精确的数据。下一步会增加价格版本和 P50/P95 指标。

## 学习卡 039：为什么“让用户在 App 中填写 API Key”仍不能把 Key 保存在客户端？

日期：2026-07-18

### 业务问题

用户希望配置自己的 OpenAI API Key，以便真实调用模型。最直观的方案是把 Key 存进移动端 SecureStore 或 Web `sessionStorage`，再随每次分析请求发送。但客户端环境无法被服务端控制：移动包可能被逆向，浏览器存储可能被 XSS 读取，调试代理也可能捕获请求。SecureStore 能改善静态存储，却不能消除运行时暴露。

### 最终方案

客户端设置页只在保存时提交一次 Key，不写入 SQLite、SecureStore 或前端持久化状态。后端认证用户后，使用服务端主密钥派生 256 位密钥，通过 AES-GCM 和随机 96 位 nonce 加密；Associated Data 绑定 `user_id` 和格式版本，因此把密文复制给另一个账号会校验失败。数据库只保存密文与末四位，GET 接口只返回 `configured`、掩码和更新时间。

AI 分析时，后端按当前用户读取并临时解密；用户凭证优先于服务端默认 Provider。Key 不可用时走已有规则降级。主密钥只由部署环境提供，生产环境拒绝开发默认值；正式网络必须使用 HTTPS，避免传输阶段泄露。

### 取舍与边界

这不是端到端加密：后端为了调用模型必须能解密，所以服务器进程和有权访问主密钥的管理员仍在信任边界内。AES-GCM 保护数据库泄露和密文篡改，但不能替代主密钥管理、HTTPS、最小权限、日志脱敏、费用限额和 Key 轮换。主密钥丢失后旧凭证不可恢复，轮换还需要未来增加密钥版本和重加密流程。

### 测试与验证

单元测试覆盖加解密往返、错误用户、错误主密钥和密文篡改；API 测试验证响应不含明文、数据库密文不含明文、账号隔离、删除幂等，以及配置凭证后确实选择 OpenAI Provider。测试使用假 Key 和 Mock Provider，不产生真实费用。

### 面试回答模板

> 用户自带 Key 不代表可以把 Key 长期放在 App 中。我让客户端只提交一次，服务端用 AES-GCM 加密落库，AAD 绑定用户 ID，读取接口只返回末四位。模型调用时服务端临时解密，因此它防的是数据库泄露和密文篡改，不是端到端加密；生产上仍要保护主密钥、启用 HTTPS、限制日志权限并设计密钥轮换。

## 学习卡 040：为什么 AI 功能必须有固定评测集，而不是手动试几个句子？

日期：2026-07-19

### 业务问题

Prompt 和模型输出具有概率性。只在页面里试“午餐200克鸡胸肉”这类成功样例，很容易在修改 Prompt 后提高某一题、同时破坏否定句、多实体或目录外食物，却没有证据发现回归。Schema 合法也只证明字段形状正确，不能证明语义正确。

### 原有方案及限制

原来只有规则 Provider 单测和 OpenAI HTTP Mock：它们能证明接口契约、重试与降级正确，但不能回答“整体识别效果是多少”“新 Prompt 是否更好”“失败集中在哪里”。调用日志记录线上运行状态，也没有 Ground Truth，不能替代离线评测。

### 最终方案

建立 `food-text-zh-cn-v1.0.0` 脱敏数据集，26 条输入包含 32 个期望实体，并故意覆盖未知食品、品牌饮品、否定、未来意图和无食物文本。评测器复用正式 `FoodTextProvider` 接口，计算实体 Precision、Recall、F1，以及名称匹配后的数量/单位/餐次准确率、整例完全正确率、Schema、请求成功率、P50/P95、Token 和可选成本。报告同时保存数据集、Provider、实际模型和 Prompt 版本。

规则 Provider 首版得到 TP/FP/FN = 26/6/6，P/R/F1 均为 81.25%，Case Exact Match 为 65.38%。数值不追求好看，重点是能从逐例报告定位三类真实缺陷，并把当前结果固化为最低门槛。

### 遇到的问题与定位过程

最容易写错的是 Schema 合法率分母。若把网络超时也算成 Schema 不合法，就无法区分“模型没有返回”与“模型返回但格式错误”。最终将请求成功率单独统计；Schema 合法率只比较强类型成功结果与 Schema/空响应错误，网络错误标记为不可评估。

第二个问题是指标重复惩罚。如果食物名称没匹配，数量也必然无法对齐；把它同时算作名称、数量、单位和餐次四次错误，会让字段指标失去解释力。因此字段准确率只在名称 TP 上计算，整例完全正确率再负责衡量端到端结果。

### 替代方案及取舍

可以直接使用供应商托管 Evals，但当前项目需要无 Key、无费用地在本地和 CI 中运行规则基线，而且现有 Provider 已经统一了模型入口。因此首版选择本地 Pydantic 评测器；后续样本和团队扩大后，可把同一 Ground Truth 同步到托管 Evals。严格标准名匹配解释简单，但会惩罚合理同义词；未来只能增加受控别名，不能用宽松模糊匹配掩盖错误。

### 测试与验证

Pytest 固定验证 26 条样本的 TP/FP/FN 和主要质量指标；第二组测试专门验证 Schema 错误计入 Schema 分母、网络错误只影响请求成功率。CLI 用 JSON 基线做回归门禁，并要求真实 OpenAI 评测同时提供环境变量 Key 和 `--allow-paid-api`，避免误调用和 Key 进入命令历史。本轮后端全量结果为 52 个通过、3 个环境相关测试跳过。

### 面试回答模板

> 我没有用几条演示输入评价模型，而是建立了版本化 Ground Truth。评测复用生产 Provider，分实体 P/R/F1、字段准确率和整例完全正确率，同时记录 Schema、可用性、延迟、Token、成本、模型和 Prompt 版本。首版规则降级在 26 条样本上 F1 为 81.25%，失败主要是目录外食品和否定语义。这个数字只是回归基线，不是生产准确率；真实模型和用户修改率需要分别采集。

## 学习卡 041：Tool Calling 为什么不是“让模型直接访问数据库”？

日期：2026-07-19

### 业务问题

饮食助手必须根据用户真实记录回答，但模型本身不知道数据库状态。若把整库数据塞进 Prompt，既浪费 Token，又扩大隐私暴露；若允许模型生成任意 SQL，则会引入越权、写操作和不可控查询风险。只做一个聊天 UI 也无法证明结论来自哪里。

### 原有方案及限制

已有 AI 文本抽取只处理用户本次输入，不读取历史数据。每日汇总和周趋势已有确定性查询能力，但前端只能分别打开页面查看，模型无法按问题选择数据。规则助手若直接拼接数据库结果可以运行，却不能验证真实 Responses Function Calling 协议，也难以扩展多个受控能力。

### 最终方案

实现三个白名单只读工具：每日汇总、固定七天趋势和食品搜索。模型只能填写日期、查询词等业务参数，`user_id` 由 JWT 上下文在服务端注入，完全不进入工具 Schema。OpenAI 首轮强制调用工具，后端用 Pydantic 校验参数、执行用户隔离查询，再用相同 `call_id` 回传 `function_call_output`；最终响应必须包含工具证据。无 Key 或模型异常时，本地规则助手复用同一工具执行器，避免降级路径绕过权限边界。

### 遇到的问题与定位过程

第一个难点是 Function Calling 是多轮协议，不是模型直接返回答案。应用必须保留模型原始输出项，并把每个工具结果以相同 `call_id` 送回下一轮，否则无法关联调用。测试因此模拟“先 function_call、再最终文本”的两次 Responses 请求，而不是只 Mock 最终答案。

第二个难点是“零”的语义。七天范围内没有日志不等于用户没有吃东西，所以查询固定补齐七个日期，同时返回 `days_with_records`；回答明确写“记录可能低估实际摄入”。代码复查时还发现首版用 `kcal > 0` 计算记录天数，会把零热量饮品误判成缺失日；最终改为使用分组 SQL 实际返回的日期数，并加入零热量记录回归用例。平均值按完整七天计算并说明分母，防止指标看似准确但含义模糊。

第三个难点是防止工具循环失控。首版关闭并行 Tool Calls，每轮最多一个调用，总计最多三轮；超限交给已有 Provider 错误与规则降级处理。当前需求只需单轮问答，因此没有为了“像 Agent”而提前加入写工具或长期记忆。

### 替代方案及取舍

可以用 RAG 检索文档，但用户饮食记录是结构化、强权限、需要准确聚合的数据，SQL 工具比向量相似度更合适。也可以把所有统计预先放进系统 Prompt，但数据会过期且每次占用上下文。当前证据保存摘要而非完整原始工具 JSON，界面可读性更好；若未来需要审计级复现，应在受控存储中保存脱敏的工具输入输出版本。

### 测试与验证

HTTP Mock 覆盖严格工具 Schema、禁用并行调用、`call_id` 回传和 Token 汇总；API 集成测试覆盖双用户日志隔离、私有食品隔离、固定七天窗口和无效 Key 降级。Expo Web 中实际查询了每日汇总与七天趋势，页面均显示对应证据卡。本轮全量结果为后端 58 个通过、3 个环境相关跳过、覆盖率 81%，前端 15 个套件/45 个测试通过。

### 面试回答模板

> 我没有让模型直接查数据库，而是提供三个白名单只读工具。工具参数使用严格 Schema，但权限不交给模型：用户 ID 来自 JWT 并由服务端注入，所有查询在 SQL 层绑定当前账号。Responses 返回 function_call 后，服务端执行工具并用同一 call_id 回传结果，最终回答同时展示证据。首轮必须调用工具、最多三轮，失败回退到复用同一工具层的本地助手。这样模型负责语言理解和表达，确定性代码负责权限、查询和数值。

### 可继续追问的问题

- 严格 JSON Schema 为什么不能替代鉴权？
- `tool_choice=required` 和 `auto` 分别用在哪一轮？
- 如何保证本地降级与 OpenAI 路径的数据权限一致？
- 为什么当前不保存多轮对话？
- 如果未来加入“删除记录”工具，需要增加哪些确认与审计机制？

## 学习卡 042：多轮 AI 对话为什么需要自己设计状态、裁剪和幂等？

日期：2026-07-20

### 业务问题

单轮助手无法理解“那最近七天呢”之类追问，刷新页面后回答也会消失。最简单的做法是把全部历史塞给模型或只保存供应商的 `previous_response_id`，但前者会让 Token 和延迟无界增长，后者会把会话所有权、删除和供应商切换绑定到外部状态。移动网络还可能出现服务端成功、客户端超时的情况，直接重试会重复调用和重复消息。

### 原有方案及限制

首版 `/assistant:answer` 只接收当前问题和参考日期，回答带工具证据但不持久化。AI 调用日志只保存问题 SHA-256，适合可观测性，却无法恢复用户可见对话。它也不能替代消息库，因为哈希不可逆，且没有角色、顺序和回答元数据。

### 最终方案

新增 PostgreSQL v7 的 `assistant_conversations` 和 `assistant_messages`。所有会话操作先用 JWT 获得当前用户，再以 `conversation_id + user_id` 查询；消息保存角色、顺序、正文、参考日期、工具证据、Provider、模型、Prompt 版本、Token、延迟和调用追踪。页面支持新建、切换、刷新恢复和删除对话。

每轮只读取最近 8 条消息和最多 6,000 字符，历史用于理解省略表达；Prompt 升级到 v1.1.0，要求所有营养事实重新调用当前工具。OpenAI 请求保持 `store: false`，应用手动传入交替的用户/助手消息。本地规则降级也接收相同上下文接口，但仍通过同一只读工具层查询事实。

客户端生成 `client_message_id`，网络结果不确定时保留同一会话、问题和 ID；服务端唯一约束确保完成后的重试直接返回原结果。同一 ID 配不同正文或参考日期返回 409，避免把两条业务消息错误合并。

### 遇到的问题与定位过程

第一个问题是“有唯一键”不等于端到端幂等。前端最初每次点击都生成新 UUID，而且创建会话成功、发送消息超时后没有保留空会话；用户重试仍会产生新会话。最终使用内存中的待发送状态保存会话 ID、问题和消息 ID，只有成功、切换会话或内容变化时才清除或换键，并为该规则增加纯函数测试。

第二个问题是历史事实可能过期。若上一轮回答“今天 520 kcal”，用户随后补录食物，再问“那蛋白质呢”，直接复述历史会错。最终只把历史作为语言语境，并在 Prompt 和首轮 `tool_choice=required` 双重约束下重新查询工具。

第三个问题是消息读取不能无界。模型上下文限制为最近四轮，详情接口最多返回最近 100 条；完整消息总数单独统计。字符裁剪简单可解释，但不等同于 Token 裁剪，真实模型评测后还要改进。

### 替代方案及取舍

Responses API 可以用供应商托管会话或 `previous_response_id` 简化状态，但项目需要本地规则降级、跨 Provider、用户删除和统一证据展示，因此选择应用自管消息。官方建议无状态推理场景保留完整输出项；当前使用无推理强度并只保存可见文本，不保留加密推理项，所以不能声称完整恢复模型内部状态。

分布式并发下，两个实例仍可能同时通过预检查并各自调用一次模型，最终只有一个写入成功。这说明数据库唯一约束保证“消息最终一份”，但不保证“模型调用恰好一次”。进一步优化需要 Redis single-flight、处理中状态和超时恢复。

### 测试与验证

API 测试覆盖连续两轮、顺序、证据、幂等重放、同键异内容冲突、跨用户 404、删除和上下文裁剪；HTTP Mock 验证历史进入 Responses 请求；前端测试验证弱网重试键复用。真实 PostgreSQL 升级到 v7，浏览器完成两轮追问、创建第二会话、切换和刷新恢复，控制台无错误。全量结果为后端 62 个通过、3 个跳过、覆盖率 79%，前端 16 个套件/48 个测试通过。

### 面试回答模板

> 我把对话状态放在自己的 PostgreSQL，而不是完全依赖供应商会话。每条消息带角色、顺序、证据和调用元数据，会话查询按 JWT 用户隔离。模型只读取最近四轮和 6,000 字符，历史用于理解追问，营养事实每轮重新 Tool Calling。客户端消息 ID 配合数据库唯一约束覆盖弱网重试，同键异内容返回 409。这个方案保证消息不重复，但并发模型调用还不是恰好一次，生产化会增加 Redis single-flight 和处理中状态。

### 可继续追问的问题

- 为什么 AI 调用哈希日志不能代替对话消息表？
- 字符裁剪和 Token 裁剪有什么差异？
- 如何处理两个实例同时收到相同幂等键？
- `store: false` 是否意味着数据没有发送给 OpenAI？
- 对话删除后备份中的数据如何处理？

## 学习卡 043：AI 周报为什么要拆成“确定性事实”和“生成式叙事”？

日期：2026-07-21

### 业务问题

周报既要汇总两周日志和个性化目标，又要生成自然、可执行的中文建议。如果把原始日志直接交给模型，让它同时加总、计算环比和写结论，即使返回 JSON 结构正确，也不能保证算术稳定、记录天数语义正确或跨用户权限安全。记录缺失时的 0 还可能被误写成“用户没有吃”。

### 原有方案及限制

已有 `get_weekly_trend` 工具只返回最近七天和基础摘要，适合问答证据，但没有上一周基线、完整度门槛、事实指纹和严格的周报叙事结构。统计页读取本地 SQLite，不能直接证明 AI 使用了服务端当前用户的事实。让页面进入时自动调用模型也会在每次刷新时产生无意费用。

### 最终方案

新增双层管线。事实层以 JWT 用户 ID 查询当前七天和上一七天，固定补齐日期，计算 7 天日均、记录覆盖率、个性化目标和周环比；两周都至少记录四天且上周基数大于零时才返回百分比。规范化事实生成 SHA-256 指纹。叙事层只接收 `WeeklyReportFacts`，OpenAI 使用严格 Structured Outputs 生成标题、总结、最多三条要点和行动；返回后再经过 Pydantic 校验。无 Key 直接用本地规则 Provider，真实模型错误则有限重试后降级。

前端同时展示事实指标和生成文字，明确日均按七天、Provider、降级、Token、延迟、警告和指纹前缀。只有用户点击按钮才调用接口。

### 遇到的问题与定位过程

第一个难点是平均值分母。若只除以已记录天数，三天高热量记录可能看起来比完整七天更“真实”，但两周记录习惯变化会让环比失去可比性；若缺失补零又不提示，则会低估实际摄入。最终固定除以七，并把 `days_with_records` 和低估警告作为一等字段展示。

第二个难点是百分比的可定义性。上周没有记录时不能除以零，也不能把本周数值写成“增长 100%”；当前返回 `null`。两周任一周不足四天也不比较。这个门槛是首版产品规则，不冒充营养学标准。

第三个难点是 Structured Outputs 的边界。严格 Schema 能保证字段形状和类型，却不能保证数字真实；因此模型输出中不包含重新计算的事实对象，数值始终来自后端。模型只负责有限文字，前端的主要指标直接读取 `facts`。

### 替代方案及取舍

可以让模型通过 Tool Calling 自己调用两次周趋势工具，但周报是固定工作流，不需要模型决定查询步骤；直接构造事实更省 Token、更容易测试。也可以持久化每份周报，但首版没有历史周报产品需求，先通过调用日志和事实指纹实现运行追踪，避免为了展示技术而增加表和迁移。需要历史回看、缓存或审计时再设计报告快照和失效策略。

### 测试与验证

API 集成测试覆盖鉴权、双用户隔离、双周窗口、完整度、环比、无效 Key 降级和调用日志；HTTP Mock 覆盖严格 JSON Schema、输入事实、模型版本和 Token；前端纯函数覆盖空环比和降级标签。全量自动化结果为后端 68 个通过、3 个环境相关跳过、覆盖率 78%，前端 17 个套件/51 个测试；Expo Web 生产构建成功。真实 PostgreSQL 冒烟得到当前/上周总量 800/400 kcal、4/7 天、环比 100%、64 位指纹和 trace ID。真实 OpenAI 质量和公网延迟尚未测量，不能用 Mock 结果替代。

### 面试回答模板

## 学习卡 044：结构化日志为什么首先是“数据契约和隐私设计”？

日期：2026-07-22

### 业务问题

应用进入上线阶段后，用户只说“刚才保存失败了”无法定位问题。需要一个能从客户端响应关联到服务端请求的 ID，并记录端点、状态和耗时；同时项目包含 Authorization、用户 API Key、饮食正文和健康资料，日志一旦无边界地收集请求对象，反而会成为新的敏感数据仓库。

### 原有方案及限制

后端只有 Uvicorn 默认 access log，能看到方法、原始 URL 和状态码，但没有统一请求 ID、结构化字段和异常追踪。默认日志把 Query 原样打印，无法安全接入日志平台。未处理异常依赖框架返回，也没有稳定的、可让用户反馈的关联信息。仅仅安装 Sentry SDK 也不够，因为官方集成可能附加 URL、Header 和 JSON 等请求数据。

### 最终方案

实现纯 ASGI 请求中间件：接受通过正则校验的 `X-Request-ID`，否则生成随机 ID，并通过 `ContextVar` 绑定异步请求。每个响应带相同 Header，完成日志只写时间、级别、事件、环境、方法、低基数端点函数、状态和耗时。JSON Formatter 只序列化白名单，Uvicorn access log 被关闭。

统一异常处理器返回通用 500 和 request ID，控制台只记异常类型；Sentry 作为可选能力，只有 DSN 存在时初始化，并关闭默认 PII、本地变量和请求正文，`before_send` 再删除用户、URL、Header、Cookie、Query、Body 和环境，只用已校验 request ID 关联事件。

### 遇到的问题与定位过程

最关键的问题是在 Docker 冒烟时发现：自定义 JSON 日志确实没有 Query，但 Uvicorn 自己仍输出 `?token=must-not-log`。这说明“我的 Formatter 不泄漏”不等于整个进程日志不泄漏。最终关闭框架 access log，由应用的低基数端点日志完整替代，并增加配置测试。这个问题只靠单元测试自定义 Logger 很难发现，是容器级验收的价值。

第二个问题是客户端 request ID 不能盲目信任。攻击者可以发送换行或超长字符串污染日志，因此只接受 8~128 位受限字符，否则重建随机 ID。第三个问题是异常消息可能包含 SQL 参数或用户输入，所以控制台不直接记录 `str(error)`；堆栈交给经过脱敏配置的错误监控。

### 替代方案及取舍

可以直接采用 structlog，但当前字段少，标准库 Logging 加白名单 Formatter 更少依赖，也更容易解释。可以一开始引入完整 OpenTelemetry Collector、Trace 和 Metrics，但项目尚未部署多服务，先建立 request ID 与安全日志契约，后续再接 OTLP。完全不记录路径减少了泄漏和高基数风险，代价是排查时只能看到端点函数；具体资源 ID 应通过受控业务 trace 查询，而不是进入通用日志。

### 测试与验证

测试覆盖合法 ID 复用、非法换行、端点低基数、状态与耗时、统一 500、Sentry request ID 标签、SDK 默认关闭和隐私 scrubber；专门把 Authorization、API Key、Query、Cookie、Body、用户与异常敏感文本放进测试，验证输出不包含它们。本轮后端全量为 75 个通过、3 个环境相关跳过、覆盖率 79%。Docker/PostgreSQL/API 健康，curl 验证响应头为 `docker-final-20260722`，容器 JSON 日志包含相同 ID、端点和 2 ms 耗时，且不包含测试 Query。

### 面试回答模板

> 我把日志当成有隐私边界的数据契约。每个请求校验或生成 X-Request-ID，通过 ContextVar 贯穿异步链路，响应头和 JSON 日志使用同一 ID。日志只输出白名单字段和低基数端点，不记录 URL、Query、Header、Body、IP、用户 ID或异常文本。Docker 验收时我发现 Uvicorn 默认 access log仍会泄漏 Query，于是关闭它并由结构化日志替代。Sentry 默认关闭，启用时关闭 PII、本地变量和正文，再用 before_send 二次清洗。真实告警必须等部署项目和 DSN 后验收，当前不虚构线上效果。

### 可继续追问的问题

- 如何给健康检查日志降噪？

## 学习卡 045：演示数据为什么也是安全与事务问题？

日期：2026-07-22

### 业务问题

面试官不可能先连续记录两周饮食再体验统计和周报，因此项目需要一个登录后立即可讲清主线、且每次演示前能恢复初始状态的账号。共享演示账号同时带来普通数据脚本没有的风险：覆盖真实用户、留下旧登录状态、泄露或消耗 API Key，以及多个表只删除一半造成脏数据。

### 原有方案及限制

最简单的做法是在 README 写一组账号并手工插入几条日志，但数据会随演示逐渐变化，无法复现双周趋势，也不能证明重置是安全的。提交 SQL dump 会绑定 PostgreSQL 结构和密码摘要，应用 Schema 变化时容易漂移。只按固定邮箱判断演示用户也不可靠，可能误删同邮箱的普通账号。

### 最终方案

Alembic v8 给用户增加非空 `is_demo` 标志。CLI 只从环境读取密码，以锚点日期生成一个带资料、58 条双周日志、5 个品牌饮品、2 个私有食品和 58 条同步变更的故事数据集。已有普通账号一律拒绝覆盖；已有演示账号只有显式传入 `--reset-existing` 才重建，生产环境还要额外传入 `--allow-production`。

重置在单个事务中显式删除所有用户从属表，并创建新的随机用户 ID，使旧 JWT subject 找不到用户；Refresh Token 行也被删除。演示用户不能保存 API Key，服务端选择 Provider 时也忽略全局付费 Key，固定走本地规则实现。客户端展示演示标记、隐私提示并禁用 Key 输入。

### 遇到的问题与定位过程

SQLite 单元测试全部通过后，第一次在真实 PostgreSQL 运行 CLI 仍发生 `ForeignKeyViolation`：`food_items.owner_user_id` 指向的用户尚未插入。原因不是事务失效，而是模型只设置外键 ID、没有 ORM relationship，SQLAlchemy 无法从对象关系推断 flush 顺序；SQLite 测试环境又没有以相同方式强制外键，因此没有暴露。

修复是在 `session.add(user)` 后立即 `flush` 用户父记录，再创建资料、食品和日志。`flush` 只是把当前事务中的 SQL 发给数据库，不会提交；后续任一步失败仍能回滚。重建容器后，PostgreSQL v8 种子和重置均通过。另一次接口测试最初得到 422 而非预期 403，是因为故意提交的假 Key 少于 Schema 的 20 字符，校验在鉴权后的业务分支前执行；换成满足输入 Schema 的假值后才正确验证到演示账号 403 策略。

API 冒烟通过后，浏览器首次登录仍显示“先生成个性化目标”，但当天 4 条日志已经出现。由此定位到增量同步只覆盖 `food_logs`，没有把 `/users/me/profile` 写入账号隔离的本地 SQLite。新增资料同步服务：本地缺失时拉取云端，本地时间较新或云端 404 时推送本地，再用服务端时间回写。首页监听 `lastSyncAt` 后自动刷新。这使演示资料真正进入 UI，也补上普通用户跨设备资料同步；当前整对象时间戳 Last-Write-Wins 仍受客户端时钟漂移影响，后续应改为服务端版本号或显式冲突。

### 替代方案及取舍

可以为所有模型补 ORM relationship，让 Unit of Work 自动排序，但这会扩大当前任务范围，且显式外键仍是项目现有风格；一次父记录 flush 更直接。可以保留相同用户 ID 并只删业务数据，但已签发 Access JWT 仍能继续使用，不适合共享账号重置。也可以每位访客克隆独立账号，隔离更好，但需要生命周期、配额和清理任务，留到公开部署阶段。

### 测试与验证

自动化覆盖完整双周事实、重复执行保护、重置后唯一账号与计数、普通账号冲突、生产保护、演示用户凭证和 Provider 策略，以及资料拉取、较新本地资料推送和云端 404 创建。本轮后端 79 个通过、3 个环境相关跳过、综合覆盖率 80%；前端 19 个套件、56 个测试通过，类型检查与零警告 Lint 通过。

Docker/PostgreSQL 验收确认 Alembic 位于 v8，生成和重置后均有 58 条日志、2 个私有食品，两周各 7 个记录日；用户 ID 发生轮换，旧 Access/Refresh Token 都返回 401；周报使用规则 Provider，API Key 写入返回 403。Expo Web 实际登录后，首页显示由云端资料计算的 2023 kcal 目标，“我的”页显示演示标记和完整资料，AI Key 保存按钮禁用。

### 面试回答模板

> 我没有把演示账号当成几条随手插入的数据，而是实现成可复现的运维能力。数据库用 is_demo 明确区分账号，CLI 从环境读取密码，以锚点日期生成完整双周故事；重置必须显式确认，并在单事务中清理所有从属数据。重置会轮换用户 ID、删除 Refresh Token，让旧的两类令牌都失效。共享演示账号禁止保存或使用付费 API Key。SQLite 测试通过后，真实 PostgreSQL 仍暴露了无 relationship 时 flush 顺序导致的外键错误，我通过先 flush 父用户、仍保持单事务回滚解决；浏览器又暴露了日志已同步但资料未同步的链路缺口，因此补了云端资料双向同步。最终用容器 API 和 Expo Web 验证了 58 条记录、个性化目标、双周周报、401 和 403 行为。

## 学习卡 046：限流为什么不只是“计数大于 N 就拒绝”？

日期：2026-07-22

### 业务问题

演示账号的密码必须公开，任何访客都可以高频生成规则周报、创建对话和写入日志。禁用付费 API Key 只消除了模型费用风险，没有限制 CPU、Redis、PostgreSQL 容量，也不能保证面试前数据处于可展示状态。公开 Demo 需要频率限制、资源上限和周期恢复，同时不能把用户输入复制进新的风控数据仓库。

### 原有方案及限制

上一阶段只有手动种子重置和 AI Key 隔离。单进程内存计数器实现简单，但多副本各自计数，重启又会清零；数据库每次写一条请求日志太重。直接按 IP 限流需要正确识别可信反向代理，盲信 `X-Forwarded-For` 可被伪造，保存原始 IP 还增加隐私负担。仅靠定时清库也无法阻止一个周期内的请求洪峰。

### 最终方案

演示用户的写入和 AI 请求分别进入 Redis 桶。Lua 脚本原子执行 `INCR`、首次 `PEXPIRE` 和 `PTTL`，超过阈值返回 429，并把剩余 TTL 转为 `Retry-After`。键只有轮换用户 UUID 和动作类型，不含邮箱、IP、饮食或问题正文。普通用户直接绕过这组演示桶。

创建日志、私有食品、对话和消息前再检查 PostgreSQL 资源数；幂等日志和消息先查已有请求，重放不会被配额错误拒绝。一轮对话会写用户与助手两条消息，因此容量判断必须预留两个位置，而不是只判断当前计数小于上限。

自动重置循环在启动后先等待一个周期。多实例通过 Redis `SET NX EX` 竞争锁，锁值是随机所有权 Token；释放时 Lua 先比较 Token 再删除，避免实例 A 的锁过期并被实例 B 获取后，A 又误删 B 的锁。重置继续复用上一阶段的 PostgreSQL 单事务种子服务。

### 遇到的问题与定位过程

第一个问题是限流测试本身写错了 Redis `eval` 参数位置：调用结构是 `script, numkeys, key, window_ms`，测试误把窗口整数当成键并执行字符串包含判断，产生 `TypeError`。检查真实调用元组后修正为索引 2。这提醒我测试不仅要断言状态码，也要准确理解客户端协议，否则可能验证了错误对象。

第二个边界是消息配额。最初逻辑是 `count < limit` 就允许，但追加一轮会同时落两条消息；当 count=39、limit=40 时会写到 41。最终按资源计算 `required_slots`，消息为 2，其他创建资源为 1。

第三个边界是分布式锁不能只 `DEL key`。锁可能在重置过程中到期并由其他实例重新获取，旧实例结束时直接删除会破坏新锁。因此释放脚本必须比较随机 Token。TTL 仍需覆盖最大任务时间；如果未来重置超过 300 秒，应做续租。

### 替代方案及取舍

可以使用令牌桶或滑动窗口，突发控制和公平性更精细；当前固定 TTL 窗口足以保护低流量作品集，Lua 少依赖、易验证。可以使用 IP+用户双层限流，但可信代理尚未部署，所以先做共享账号总量保护。可以用数据库 advisory lock 实现严格配额，但当前资源上限主要防滥用，Redis 限流与周期重置已降低并发超额影响；文档明确不把它称为硬配额。

开发环境 Redis 故障选择 fail-open，减少本地启动依赖；生产则由 Settings 强制 fail-closed，保护失效时返回 503。`/ready` 仍只依赖 PostgreSQL，因为普通用户和只读 API 可继续服务；Redis 必须由独立探针告警。

### 测试与验证

自动化覆盖阈值内放行、429 与 Retry-After、键不含邮箱、Redis fail-open/fail-closed、普通用户绕过、真实种子日志配额、多实例锁、账号轮换、配置校验，以及写入/AI 路由确实调用保护依赖。本轮后端 88 个通过、3 个环境相关跳过、综合覆盖率 80%；前端 19 个套件、56 个测试继续通过。

Docker/PostgreSQL/Redis 验收把 AI 阈值临时设为 2、日志上限设为 58。三次周报得到 200/200/429，`Retry-After` 为 60；额外日志返回 403；重置首次执行为 true，人工预占锁后第二实例为 false；Redis 键不含邮箱。随后恢复默认开发阈值并确认三个容器健康。真实周期循环尚未在公网多副本连续运行，不能声称已验证长期调度稳定性。

### 面试回答模板

> 我把公开演示账号保护拆成频率、存量和恢复三层。频率层用 Redis Lua 原子完成 INCR、TTL 初始化和剩余时间读取，按轮换用户 UUID 区分 write/AI 桶，返回 429 和 Retry-After；键不含邮箱、IP或正文。存量层限制日志、食品、对话和消息，并让幂等重放先于配额检查。恢复层按周期执行单事务种子重置，多实例用 SET NX EX 抢锁，释放时比较随机 Token，避免误删别人的新锁。生产强制 Redis 故障 fail-closed。真实容器测试得到 200/200/429、配额 403 和第二实例跳过；我也明确说明当前计数后写入仍可能并发超额，公开注册风控尚未完成。

## 学习卡 047：公开登录页背后的安全边界

日期：2026-07-23

### 业务问题

演示账号已经有限流和资源配额，但公开注册仍允许攻击者创建普通账号绕过保护；登录接口也可以针对固定邮箱持续试密码。作品集页面必须既能在本地允许注册，又能在公开部署只提供演示账号，并且不能把原始邮箱复制到 Redis 风控键。

### 原有方案及限制

只在前端删除注册按钮最简单，但攻击者可直接调用 API。只按 IP 限流又需要正确解释反向代理；盲信 `X-Forwarded-For` 可被伪造，直接保存 IP/邮箱还扩大隐私数据范围。普通 SHA-256 也不足，因为邮箱是可枚举的低熵标识符。

### 最终方案

后端新增部署级注册开关，并提供只暴露 `registration_enabled` 的公开配置接口。Expo 登录页读取配置；请求失败时默认隐藏注册。注册路由在密码哈希和数据库写入前返回 403，因此 UI 不是安全边界。

登录和注册复用抽取后的 `RedisRateLimiter`，Lua 原子完成 `INCR`、首次 TTL 和 `PTTL`。邮箱先规范化，再用服务器密钥对版本、动作和邮箱做 HMAC-SHA256；Redis 只保存动作与 64 位摘要。未知和已知邮箱使用同一策略与 401 文案。成功登录删除登录桶，注册桶独立存在。生产启用保护时配置校验强制 fail-closed。

### 遇到的问题与定位过程

第一次完整后端测试失败不是路由逻辑错误，而是测试直接期望输入 `Guard@Example.com` 原样传递。Pydantic `EmailStr` 会把域名规范化为 `Guard@example.com`，说明限流接收的是校验后的 Schema 值；测试改为验证实际契约。

第一次 Docker 验收全部返回 422。服务端日志和响应都指出 JSON 解析失败，原因是 Windows PowerShell 调用原生 `curl.exe` 时正文双引号跨进程边界丢失。改用 PowerShell Hashtable + `ConvertTo-Json` 后，真实结果才是注册 403 和登录 401/401/429。不能把脚本构造错误误判为 API 缺陷。

代码检查还发现测试替身的 `enforce_capacity` 因补丁位置缩进进了 `NoopAuthGuard`。认证专项测试没有覆盖饮食路由，所以起初仍通过；完整测试会暴露 `NoopDemoGuard` 缺方法。修正归属后再运行全套回归，这说明共享 Fixture 的错误可能被局部测试掩盖。

最终审查又发现更隐蔽的事务边界：`login_user` 先提交 Refresh Token，路由随后删除 Redis 失败桶。如果 Redis 在这一步故障且仍按生产 fail-closed 抛 503，客户端会以为登录失败，但数据库已经产生一个客户端拿不到的有效令牌。修复后，入口限流故障继续 503，成功后的清理故障只记录告警并返回已提交结果；新增测试固定这一区别。

### 替代方案及取舍

可以使用滑动窗口或令牌桶获得更平滑的边界，但固定窗口复用了已经验证的 Lua，且返回 TTL 简单。本卡阶段使用 JWT Secret 加显式域隔离减少配置项，代价是 JWT 轮换会使旧桶不可寻址；后续学习卡 048 已迁移到独立限流 Secret。此阶段在可信代理配置完成前刻意不读取可伪造 Header，后续再叠加访客桶。

### 测试与验证

单元和集成测试覆盖动作隔离、大小写规范化、键不含邮箱、429/`Retry-After`、Redis 入口故障策略、成功后清理故障、关闭注册、路由接入和成功清桶。本轮后端 97 个通过、3 个环境相关跳过、综合覆盖率 81%；前端 20 个套件、57 个测试通过，类型检查、零警告 Lint、Ruff 和格式检查通过。

## 学习卡 048：可信代理不是读取一个 Header

日期：2026-07-25

### 业务问题

账号邮箱桶可以限制集中爆破，但攻击者只要轮换邮箱就能绕过。公开部署需要访客维度；API 又通常位于 HTTPS 网关后，TCP 对端是代理而非用户。如何取得客户端地址，同时不接受攻击者伪造的 `X-Forwarded-For`，是这阶段的核心边界。

### 原有方案及限制

直接取 Header 最左侧实现最简单，却完全由客户端控制。完全忽略 Header 又会让所有访客共享代理地址。让 Uvicorn 自动处理 Proxy Headers 看似省事，但应用随后只看到被改写的 `scope.client`，无法再验证原始最后一跳是否可信。只用 IP 桶也会误伤校园网、公司网和 CGNAT 用户，且无法限制多个来源攻击同一邮箱。

### 最终方案

Uvicorn 显式使用 `--no-proxy-headers` 保留 TCP 对端。应用只有在对端属于 `trusted_proxy_cidrs` 时才读取 XFF，并从右向左跳过可信代理，取第一个不可信地址。非法、空、非 ASCII 或超过 20 跳的链回退到 TCP 对端；配置拒绝全网 CIDR。

认证请求先消耗访客总量桶，再消耗登录/注册账号桶。访客桶跨动作共享，防止轮换邮箱；账号桶分动作，防止分布式集中攻击。成功登录只清账号桶，不清访客桶。IP 和邮箱都用独立限流 Secret 做 HMAC-SHA256，Redis 不保存原值；JWT、AI 凭证加密和限流三类 Secret 分离。

生产侧增加显式 Host 白名单、非 root 容器、生产环境模板和静态预检。预检的 Portfolio 模式要求关闭注册、开启 Demo 保护并配置 HTTPS Web Origin；Proxy 模式要求可信 CIDR。TLS、HSTS 和边缘 DDoS 仍归托管网关。

### 遇到的问题与定位过程

审计 Uvicorn 帮助时发现它支持自动 Proxy Headers，并默认只信任特定来源。若生产部署恰好通过本机 Sidecar，自动改写可能先于应用逻辑发生。最终不是同时使用两套信任机制，而是关闭 Uvicorn 改写，把对端验证集中到可单测的应用函数。

第一版配置只验证 CIDR 语法，`0.0.0.0/0` 仍是合法网络，却等于信任所有连接者。代码审查时补上 prefix length 为 0 的拒绝测试。这说明“格式合法”和“安全策略允许”是两个层次。

真实容器测试使用 Docker 网桥模拟可信最后一跳。三个请求在 XFF 左侧放入不同伪造值，并轮换邮箱；右侧真实访客保持一致，结果为 401、401、429。更换右侧地址后恢复 401，证明解析方向与访客隔离正确。恶意 Host 得到 400，容器 `id` 显示 UID 999。

### 替代方案及取舍

可以完全依赖云平台或 WAF 的限流，运维更集中，但本地无法复现且不同平台配置不可移植；应用双层桶仍能保护昂贵的密码哈希和数据库入口。可以保存明文 IP 方便封禁和分析，但会扩大隐私数据与日志风险；本项目只保存短 TTL HMAC。可以按 IPv6 /64、ASN 或设备指纹聚合，但需要真实流量和隐私评审，当前不伪装成已完成。

### 测试与验证

后端新增可信链、非法链、IPv6、伪造 Header、访客邮箱轮换、生产 Secret/Host/CIDR 和预检测试。本轮后端 109 个通过、3 个环境相关跳过、覆盖率 82%；前端 20 个套件、57 个测试继续通过，OpenAPI 哈希不变。

Docker/PostgreSQL/Redis 实测同访客不同邮箱为 401/401/429，`Retry-After=60`；异访客为 401；Redis 有 2 个访客和 3 个账号摘要键，均无 IP/邮箱。恶意 Host 为 400，API 以 `uid=999(nutripilot)` 运行，命令包含 `--no-proxy-headers`。模拟生产配置执行 `production_preflight --portfolio --behind-proxy` 返回 ok。验收后临时桶和配置已恢复。

### 面试回答模板

> 我没有直接相信 X-Forwarded-For。Uvicorn 保留 TCP 对端，只有最后一跳位于显式代理 CIDR 时，应用才从右向左剥离可信代理，非法或超长链回退到对端，并拒绝全网 CIDR。认证先走跨邮箱共享的访客桶，再走按 login/register 分开的账号桶；成功登录只清账号桶。IP 和邮箱通过独立 Secret 做 HMAC，Redis 不保存原值。真实容器用 Docker 网桥模拟代理，攻击者更换左侧伪造地址和邮箱仍得到 401/401/429，另一个访客为 401。容器还以非 root 运行，生产预检验证 Host、HTTPS CORS、保护开关和依赖 URL。我明确把 TLS/WAF 和真实代理网段留给托管平台，尚未声称完成公网部署。

### 可继续追问的问题

- 为什么右向左而不是左向右解析代理链？
- Uvicorn 和应用同时处理代理 Header 会发生什么？
- 漏配与过宽配置分别是 fail-safe 还是 fail-open？
- 为什么成功登录不能重置访客桶？
- CGNAT 和 IPv6 隐私地址如何影响公平性？
- 静态预检、Readiness 和外部可用性探测有什么区别？

## 学习卡 049：把“本地能跑”收敛成可发布的同源生产镜像

### 业务问题

项目已经有 Expo Web、FastAPI、PostgreSQL、Redis、演示账号和安全预检，但前后端仍是两个本地端口。作品集需要一个可公开访问、可复现、可回滚且不会泄露 Secret 的发布包。Expo SQLite Web 又依赖 WASM/Worker 和 COOP/COEP，普通静态上传不足以证明可用。

### 原有方案及限制

独立静态站 + API 看似符合“前后端分离”，却形成部署循环：Web 构建需要 API URL，API CORS 需要 Web Origin，静态平台还必须配置安全头。Render 免费 Web Service 不支持独立 pre-deploy command，免费 PostgreSQL 30 天到期，直接写“生产部署”会夸大。

### 遇到的问题与定位过程

代理方面没有猜测 Render 入站网段。免费部署不采信转发 Header，访客桶退化为共享平台代理桶，阈值提高以减少误伤；账号 HMAC 桶仍有效。这会暴露共享桶 DoS 风险，但不会接受伪造 IP，属于安全退化。

## 学习卡 050：平台内置环境变量不等于 Blueprint 可引用变量

日期：2026-07-26

### 业务问题

Render 首次公网 Blueprint 同步已经成功读取发布分支并创建数据库、Key Value 和 Web Service，但同步随后提示找不到 `RENDER_EXTERNAL_HOSTNAME` / `RENDER_GIT_COMMIT`，公网构建无法继续。

### 原有方案及限制

第一版把 Render 内置变量当成普通服务环境变量，通过 `fromService.envVarKey` 再映射成 `NUTRIPILOT_PLATFORM_EXTERNAL_HOST` 和 `NUTRIPILOT_RELEASE`。这种写法对 Blueprint 自己声明的变量成立，但 Render 的运行时内置变量没有进入该引用集合；“容器运行时存在”不代表“基础设施解析阶段可引用”。

### 最终方案

删除两个无效的 Blueprint 自引用。Settings 在没有显式 `NUTRIPILOT_*` 值时，分别回退读取 `RENDER_EXTERNAL_HOSTNAME` 和 `RENDER_GIT_COMMIT`。这样平台适配集中在配置边界，Render 仍能注入 Host 白名单和可观测性 Release，本地、测试和其他平台仍可用显式配置覆盖。

### 遇到的问题与定位过程

同步页先显示三个资源创建成功，随后在两个环境变量步骤明确报告 `environment variable not found`。这说明故障发生在 Blueprint 配置解析，而不是 Docker 构建或应用启动。对照 `render.yaml` 后定位到两个 `fromService` 自引用；数据库和 Redis 的连接串引用正常，因为它们是 Blueprint 资源显式公开的属性。

### 替代方案及取舍

可以在 Render 控制台手工复制 Host 和 Commit，但不可复现且后续同步容易漂移；也可以硬编码公网域名，但服务改名会失效。由 Settings 读取平台内置变量既保留 IaC，又让应用层拥有可测试的兼容逻辑。

### 测试与验证

新增单测模拟 Render 两个内置变量，验证 Host 和 Release 回退值；聚焦生产预检测试 7/7 通过。修复提交推送后需以同一 Blueprint 重新同步，并继续验证公网健康、登录和浏览器数据同步。

### 面试回答模板

> 第一次 Render 同步失败不是容器问题，而是 IaC 解析阶段和运行时环境阶段混淆。我原来用 `fromService.envVarKey` 引用 Render 内置变量，但该机制只能解析 Blueprint 暴露的资源属性或用户变量。修复时没有在控制台手填，而是删除无效引用，让 Settings 以显式 `NUTRIPILOT_*` 为主、Render 内置变量为回退，并补单测。这样修复可复现、可迁移，也把平台耦合限制在配置边界。

## 学习卡 051：服务器的“今天”不一定是用户的“今天”

日期：2026-07-26

### 业务问题

公网登录和资料同步均成功，首页目标正确显示 2023 kcal，但“今日记录”为 0。服务端只读查询确认 58 条演示数据存在，最新记录却落在 2026-07-25，而上海浏览器已经是 2026-07-26。

### 原有方案及限制

演示重置 CLI 和服务使用 `date.today()` 作为种子锚点。Render 容器按 UTC 运行，部署发生在上海凌晨时，UTC 仍是前一天。代码没有报错、数据库也不为空，但产品语义已经错位；这类问题无法靠健康检查发现。

### 最终方案

新增 `demo_timezone_offset_minutes` 配置，Render 显式设置为 `480`。演示锚点统一由一个可注入时钟的函数计算：先取得带时区的 UTC 时间，再转换到配置偏移后取日期。手工 CLI 仍可用 `--anchor-date` 覆盖，便于复现和测试。

### 遇到的问题与定位过程

先排除登录与同步失败：浏览器目标值已经来自服务端；再使用独立认证请求查询最近 8 天日志，发现所有记录整体落后一天。对照 Render 日志的 UTC 时间和上海日期后定位到 `date.today()`。这说明“数据存在”和“用户当前日期能查到数据”是两个不同断言。

### 替代方案及取舍

可以把容器系统时区改成 Asia/Shanghai，但会影响日志和其他基础设施时间语义；也可以依赖 `zoneinfo`，但精简镜像可能缺少 tzdata。当前产品面向国内演示，使用可配置分钟偏移避免新增系统依赖，同时明确它不是通用历史时区数据库。

### 测试与验证

新增 UTC 2026-07-25 17:30 转换为 UTC+8 后锚点为 2026-07-26 的边界测试；聚焦 Demo 测试 6/6 通过。发布后需要重新执行演示重置，并验证首页今日 4 条记录与 1790 kcal。

### 面试回答模板

## 学习卡 052：安全隔离条件也必须验证写入是否生效

日期：2026-07-26

### 业务问题

最终 Render 版本的公网 API 有 58 条演示日志，当日汇总也是 1790 kcal，但浏览器重新登录后首页显示 0 条。认证、健康检查和服务端数据均正常，只有本地增量同步结果错误。

### 原有方案及限制

本地 `food_logs.id` 是全局主键，远程记录首次落地时优先复用 `client_id`。为避免账号 A 的行被账号 B 覆盖，Upsert 使用 `WHERE food_logs.owner_user_id = excluded.owner_user_id`。演示重置会轮换用户 ID，但同一锚点复用确定性 client ID；因此新用户命中旧用户主键时，数据库安全地拒绝更新，却返回一个没有抛错的“写入 0 行”，同步随后仍推进游标。

### 最终方案

应用远程 Upsert 前先检查候选本地主键是否被其他账号占用。如果发生跨账号碰撞，为新账号生成随机本地 ID；远程 `server_id` 和 `client_id` 仍保存在行中，所以后续更新和删除可以正常定位。旧账号离线数据不删除，新账号也能完整同步。

### 遇到的问题与定位过程

先用独立公网请求证明服务端有 58 条日志、当日 1790 kcal、同步游标为 174，再排除后端种子和日期问题。结合“重置后用户 ID 改变”和“种子 client ID 可复现”，检查本地 Upsert 后发现跨账号冲突分支没有报错，也没有验证受影响行数。这解释了为什么监控显示同步请求成功，UI 却为空。

### 替代方案及取舍

登录时直接删除旧账号本地数据实现简单，但破坏离线数据和账号隔离设计；重置时改为随机 client ID 会降低演示数据可复现性，也不能解决一般跨账号 ID 碰撞。为碰撞行重新分配本地主键把修复限制在客户端存储边界，且不改变服务端契约。

### 测试与验证

新增回归测试构造“旧账号占用确定性 client ID、新账号拉取同一远程记录”，断言插入使用新的本地 ID 且 owner 为新账号。聚焦同步测试 4/4、前端全量 20 套件/58 测试、TypeScript 和零警告 Lint 全部通过。

### 面试回答模板

> 公网重登后 API 有 58 条数据但首页为零。根因不是网络，而是演示重置轮换用户 ID、同时复用确定性 client ID；本地跨账号 Upsert 保护拒绝覆盖旧行，却仍推进了同步游标。我先用 API 数据和游标缩小范围，再让跨账号碰撞生成新的本地主键，继续用 server/client ID 对齐远程变化。修复保留了旧账号离线数据和隔离边界，并用账号轮换回归测试验证。

### 可继续追问的问题

- 为什么不能直接删除旧账号的本地数据？
- `ON CONFLICT ... WHERE` 写入 0 行为什么没有抛错？
- 本地主键、client ID 和 server ID 分别承担什么职责？
- 如果同步历史超过分页上限，如何设计快照恢复？
