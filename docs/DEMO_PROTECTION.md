# 公共演示账号保护：限流、配额与自动重置

## 1. 威胁模型

共享演示账号的密码会公开，任何访客都可以并发登录。即使它不能使用付费 OpenAI Key，攻击者仍可能高频调用规则 AI、无限新增记录和对话、占满数据库，或者在面试演示前把样例数据改乱。本阶段保护的是已标记 `is_demo=true` 的共享账号，不把它包装成完整的公网 WAF 或账号风控系统。

## 2. Redis 原子限流

演示请求分为两个桶：

| 动作    |    默认阈值 | 覆盖范围                                                |
| ------- | ----------: | ------------------------------------------------------- |
| `write` | 60 秒 30 次 | 新增食品/日志、修改或删除日志、修改资料、创建或删除对话 |
| `ai`    | 60 秒 12 次 | 文本识别、单轮助手、周报和对话消息                      |

Redis Lua 脚本在一次原子执行中完成 `INCR`、首次请求设置 `PEXPIRE` 和读取剩余 TTL，避免两个 API 实例同时看到“计数不存在”并分别初始化。超过阈值返回 HTTP 429，并把 Redis TTL 向上取整后写入 `Retry-After`。

键格式为 `nutripilot:demo-rate:{user_uuid}:{action}`，不包含邮箱、IP、问题正文或饮食内容。每次重置都会轮换用户 UUID，因此旧限流键自然与新账号隔离，并由 TTL 自动过期。

Demo 写入与 AI 操作仍按共享账号总量限流，这能可靠限制总资源消耗；登录/注册入口已经在可信代理后增加访客桶，但它不细分登录后的 Demo 操作。代价是一个访客的高频写入仍会占用其他访客的共享额度。若要按访客公平分配 Demo 写入，需要把已解析的可信访客摘要安全绑定到会话或请求上下文，不能让客户端自行声明。

## 3. Redis 故障策略

- 开发环境默认 `demo_protection_fail_closed=false`：Redis 暂时不可用时记录不含敏感数据的错误类型，并允许请求继续，方便无 Redis 的本地开发。
- 生产环境要求 `demo_protection_fail_closed=true`：Redis 故障时演示写入和 AI 请求返回 503 与 `Retry-After: 30`，防止保护层失效后无限放行。
- `Settings` 会拒绝“生产环境启用演示保护但未失败关闭”的配置，避免部署者忘记设置。

这里的 fail-closed 只影响受保护的演示操作；普通账号和只读接口不访问这个限流桶。当前 `/ready` 只检查 PostgreSQL，因此 Redis 故障不会把整个 API 标记为不就绪，这是为了避免普通读流量被演示能力拖垮；部署监控仍应单独探测 Redis。

## 4. 资源配额

默认上限：

- 100 条演示饮食日志，种子初始占 58 条；
- 10 个演示私有食品，种子初始占 2 个；
- 8 个助手对话；
- 每个对话 40 条消息，也就是最多约 20 轮用户/助手消息。

达到上限时创建请求返回 403，并提示等待重置。日志的幂等重放先检查 `client_id`，已有请求仍能返回原结果，不会因为已达上限破坏离线重试语义。对话消息同样先检查 `client_message_id`，再为新的一轮预留两个消息位置。

当前配额采用“查询计数后写入”，两个完全并发的请求仍可能同时看到剩余一个位置并短暂超出上限。Redis 频率限制和周期重置降低了影响，但这不是严格并发配额。若公开流量需要硬上限，应在 PostgreSQL 中按用户获取 advisory transaction lock，或者使用 Redis Lua 做原子配额预留，并设计数据库失败后的补偿释放。

## 5. 多实例安全的自动重置

设置 `NUTRIPILOT_DEMO_RESET_INTERVAL_MINUTES` 大于 0 后，每个 API 实例都会启动轻量后台循环。启动时不会立即清库，而是先等待一个完整周期，避免每次滚动发布都意外踢出演示用户。

周期到达后实例使用 Redis `SET key token NX EX ttl` 竞争锁：

1. 只有拿到锁的实例执行已有的单事务种子重置；
2. 重置轮换用户 ID、删除旧 Refresh Token，并把锚点日期更新为当天；
3. 释放锁时用 Lua 比较随机所有权 Token，只有锁持有者才能删除；
4. 进程中途崩溃时，锁由 TTL 自动释放，避免永久死锁。

锁 TTL 必须大于一次重置的最大执行时间。当前默认 300 秒，真实部署应监控重置耗时；如果任务可能超过 TTL，应增加锁续租，而不是仅提高一个拍脑袋的常量。

自动重置密码只允许通过部署环境的 `NUTRIPILOT_DEMO_RESET_PASSWORD` 注入。启用周期但没有密码时，配置校验直接拒绝启动。日志只记录 `demo.reset.completed` 或异常类型，不记录邮箱、密码和数据内容。

## 6. 本地与外部调度命令

一次性执行带分布式锁的重置：

```powershell
$env:NUTRIPILOT_DEMO_RESET_PASSWORD = "replace-with-at-least-10-characters"
docker compose exec -e NUTRIPILOT_DEMO_RESET_PASSWORD api `
  python -m app.cli.reset_demo --anchor-date 2026-07-22
Remove-Item Env:NUTRIPILOT_DEMO_RESET_PASSWORD
```

输出只包含 `executed` 和锚点日期。`executed=false` 表示另一个实例或任务正在持锁。生产环境还必须显式传入 `--allow-production`。这个一次性命令也可以交给部署平台的 CronJob 使用；不要同时启用内部循环和外部高频 Cron，除非明确依赖同一把锁协调。

## 7. 真实验收

2026-07-22 在 Docker Compose 的 PostgreSQL 17、Redis 7.4 和 API 容器中临时使用“每分钟 2 次 AI、最多 58 条日志”完成：

- 分布式重置执行成功，输出 `executed=true`；
- 人工预占重置锁后，第二个重置输出 `executed=false`，没有重复清库；
- 同一演示用户连续生成周报得到 200、200、429，第三次 `Retry-After` 为 60 秒；
- 尝试创建第 59 条之外的新日志返回 403；
- Redis 中生成两个动作键，均不包含演示邮箱；
- 验收后容器恢复默认开发阈值，API、PostgreSQL 和 Redis 健康。

自动化回归为后端 88 个通过、3 个环境相关跳过、综合覆盖率 80%；前端仍为 19 个套件、56 个测试通过。

## 8. 仍未解决的公网边界

- 注册接口仍开放，攻击者可以创建大量普通账号绕过“仅演示账号”配额；公开部署前应关闭公开注册、加入邀请机制，或实现独立的注册/登录风控。
- 认证入口已有可信代理访客限流，但 Demo 写入/AI 仍是共享桶；验证码、封禁名单、WAF 和 DDoS 防护尚未接入。
- 配额不是严格并发硬上限。
- 内部周期循环已经实现，但尚未在真实公网多副本环境连续运行数日；当前真实验收覆盖一次性锁、重复实例跳过和数据库重置。
- Redis 可用性尚未进入外部告警，Sentry 和生产监控仍待部署。
